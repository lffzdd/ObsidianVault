要回答这个问题，关键是要意识到一件事：`console`、`document`、`navigator` 这些**根本不属于 JavaScript 语言本身**。ECMAScript 标准只规定了 `Object`、`Array`、`Math`、`JSON`、`Promise` 这些。如果你下载 V8 源码自己编译，跑它附带的 `d8` shell，里面没有 `document`，也没有 `console`（V8 自己提供了一个简化版的 print，但那也不是规范）。

所以这些东西是"从外面塞进来的"。下面自底向上看清楚。

## 第 0 层：浏览器本身就是个原生程序

Chrome、Firefox、Safari 在你的操作系统看来，就是一个用 C++（Firefox 还有 Rust）写的可执行文件。它要做的事情很多：发网络请求、解析 HTML、跑 CSS 布局、调 GPU 画像素、和操作系统通信。内部分成若干个大模块：网络栈、HTML 解析器、渲染引擎（Blink / Gecko / WebKit）、JavaScript 引擎（V8 / SpiderMonkey / JavaScriptCore）等。

注意 JS 引擎只是其中**一个模块**，它和渲染引擎是分开的。

## 第 1 层：JS 引擎只是一个库

V8 本质上是一个 C++ 库，它会做的事：

- 把 JS 源码解析成 AST
- 编译成字节码 / JIT 出机器码
- 执行，管理堆、垃圾回收
- 实现 ECMAScript 标准的内置对象

仅此而已。它**完全不知道**什么是 DOM、什么是网络、什么是控制台。它甚至不知道自己跑在浏览器里还是 Node.js 里还是 Deno 里——这些都是它的"使用者"。

## 第 2 层：嵌入 API（Embedding API）—— 关键的一层

V8 暴露了一组 C++ API，让"使用 V8 的程序"（叫 embedder，嵌入者）可以：

- 创建一个 JS 执行环境（Context）
- 往这个环境的全局对象上挂属性
- **把任意一个 C++ 函数注册成一个 JS 函数**
- 让 C++ 持有 JS 对象的引用，反过来也一样

简化的样子大概是这样：

```cpp
// C++ 这边
void MyCppCallback(const v8::FunctionCallbackInfo<v8::Value>& args) {
    // 从 args 里取出 JS 传过来的参数
    // 干你想干的事，比如 printf
    printf("hello from C++\n");
}

// 注册
global_template->Set(
    String::NewFromUtf8(isolate, "myFunc"),
    FunctionTemplate::New(isolate, MyCppCallback)
);
```

注册完之后，JS 这边写 `myFunc()`，控制流就会跳进 `MyCppCallback` 这个 C++ 函数里执行。

**这就是所有 Web API 的本质：一座座从 JS 到 C++ 的桥。**

## 第 3 层：浏览器是 V8 的"嵌入者"

每打开一个网页，渲染进程（Renderer Process）大致干这件事：

1. 启动 V8，新建一个 Context（一个独立的 JS 世界，互相隔离）
2. 在这个 Context 的全局对象（也就是 `window`）上，把所有 Web API 一个个挂上去：`console`、`document`、`navigator`、`fetch`、`setTimeout`、`localStorage`、`XMLHttpRequest`……
3. 解析 HTML，遇到 `<script>` 把代码丢给 V8 跑

第 2 步里挂上去的每一个，都是 V8 角度的"宿主对象（host object）"，本质上是一个 C++ 对象在 JS 世界里的代理。

## 第 4 层：具体看 console.log

Blink（Chrome 的渲染引擎）里有一个 C++ 类大致是 `Console`。它的 `Log` 方法做的事：格式化参数、通过 DevTools Protocol 推给开发者工具、写日志。

启动时，Blink 用 V8 嵌入 API 做了如下事情（伪代码）：

```cpp
// 创建一个 JS 对象代表 console
Local<Object> console = ObjectTemplate::New(isolate)->NewInstance();

// 把 log 方法挂上去，绑到 C++ 的 Console::Log
console->Set("log", FunctionTemplate::New(isolate, &Console::LogCallback));
console->Set("error", FunctionTemplate::New(isolate, &Console::ErrorCallback));
// ... warn, info, debug, table, ...

// 挂到全局对象上
window->Set("console", console);
```

于是当你写 `console.log("hi")`：

1. V8 在全局对象里查 `console` → 找到那个对象
2. 在它上面查 `log` → 发现是一个 native function（C++ 回调）
3. V8 把 `"hi"` 装箱成 `v8::Value`，调用注册的 C++ 函数
4. C++ 把字符串拿出来，走它该走的路径输出到 DevTools 或终端

## 第 5 层：document 更复杂，但是同一套机制

`document` 背后是一棵真实的 C++ 对象树。Blink 里有大量 C++ 类：`Document`、`Element`、`HTMLDivElement`、`Node`、`Text`、`Attr`……HTML 解析器每读到一个标签，就 `new` 出对应的 C++ 对象，串成 DOM 树。这棵树是真实存在的、占着内存的、C++ 实现的数据结构。

JS 里拿到的 `document`，其实是一个轻薄的 wrapper（V8 对象），它内部有个指针指向那个真实的 C++ `Document` 对象。

当你写 `document.querySelector(".foo")`：

1. V8 调用注册的 C++ 回调
2. 回调进入 Blink 的 CSS 选择器引擎（纯 C++）
3. 在 DOM 树上遍历查找匹配的 Element
4. 找到的 C++ Element 要返回给 JS——这里有个细节：每个 C++ DOM 对象在 JS 世界最多对应一个 wrapper（这样 `===` 才会成立）。所以引擎要么找出已有的 wrapper，要么 new 一个新的并记下来

所以 `document.body.appendChild(x)` 修改的是 C++ 那棵树。然后这个修改会触发 Blink 的样式重算、布局、绘制，最终变成你屏幕上的像素。**JS 只是一个遥控器**，真正的"重活"全是 C++ 在做。

## 第 6 层：navigator 更简单的例子

`navigator.userAgent` 就是 C++ 里有个字符串，getter 把它包成 V8 String 返回——一行代码的桥。

但 `navigator.geolocation.getCurrentPosition(...)` 就涉及更多：渲染进程是沙箱化的，不能直接访问硬件，所以这个调用最终通过进程间通信（IPC）发到浏览器主进程，那边去问操作系统要 GPS / WiFi 定位，结果再 IPC 回来。

## 第 7 层：WebIDL —— 让这套机制可规模化

Web API 有几百个接口、几千个方法。手写每一个 V8 binding 不现实。所以 W3C/WHATWG 用一种叫 **WebIDL** 的接口描述语言来定义所有 API：

```
interface Console {
  undefined log(any... data);
  undefined error(any... data);
  // ...
};
```

浏览器仓库里有代码生成器，吃 WebIDL，吐出对应的 V8 绑定 C++ 代码。所以你看 Chromium 源码会有很多 `*_v8_bindings.cc` 文件，那些都是生成的胶水代码。

---

## 总结一条完整的链路

「`console.log("hi")` 到底发生了什么」自底向上：

1. 浏览器作为 C++ 程序，内置了 Console 模块的实现
2. 浏览器把 V8 作为库链接进来，调 V8 的 API 创建一个 JS 执行环境
3. 在 JS 跑起来之前，浏览器用 V8 嵌入 API 把 `console` 对象注入到全局对象（window）上，并把它的方法绑到对应的 C++ 函数
4. 你的脚本里 `console.log("hi")` 被 V8 解析、编译、执行；执行到方法调用时，V8 发现这是个 native function，于是按调用约定跳进 C++
5. C++ 拿到参数，调内部模块（DevTools 协议、stdout、log 子系统）
6. WebIDL + 代码生成让这套绑定不用手写

如果你把这个心智模型套到任何一个 Web API（`fetch`、`localStorage`、`requestAnimationFrame`、`WebGL`、`Audio`），它都成立——它们都是 JS 世界里的把手，背后是 C++ 真正在执行的逻辑。Node.js 也是同一套思路，只是嵌入者不是浏览器，而是 Node，它注入的是 `process`、`require`、`fs` 这些不一样的全局而已。

如果你想顺着这条线再深入，有几个具体方向：V8 的 `v8.h` 头文件（看嵌入 API 长什么样）、Chromium 的 `third_party/blink/renderer/bindings/` 目录（看生成的绑定代码）、或者一份 WebIDL 规范（看接口是怎么声明的）。
