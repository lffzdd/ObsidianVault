回调没有任何魔法，就是普通的函数调用。

`add_done_callback` 只是把函数存进 Future 的一个列表里：

```python
self._done_callbacks.append(fn)
```

当工作线程执行完任务，在 `return` 之后，框架代码**同步地**遍历这个列表，挨个调用：

```python
for callback in self._done_callbacks:
    callback(self)
```

就是普通的 `for` 循环，在**工作线程自己的调用栈**上顺序执行，没有任何异步或中断。

所以完整的调用栈是：

```
工作线程
  → download() return
  → Future._invoke_callbacks()
  → as_completed 注册的那个 callback()
  → queue.put(future)
  → Condition.notify()
  → 唤醒 as_completed 的线程
```

" 回调 " 这个词容易让人觉得有什么特别的机制，其实就是 " 把函数引用存起来，之后某个时机调用它 "，仅此而已。

你说得对，这里要分两层：

**线程层（`add_done_callback` 这里）**

没有内核参与，纯用户态。工作线程自己执行完任务后，自己调用回调列表，自己 `queue.put()`，自己触发 `Condition.notify()`。内核只做一件事：把挂在 `Condition` 上的线程从等待队列移到就绪队列。内核不知道也不调用任何回调，回调是工作线程在用户态跑的。

**epoll 层（你说的那个机制）**

这里内核确实提供了一个协议：

```
你把 fd + 回调注册进 epoll
内核在 fd 就绪时，把事件写进 epoll 的就绪链表
你调用 epoll_wait() 拿到就绪事件
然后用户态自己去遍历，调用对应的回调
```

内核**不直接调用**你的 fn，它只负责把 " 谁就绪了 " 告诉你，调用 fn 还是用户态自己做的。

所以两层都一样：**内核只管调度线程/通知事件，fn 始终由用户态代码调用**。

真正让内核直接调用用户态 fn 的机制是**信号（signal）**，`kill()` 触发后内核会强行打断进程去跑 signal handler，这才是内核主动调用用户态代码。

你手写过 Promise，那你已经知道答案了——回调的实现和 Promise 完全一样。

用最裸的方式写，不用任何同步原语：

```python
class SimpleFuture:
    def __init__(self):
        self._result = None
        self._done = False
        self._callbacks = []

    def set_result(self, value):
        self._result = value
        self._done = True
        for cb in self._callbacks:   # 就这一行，和你的 Promise 一模一样
            cb(self)

    def add_done_callback(self, fn):
        self._callbacks.append(fn)
```

这和你 JS 里写的 Promise 是同一个东西：

```js
class SimplePromise {
    constructor() {
        this._callbacks = []
    }
    resolve(value) {
        this._value = value
        this._callbacks.forEach(cb => cb(value))  // 完全一样
    }
    then(fn) {
        this._callbacks.push(fn)
    }
}
```

**回调本身没有任何魔法，就是把函数存进列表，完成时遍历调用。**

## [#48] Assistant

- Timestamp: `2026-06-10 18:11:18`

你的 Promise 能工作，是因为 `resolve` 和 `callbacksFulfilled` 在**同一个堆内存对象**里，单进程内共享地址空间，直接引用就行。

跨进程就不行了，因为每个进程有独立的地址空间，你存的函数引用在另一个进程里毫无意义。

跨进程回调的本质变了——**不能传函数引用，只能传数据**，接收方收到数据后自己决定调什么函数。

实现方式就是 IPC，几种常见机制：

**管道 / socket**
```
工作进程完成 → write(fd, result) → 主进程 read(fd) 拿到数据 → 主进程自己调回调
```

**信号**
```
工作进程完成 → kill(parent_pid, SIGUSR1) → 主进程的 signal handler 被触发
```

**共享内存 + 信号量**
```
工作进程把结果写进共享内存 → 释放信号量 → 主进程阻塞在信号量上被唤醒 → 读共享内存
```

本质都一样：**工作进程负责 " 发信号/写数据 "，主进程负责 " 监听/读数据后调函数 "**。回调列表永远在接收方自己的进程里，发送方只管通知，不管调函数。

Python 的 `multiprocessing` 用的就是管道，`ProcessPoolExecutor` 内部有一个专门的结果读取线程，死循环 `read` 管道，读到结果就找到对应的 Future 调 `set_result`，然后回调链就和单进程一样跑起来了。

**管道：传数据，不传函数**

管道传的是序列化后的结果值（pickle），不是函数。接收方收到数据后，自己在本进程的回调列表里找到对应的函数调用。

```
工作进程：pickle(result) → write(pipe)
主进程：read(pipe) → unpickle → 找到 future → set_result(value) → 跑回调列表
```

函数从来没有跨进程，只有数据跨进程。

---

**信号：对，是内核机制**

信号是内核提供的唯一一个 " 内核主动打断用户态 " 的机制。你注册 `signal(SIGUSR1, handler)`，本质是告诉内核 " 把这个函数地址存在我的进程控制块里 "，内核收到信号时，强行把你的指令指针跳转到 handler，跑完再跳回来。

这才是真正的 " 内核调用用户态函数 "，和管道、epoll 那种 " 用户态自己轮询/阻塞后自己调函数 " 是不同层次的机制。

---

所以两类机制的本质区别是：

| | 谁调函数 |
|---|---|
| 管道 / epoll / Condition | 用户态代码自己调，内核只负责数据传递和线程调度 |
| 信号 | 内核强行跳转到函数地址，用户态无法拒绝 |

对，你已经想清楚了。

" 通知 " 就是**线程 B 调一个系统调用，告诉内核把线程 A 移出等待队列**。

线程 A 睡觉时，内核把它挂在一个等待队列上（和某个条件绑定）。线程 B 调 `notify()`，底层是一个 syscall，内核收到后找到那个等待队列，把线程 A 移到就绪队列，下次调度到它时它就醒了。

所以 " 通知 " 不是发消息给线程 A，而是**操作内核数据结构**——把线程 A 从一个队列移到另一个队列。线程 A 感知不到 " 通知 " 这个动作，它只是某一刻被调度到了，从 `wait()` 返回，继续跑。

```
线程A 调 wait()
  → syscall：把自己加入等待队列，让出 CPU

线程B 调 notify()
  → syscall：把等待队列里的线程A移到就绪队列

调度器运行
  → 发现线程A在就绪队列
  → 分配 CPU，线程A从 wait() 返回
```

整个过程线程 A 和线程 B 从没有直接通信，通信的对象都是内核，内核是中间人。

## [#54] Assistant

就是系统调用。

线程 B 调 `notify()`，Python 的 `threading.Condition.notify()` 最终会调一个 syscall，比如 Linux 上是 `futex(FUTEX_WAKE)`。

```
线程B：futex(addr, FUTEX_WAKE, 1)
         ↓
       内核：找到挂在 addr 这个地址上的等待队列
             取出一个线程，移到就绪队列
```

`futex` 的设计就是这样：

- 线程 A 睡觉时调 `futex(addr, FUTEX_WAIT)`，内核把它挂在 `addr` 对应的等待队列上
- 线程 B 唤醒时调 `futex(addr, FUTEX_WAKE)`，内核找到同一个 `addr` 的等待队列，把里面的线程移出来

`addr` 是一个内存地址，是两个线程之间约定好的 " 集合点 "，内核用它来索引等待队列。

所以本质是：**线程 B 没有直接操作线程 A，而是操作了一个内核数据结构（以 addr 为 key 的等待队列），内核负责把对应的线程移到就绪队列。**

线程 B 能做到这件事，就是因为 syscall 是用户态和内核之间的协议——任何线程都可以通过 syscall 请求内核做任何内核允许的操作，包括唤醒另一个线程。

所有这些机制的本质都是同一个模式：

**内核提供一张表，用户态按协议往里注册，内核在特定时机执行。**

| 机制 | 注册什么 | 内核在什么时机执行 |
|---|---|---|

没有内核配合，用户态什么都做不了——你无法让一个睡着的线程醒来，无法监听 fd，无法跨进程通知，因为这些都涉及调度，而调度权在内核手里。

用户态能做的所有 " 异步 "、" 回调 "、" 通知 "，往深了看都是在内核提供的某张表上注册，然后等内核在约定时机回来执行。这是用户态和内核之间最根本的协议。
