MVC 和 DDD 都有清晰的演进逻辑，为什么突然蹦出一堆 `base`、`core`、`utils`？它们是从哪来的？

答案其实一句话：
> **MVC 和 DDD 只是“纵向的业务流程”；但现实开发中，有大量的代码根本不属于任何业务，它们是“横向的工程辅助”。**

---

### 来龙去脉：工程师们遇到了 4 个工程灾难

当你兴致勃勃地用 MVC 或 DDD 写完几个业务后，你会突然发现：**整个项目快被重复代码、系统杂质给淹没了。**

#### 灾难 1：面向对象的“疯狂复制粘贴” ➔ 催生了 `base/`
* **问题**：你建了 `UserEntity`、`OrderEntity`、`GoodsEntity`……每个文件第一行都要写：
  `id: string; createdAt: Date; updatedAt: Date; isDeleted: boolean;`
  写了 20 个表，你复制粘贴了 20 遍。
  再比如每个 Controller 报错都要写一遍：`return { code: 500, msg: 'error' }`。
* **解决办法**：程序员说，面向对象不是有**“继承”**吗？我们抽一个公共爹出来吧！
* **于是诞生了**：`base/` 目录。
  它的出现完全是为了**解决面向对象里的代码重复**，给别人当爹（父类）用的。

---

#### 灾难 2：有些代码根本不归任何业务管（横切关注点） ➔ 催生了 `core/`
* **问题**：
  * “用户下单”属于订单业务；
  * “修改密码”属于用户业务；
  * **但是，“服务器启动时怎么连数据库？”、“每个请求进门时怎么查 Token 鉴权？”、“系统突然崩了怎么发钉钉报警？”**
  这些东西算订单还是算用户？
  它们谁也不算，它们是**整座大厦的地基和水电路（系统内核）**。
* **解决办法**：如果不给它们找个地方，Controller 和 Service 就会被这些与业务无关的技术代码污染得一塌糊涂。
* **于是诞生了**：`core/` 目录（有的框架叫 `kernel/` 或 `framework/`）。
  它的出现是为了安放**应用赖以生存的系统级能力**。

---

#### 灾难 3：模块间的“先有鸡还是先有蛋”死循环 ➔ 催生了 `common/`
* **问题**：
  * 订单模块（`order`）需要知道用户类型是不是 VIP。
  * 用户模块（`user`）的个人中心里，又想显示用户的最新订单状态。
  * 这两个模块如果互相 `import` 对方的代码，编译器就会直接报警：**循环依赖（Circular Dependency）**！系统死锁了。
* **解决办法**：找一个**绝对中立的第三块地皮**。把大家都要用的常量、状态枚举抽出来放进去，两边都去依赖这个中立地皮，谁也不直接依赖谁。
* **于是诞生了**：`common/`（或者 `shared/`）目录。
  它的出现是为了**打破模块间的相互缠绕和循环依赖**。

---

#### 灾难 4：纯数学/格式转换函数到处乱丢 ➔ 催生了 `utils/`
* **问题**：格式化一个日期 `2026-09-23`、把密码进行 MD5 加密、手机号正则表达式校验……这些代码如果塞进 `service` 或 `domain`，简直是侮辱了业务模型的高贵纯洁。
* **解决办法**：放进一个“垃圾桶”，谁要用谁静态调用。
* **于是诞生了**：`utils/`（实用工具集）。

---

### 终极全景图：十字交叉模型

把它们和 MVC/DDD 放在一起，你脑海里的工程全景就应该是这样的：

```text
               【纵向：业务流（MVC / DDD 负责的事）】
                      用户业务       订单业务       商品业务
                         │              │              │
┌──────────────┐         ▼              ▼              ▼
│  横向工程支撑 │   ┌──────────┐   ┌──────────┐   ┌──────────┐
│              │   │Controller│   │Controller│   │Controller│
│  1. base     │───┼──────────┼───┼──────────┼───┼──────────┼── 继承公共父类
│  2. core     │───┼──────────┼───┼──────────┼───┼──────────┼── 全局守卫拦截、错误捕获
│  3. common   │───┼──────────┼───┼──────────┼───┼──────────┼── 共享公共枚举、状态码
│  4. utils    │───┼──────────┼───┼──────────┼───┼──────────┼── 纯工具函数（日期/加密）
└──────────────┘   │ Service  │   │ Service  │   │ Service  │
                   │(或Domain)│   │(或Domain)│   │(或Domain)│
                         │              │              │
                         ▼              ▼              ▼
                   ┌──────────┐   ┌──────────┐   ┌──────────┐
                   │Repository│   │Repository│   │Repository│
                   └──────────┘   └──────────┘   └──────────┘
```

* **纵向**（一列一列的）：是你的 **业务模块**（MVC / DDD），负责赚钱的业务逻辑。
* **横向**（切穿所有列的）：是这四个 **辅助目录**（Base、Core、Common、Utils），负责给所有业务提供通用支撑。

这样看，它们的来历和定位是不是就非常合情合理了？
