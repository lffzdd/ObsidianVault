这个写法是很多人会自然想到的一步，但这里面埋了好几个“以后会打自己的坑”。
你这个：

```python
def match_coupon_for_order(
    amount: float,
    brand: str,
    coupons_map: dict = load_config()["coupons"]
)
```

表面上看很爽：

- services 直接调用 `match_coupon_for_order(amount, brand)`
- 配置自动读好了

但从**底层机制 + 架构演化**来看，会有三个明显问题。

---

## 1. Python 默认参数的“时间点”问题

关键点：**默认参数是在函数定义时计算的，不是在调用时。**

也就是说：

```python
coupons_map: dict = load_config()["coupons"]
```

这行代码在 **导入 `coupon_rule` 模块的那一刻** 就执行了，而不是每次调用时才执行。

后果：

- 你改了 `config.yaml`，重新调用 `match_coupon_for_order`，**不会生效**，除非整个进程重启或重新导入模块
- 如果将来你想支持“热更新规则”，这个写法直接卡死你

这个叫“默认参数值只初始化一次”，在很多地方都容易埋雷。

---

## 2. 还是耦合了 base → core 的边界，只是藏得更深

你现在做的是：

- 在 `coupon_rule.py` 里 `load_config()`
- 相当于 core 层在主动下探到 base 层拿东西

从依赖方向上看，还是：

```text
core.coupon_rule 依赖 base.config
```

只是你把这个耦合藏到了默认参数里，而不是函数体里，**对读代码的人更不透明**。

未来别的同事（包括未来的你）看到函数签名只会以为它是纯业务函数：

```python
match_coupon_for_order(amount, brand)
```

结果底下悄悄读了配置和文件系统，这种“隐藏 I/O”会让：

- 单元测试变得难写（没法轻易给它假数据）
- 调试变得奇怪（看起来只是算规则，实际上在访问文件）
- 边界分析变得不清晰（core 和 base 究竟谁依赖谁？）

从架构视角，它破坏的是一个重要原则：

> 业务层应该“使用配置”，而不是“偷偷知道配置是怎么来的”。

---

## 3. 配置不可替换、不可注入，未来灵活性被锁死

你现在的 `coupons_map`：

- 永远来自 `config.yaml`
- 永远通过 `load_config()`
- 永远在导入时就锁死

但未来很常见的变化有：

- 券规则一部分从配置文件来，一部分要从数据库拉
- 想不同门店、不同环境使用不同配置（A 环境这套券，B 环境那套券）
- 想写测试：给规则函数传一套“假规则”看看匹配结果是否正确

在这些场景下，你都希望 `match_coupon_for_order` 变成一个 “**纯函数 + 明确入参**”：

```python
def match_coupon_for_order(amount: float, brand: str, coupons_map: dict):
    ...
```

然后由外面（services / 上层 core）决定：

- coupons_map 是用 config.yaml 读的
- 还是从数据库查的
- 还是测试里自己构造的

这样“规则函数”就变成**可注入、可测试、可替换**的模块，不是死死绑在 config.yaml 上。

---

## 那应该怎么设计比较健康？

推荐你这样分两层：

### ① 纯业务规则函数（core/coupon_rule.py）

```python
def match_coupon_for_order(amount: float, brand: str, coupons_map: dict):
    # 只关心根据 coupons_map 选一条合适的券
    ...
```

它：

- 不读配置
- 不访问文件
- 不依赖 base
- 你可以轻松在测试里写：
	`match_coupon_for_order(200, "某品牌", fake_coupons_map)`

### ② 在 services 里“组装规则环境”

```python
from base.config import load_config
from core.coupon_rule import match_coupon_for_order

def preview_unissued_orders():
    config = load_config()
    coupons_map = config["coupons"]

    # 再去查订单…
    for record in records:
        coupon = match_coupon_for_order(
            record["recharge_amount"],
            record["sub_brand_name"],
            coupons_map,
        )
```

这里才是“我决定这次规则基于哪套配置”的地方。
以后要换规则来源，只要改这里，而不用动规则函数本身。

## 如果你真的想“偷个懒”，可以用一个小 wrapper，但保持内核干净

你可以这么玩（兼顾“爽”和“架构干净”）：

```python
# core/coupon_rule.py

def match_coupon_for_order(amount: float, brand: str, coupons_map: dict):
    ...

# 方便现在使用的一个“糖”，但放在 services 里会更好
from base.config import load_config

def match_coupon_with_default_config(amount: float, brand: str):
    config = load_config()
    coupons_map = config["coupons"]
    return match_coupon_for_order(amount, brand, coupons_map)
```

然后在 `services` 里你可以先用糖版本，等以后需求变了，再慢慢替换成显式传 coupons_map 的写法。

---

### 一句话总结你的这个写法的问题

> `coupons_map = load_config()["coupons"]`
> 放在默认参数里：
>
> - 评价时机不在你控制（导入时就跑）
> 
> - 把 core 和 base 耦合在一起
> 
> - 把 I/O 和业务逻辑混在一起
> 
> - 让未来的测试、变更都变难
> 	

你现在的直觉是对的：**配置应该由上层决定，规则只吃参数、不关心来源。**
这就是从“写能跑的代码”向“写能演化的代码”迈的那一步。
