# ripgrep 来龙去脉

### **ripgrep 是一款用 Rust 编写的命令行文本搜索工具，它在你指定的目录里递归地、极速地查找匹配某个正则表达式的文本行，可以理解为"grep 的现代化重写版"，默认就懂 .gitignore、默认跳过二进制和隐藏文件、默认并行搜索，因此在大型代码库里通常比 grep / ack / ag 都快一个量级。**

要真正弄懂 ripgrep 是什么，光看一句定义没用。下面我从最底层的"在文件里找一行字"这件事开始，一层一层往上盖楼，把它的来龙去脉、技术原理、和你为什么会在 VS Code、Neovim、各种 IDE 里"无意中"用到它，全部讲透。

---

### **第 0 层：人类最原始的需求——"在一堆文本里找东西"**

计算机自诞生起就有一个最基础的诉求:**给我一坨文本,告诉我哪一行包含某个模式**。

最早的 Unix 系统(1970 年代初,贝尔实验室)里,这件事是通过一个叫 `ed` 的行编辑器完成的。`ed` 里有一个命令 `g/re/p`,意思是:

- `g` = global(全局)
- `re` = regular expression(正则表达式)
- `p` = print(打印)

也就是"全局地,把匹配这个正则表达式的行打印出来"。

1973 年,Ken Thompson(Unix 之父之一)觉得这个功能太常用了,干脆把它从 `ed` 里抽出来做成一个独立的小程序,名字就直接取自那个命令——**`grep`**。从此,"grep 一下"就成了程序员日常词汇,甚至变成了动词。

这就是这一切的起点:**grep 是一个把"在文件中找匹配正则的行"这件事独立出来的命令行工具**。

---

### **第 1 层:正则表达式引擎——所有此类工具的"心脏"**

要"找到匹配某个模式的行",核心问题是:**怎么高效地判断一行字符串是否匹配一个正则表达式?**

这里有两大技术路线,理解它们对理解 ripgrep 至关重要:

**路线 A:NFA / DFA(有限自动机)**
Thompson 在写 grep 时用的方法:把正则编译成一个状态机,然后让字符一个个"喂"进状态机,看最终能不能走到接受状态。这种方法的特点是**最坏情况也是线性时间** $O(n)$,n 是文本长度,跟正则的复杂度几乎无关。极其稳定、极其快。

**路线 B:回溯式(Backtracking)**
PCRE、Perl、Python 的 `re` 模块、Java 的正则等大多走这条路。它支持更丰富的特性(反向引用 `\1`、环视 `(?=...)`、递归等),但**最坏情况会指数爆炸**,出现"正则灾难"(catastrophic backtracking),一个看似无害的正则可能让程序卡死几分钟。

GNU grep(我们今天 Linux 上用的 grep)走的是 A 路线,所以它快;但代价是不支持某些"花哨"特性。

**ripgrep 走的也是 A 路线**,而且它用的正则引擎是 Rust 生态里大名鼎鼎的 [`regex` crate](https://docs.rs/regex/latest/regex/),由 ripgrep 的作者 Andrew Gallant(网名 BurntSushi)亲手编写。这个引擎严格保证线性时间复杂度,这是 ripgrep "快"的第一个根基。

---

### **第 2 层:GNU grep 的速度奥秘——为什么纯线性还不够**

只有线性时间,还不足以让 grep 变得"飞快"。GNU grep 的作者 Mike Haertel 在 2010 年写过一封著名的邮件,标题就是 ["why GNU grep is fast"](https://lists.freebsd.org/pipermail/freebsd-current/2010-August/019310.html),核心思想有三点:

1. **避免看每个字节**。利用 Boyer-Moore 算法,大部分字符可以"跳过"不看。比如要找 "hello",发现当前位置字符是 'x',直接跳 5 格——因为 "hello" 里没有 'x'。
2. **避免把输入拆成行**。先在大块内存里粗暴地找 byte 模式,匹配到了再回头定位行边界。"不找行就是最快的找行方法"。
3. **避免把字节复制来复制去**。用 `mmap` 直接把文件映射进内存,零拷贝。

GNU grep 在单文件、纯 ASCII 场景下,至今仍是顶级速度。

但是它有几个**结构性的痛点**,直到 21 世纪才被人正面挑战:

- **不递归友好**:你得自己写 `grep -r` 或者配合 `find ... | xargs grep`。
- **不懂版本控制**:它会傻乎乎地搜 `node_modules/`、`.git/`、`target/`、各种构建产物。
- **不并行**:你有 16 个核心,它只用 1 个。
- **Unicode 支持弱**:对 UTF-8、各种字符类的处理在历史上一直不太好。
- **配置不友好**:命令行参数古老、晦涩。

这些痛点,催生了一波"现代 grep"的浪潮。

---

### **第 3 层:程序员视角的演化——ack → ag → ripgrep**

随着代码库越来越大、Git 几乎一统天下,程序员对 grep 的不满集中爆发。于是出现了三代"代码搜索工具":

**第一代:`ack`(2005 年前后)**
用 Perl 写的,主打"为程序员设计"。它会自动跳过 `.git`、`.svn`、各种二进制文件,只搜代码文件。缺点:Perl 启动慢,正则也用 Perl 的回溯引擎,在大项目里比 grep 还慢。但理念领先——**"搜索工具应该懂程序员的项目结构"**。

**第二代:`ag`(The Silver Searcher,2011 年)**
Geoff Greer 用 C 重写了 ack 的理念,号称"比 ack 快 5\~10 倍"。它读取 `.gitignore`、用 `pthread` 并行、用 `mmap`。一时间风靡。但它的代码质量、Unicode 支持、`.gitignore` 解析的正确性都有不少 bug,而且并行做得不彻底。

**第三代:`ripgrep`(2016 年 9 月发布)**
Andrew Gallant 在博客 [blog.burntsushi.net](https://blog.burntsushi.net/ripgrep/) 发表了一篇名为 *"ripgrep is faster than {grep, ag, git grep, ucg, pt, sift}"* 的长文,用大量基准测试证明:它在**几乎所有场景**(单文件、整个 Linux 内核源码、含 Unicode、各种正则形态)下,要么是第一,要么并列第一,而且代码更小、bug 更少。

这篇文章一夜之间让 ripgrep 出圈。**"ripgrep" 这个名字本身,就是 "rip"(高速、撕裂) + "grep"** 的组合,意思是"撕裂级速度的 grep"。

---

### **第 4 层:ripgrep 凭什么这么快——拆开看技术细节**

把 ripgrep 拆开,你会看到它把上面提到的所有优点叠加,并修补了所有短板:

**(1) 用 Rust + 自研正则引擎**
Rust 的零成本抽象 + 内存安全,让作者可以放心写非常激进的优化(SIMD、并行、复杂状态机),不必担心段错误。`regex` crate 是 NFA/DFA 路线,线性时间保证。

**(2) Teddy 算法——多模式匹配的大杀器**
当你搜的是"字面量"(literal)或者多个候选字面量(比如 `foo|bar|baz`)时,ripgrep 会用一种基于 SIMD 的算法 [Teddy](https://github.com/BurntSushi/aho-corasick/blob/master/src/packed/teddy/README.md)(从 Intel 的 Hyperscan 项目移植),一次比对 16 或 32 个字节,速度比 Boyer-Moore 还快几倍。

**(3) 字面量提取(Literal Optimization)**
即使你写的是复杂正则,比如 `\bfn\s+(\w+)`,ripgrep 也会聪明地从中**提取出字面量子串** `fn`,先用 Teddy 飞快扫一遍,只在候选位置才启动完整正则引擎。这是它在"复杂正则 + 大代码库"场景下碾压所有对手的关键。

**(4) 默认尊重 `.gitignore` / `.ignore` / `.rgignore`**
ripgrep 内置了一个**完整的 gitignore 解析器**(精度比 ag 高),递归时会按 Git 的规则自动跳过被忽略的文件。这意味着你在一个 50GB 的 monorepo 里搜东西,它只会搜真正的源码,不会去碰几十个 G 的 `node_modules` 和 `target/`。

**(5) 自动跳过二进制文件和隐藏文件**
默认行为符合"程序员搜代码"的直觉。如果你想搜全部,加 `-uuu`(三个 u,逐级解锁:不读 ignore、搜隐藏、搜二进制),非常有记忆点。

**(6) 多线程并行遍历**
用 [`ignore` crate](https://docs.rs/ignore/latest/ignore/) 做并行目录遍历,生产者—消费者模型,把多核打满。GNU grep 完全没这个能力。

**(7) 优秀的 Unicode 支持**
默认 Unicode-aware:`\w` 会匹配中文、日文、阿拉伯语字符;`-i` 大小写不敏感对所有 Unicode 字符都成立。需要纯 ASCII 速度时可以 `--no-unicode` 关掉。

**(8) 智能输出**
默认终端下高亮颜色、显示文件名和行号、用 `\n` 分隔结果;管道到其他程序时自动关闭这些花哨格式——和现代工具的人体工学一致。

### **第 5 层:你可能早就在用它,只是不知道**

ripgrep 不只是个命令行工具,它已经悄悄变成了**整个开发者生态的搜索基础设施**:

- **VS Code** 的"全局搜索"(Ctrl+Shift+F)底层就是 ripgrep。你打字的瞬间,它在后台调用 `rg` 进程。这也是为什么 VS Code 在巨型项目里搜索响应仍然丝滑。
- **GitHub Code Search**(新版)的部分实现参考了 ripgrep 的算法。
- **Neovim** 生态里的 Telescope、fzf-lua 等插件,默认推荐用 `rg` 做 live grep 后端。
- **Emacs** 的 `consult-ripgrep`、`projectile-ripgrep` 等。
- **JetBrains 系 IDE** 在某些版本中也集成了 ripgrep。
- **Rust 自己的官方文档站** 用 ripgrep 做内容索引的一部分。

可以说,只要你在用任何一款现代代码编辑器,你每天都在间接使用 ripgrep。[ripgrep GitHub](https://github.com/BurntSushi/ripgrep)

### **第 6 层:实战——用一组例子让它具象化**

假设你在一个 Rust 项目根目录:

```bash
# 最基础:递归搜 "TODO"
rg TODO

# 只搜 .rs 文件
rg TODO -t rust

# 排除测试目录
rg TODO -g '!tests/'

# 用正则:找所有 fn 开头的函数定义
rg '^\s*fn\s+\w+'

# 大小写不敏感 + 显示前后 2 行上下文
rg -i -C 2 "error"

# 替换预览(不会真改文件,只输出替换后内容)
rg 'foo' -r 'bar'

# 列出所有匹配的文件(不显示行)
rg -l "panic!"

# 搜整个项目,包括 .gitignore 里的、隐藏的、二进制
rg -uuu "secret"

# 和 fzf 联动做模糊搜索
rg --line-number . | fzf
```

每一个开关都直接对应前面讲过的设计哲学,你应该已经能"看懂它为什么这么设计"了。

---

### **第 7 层:它的局限——什么时候不该用 ripgrep**

为了你心里更有数,也得讲它的边界:

1. **不支持回溯特性**(反向引用、环视等)。这是为了线性时间复杂度的妥协。如果你确实需要 `\1` 这种,得用 `grep -P` 或 `pcre2grep`。ripgrep 也提供 `--pcre2` 选项调用 PCRE2,但会失去线性保证。
2. **不是语义搜索**。它只看字面/正则,不懂代码结构。要按"函数定义""类型引用"搜,需要 [ast-grep](https://ast-grep.github.io/)、[Sourcegraph](https://sourcegraph.com)、`tree-sitter` 这类工具。
3. **不是替换工具**。它的 `-r` 只做输出预览,不改文件。批量替换建议用 [`sd`](https://github.com/chmln/sd) 或 `sed`。
4. **极小项目里优势不明显**。在十几个文件的小项目里,grep 和 ripgrep 速度差异感受不到,这时候用什么都行。

### **一句话回到顶层**

把上面所有层叠起来,你就理解了:**ripgrep 是 1973 年 Unix `grep` 在 50 年技术演化(自动机理论 + SIMD + Rust 内存安全 + Git 生态 + 多核并行 + Unicode)之后的"集大成现代版本"**。它不是凭空冒出来的玩具,而是把过去半个世纪文本搜索领域所有正确的工程决策,在一个工具里同时做对了——这就是它能在三五年内成为整个开发者生态默认搜索引擎的原因。

下次你在 VS Code 里按 Ctrl+Shift+F,可以默默感谢一下那个叫 BurntSushi 的人。

# grep 用法

### **grep 不只是"挑出匹配行的 Linux 命令",它是 Unix 哲学下"用正则表达式过滤文本流"的鼻祖工具,是整个命令行数据处理生态(管道、流式处理、文本即接口)的基石之一。**

你目前的认知其实没错,只是太"扁平"了——你看到的是它的**用法**,但没看到它背后的**世界观**。grep 之所以被无数人写文章、做演讲、甚至当作计算机文化符号反复提及,是因为它代表了一种**思考问题的方式**。下面我把 grep 这个东西从"它到底在做什么"开始,一层层展开,把它从一个命令,还原成一种思想。

---

### **第 1 层:grep 字面上到底在干什么**

最朴素的描述:

> 你给它一段文本(从文件读、或者从别的程序的输出读),再给它一个**模式**(pattern),它把所有"包含这个模式"的行打印出来,其余的扔掉。

举个最直白的例子。假设你有一个文件 `app.log`:

```
2024-05-01 10:00:01 INFO  user=alice action=login
2024-05-01 10:00:02 ERROR user=bob   action=login fail
2024-05-01 10:00:03 INFO  user=alice action=logout
2024-05-01 10:00:04 WARN  disk usage 85%
```

你执行:

```bash
grep ERROR app.log
```

输出:

```
2024-05-01 10:00:02 ERROR user=bob   action=login fail
```

就这么简单。它的工作可以用一句话概括:**逐行读取 → 用模式判断 → 匹配则打印**。

但这"简单"里藏着两件不简单的事:**什么算"模式"**,以及**输入到底从哪来**。

---

### **第 2 层:模式不是字符串,是"正则表达式"**

如果 grep 只能找固定字符串,它就只是一个 `Ctrl+F`,不会成为传奇。它真正的力量在于:**模式可以是正则表达式**。

正则表达式是一种"描述字符串形状"的微型语言。比如:

- `ERROR` —— 字面量,匹配"ERROR"这五个字符
- `^ERROR` —— 行首是 ERROR
- `ERROR$` —— 行尾是 ERROR
- `[Ee]rror` —— Error 或 error
- `user=\w+` —— user= 后面跟一串单词字符
- `[0-9]{3}-[0-9]{4}` —— 三位数字-四位数字(像电话号码)
- `(login|logout)` —— login 或 logout

回到刚才的日志,如果你想找"alice 做的所有事":

```bash
grep 'user=alice' app.log
```

想找"所有警告或错误":

```bash
grep -E '(WARN|ERROR)' app.log
```

想找"所有以 INFO 开头、且包含 logout 的行":

```bash
grep '^.*INFO.*logout' app.log
```

到这里你就能感觉到:**grep + 正则 = 一种声明式的文本查询语言**。你不告诉它"怎么找",你只描述"我想要的行长什么样",剩下的交给它。

---

### **第 3 层:grep 的真正身份是"文本过滤器",不是"文件搜索器"**

这一层是大多数初学者没意识到的关键。你以为 grep 是用来**搜文件**的,其实在 Unix 哲学里,它的本质是:

> **从一条文本流中,过滤出符合条件的行,再输出成新的文本流。**

注意"流"这个词。grep 不在乎你的文本来自哪里——文件、键盘、网络、其他程序的输出,它都吃。这就引出了 Unix 最伟大的发明之一:**管道(pipe,符号 `|`)**。

管道的意思是:**把前一个命令的输出,直接接成后一个命令的输入**。这让 grep 的威力呈指数级放大。看几个真实场景:

**场景 A:从进程列表里找 nginx 相关进程**

```bash
ps aux | grep nginx
```

`ps aux` 列出系统所有进程(几百行),`grep nginx` 把含 nginx 的行挑出来。

**场景 B:从某个命令的海量输出里找错误**

```bash
make 2>&1 | grep -i error
```

编译可能输出几千行,你只关心错误。

**场景 C:看实时日志里 IP 为 1.2.3.4 的请求**

```bash
tail -f access.log | grep '1\.2\.3\.4'
```

`tail -f` 持续吐出新日志,grep 实时过滤。

**场景 D:多级过滤——只要 alice 的、且不是 logout 的**

```bash
grep 'user=alice' app.log | grep -v logout
```

(`-v` 是反向匹配,即"不包含")

**场景 E:数一下有多少错误**

```bash
grep -c ERROR app.log
```

看到 `|` 后,你应该恍然大悟:grep 不是孤立的工具,而是**Unix 工具链里的一节关节**。它跟 `cat`、`sort`、`uniq`、`wc`、`awk`、`sed`、`cut`、`head`、`tail` 等等组合起来,可以解决 80% 的日常文本数据处理需求,根本不需要写程序。

这就是著名的 **Unix 哲学**:

> *"一个程序只做一件事,并把它做好;程序之间通过文本流通信。"*

grep 是这条哲学最经典的代言人之一。

---

### **第 4 层:grep 常用的几个开关——把它从"命令"变成"工具"**

只记 `grep 模式 文件` 是用不出 grep 全部威力的。以下几个开关你应该刻进肌肉记忆:

| 开关 | 作用 | 例子 |
|------|------|------|
| `-i` | 忽略大小写 | `grep -i error log.txt` |
| `-v` | 反向匹配(挑出**不含**模式的行) | `grep -v '^#' config.conf` |
| `-n` | 显示行号 | `grep -n TODO main.c` |
| `-r` | 递归搜目录 | `grep -r 'TODO' src/` |
| `-l` | 只列出含匹配的**文件名** | `grep -rl 'TODO' src/` |
| `-c` | 只输出匹配的**行数** | `grep -c ERROR log.txt` |
| `-w` | 只匹配整词(避免 `cat` 匹配到 `category`) | `grep -w cat words.txt` |
| `-E` | 启用扩展正则(支持 `+ ? \| ()` 不用反斜杠) | `grep -E '(a\|b)+' f.txt` |
| `-A 3` | 匹配行 + 后 3 行(After) | `grep -A 3 ERROR log.txt` |
| `-B 3` | 匹配行 + 前 3 行(Before) | `grep -B 3 ERROR log.txt` |
| `-C 3` | 匹配行 + 前后各 3 行(Context) | `grep -C 3 ERROR log.txt` |
| `--color` | 高亮匹配部分(很多发行版默认开) | `grep --color TODO f.c` |

最后一类要单独说:`-r` 让 grep 从"读一个文件"升级为"在整个目录树里递归搜",这是程序员日常用得最多的形态——也是 ripgrep 直接对标并完爆的场景。

---

### **第 5 层:它的"基本"在哪里——为什么 Linux/Mac 默认就有它**

你提到"Linux 中的一个命令",这其实低估了它的普及程度。grep 是 [POSIX 标准](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/grep.html) 强制要求的命令,这意味着:

- 任何一个声称符合 Unix/POSIX 标准的系统,**必须**自带 grep
- macOS、所有 Linux 发行版、各种 BSD、WSL、甚至 Android 的 shell 里,都有它
- 它是服务器运维、数据分析、开发调试的"通用语言"——你跟任何一个老练的工程师说"grep 一下",他立刻明白你在说什么

可以这么类比:**SQL 之于数据库,grep 之于文本**。它们都是行业级的"通用过滤语言"。

### **第 6 层:grep 在文化和历史里的位置**

回到你之前那个问题里我提到的起点:1973 年,Ken Thompson 把 `ed` 编辑器里的 `g/re/p` 命令独立出来,做成了 grep。这件事的意义远超一个"小工具的诞生":

1. **它定义了"命令行小工具"的范式**——专注、可组合、文本流通信。后来几乎所有 Unix 工具都遵循这套美学。
2. **它把正则表达式从理论(乔姆斯基语言学、Kleene 自动机)推向了大众**。今天每一个程序员都会写一点正则,这种普及很大程度上是 grep 带起来的。
3. **"grep" 这个词进入了英语**。在程序员圈子里,"grep" 已经动词化:"Let me grep the codebase",意思是"让我在代码库里搜一下"。这种动词化的待遇,只有极少数工具享受过(google、xerox 是另外两个例子)。
4. **它催生了一整个家族**:`egrep`(扩展正则版,现在等价于 `grep -E`)、`fgrep`(纯字面量版,等价于 `grep -F`,更快)、`zgrep`(直接搜 .gz 压缩文件)、`pgrep`(搜进程)、`git grep`(Git 内置的代码搜索)、再到现代的 `ack`、`ag`、`ripgrep`。整个家族枝繁叶茂。

---

### **第 7 层:回到 ripgrep——现在你应该看出连接了**

现在再回头看上一轮我讲的 ripgrep,你应该豁然开朗:

- **grep 是"文本流过滤器"**,设计目标是"在一段输入里找匹配的行"。
- 程序员后来发现,他们最高频的需求其实是**"在一个项目目录里找代码"**——这是 grep 的衍生用法(`grep -r`),不是它的原生设计。
- 于是 ack / ag / ripgrep 这些工具,把"递归搜代码项目"做成**第一公民**:默认递归、默认懂 .gitignore、默认跳二进制、默认并行。
- 而 ripgrep 凭借 Rust + 自研正则引擎 + SIMD,在保持 grep 全部威力的同时,把这条衍生路线推到了性能巅峰。

但请注意:**在管道场景里,grep 仍然是王者**。你写 `ps aux | grep nginx`、`tail -f log | grep ERROR`,几乎没人会换成 `rg`(虽然 rg 也支持),因为 grep 启动更快、更轻、几乎所有系统都有。

所以正确的认知是:

> **grep 用于"过滤一段文本流",ripgrep 用于"在代码目录里搜东西"**。两者并不互相替代,而是各自统治了不同的场景。

### **一个练手建议,让它真正变成你的工具**

光读不练,grep 永远只是"那个 Linux 命令"。给你一个 30 秒就能开始的练习:打开终端,执行下面这条命令,体会它的味道——

```bash
history | grep -i git | tail -20
```

这条命令的意思是:**列出你的所有历史命令,过滤出含 git 的,再取最后 20 条**。三个工具(`history`、`grep`、`tail`)用两个管道串起来,完成一个具体的小任务——这就是 Unix 命令行的精髓,也是 grep 在其中扮演的角色:**一个永远在线、随叫随到的文本过滤器**。

把这个心智模型装进脑子,grep 对你来说就不再是一个"挑出匹配行的命令",而是**操作命令行时的一种基础语法**了。
