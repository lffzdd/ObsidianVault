# 一、历史:三条支流,你只需要认第三条

知识图谱这个词底下,其实混了三拨来源不同的人。搞清楚这个,你就不会再被教材带进沟里。

**支流 A:符号逻辑派(1970s–2000s)** 语义网络 → 框架 → 描述逻辑 → OWL → Semantic Web。追求的是**严谨**:机器能做可靠的逻辑推理。代价是又重又难落地。Tim Berners-Lee 2001 年喊出"语义网",想让全网数据都变成机器可推理的 RDF——**这个宏大计划基本失败了**,没人愿意手工标注本体。

它今天活在哪:生物医学(SNOMED、Gene Ontology)、金融合规、工业知识库。这些地方**必须**严谨,所以值得这个成本。

**支流 B:工业实用派(2012–)** 2012 年 Google 提出 "Knowledge Graph" 这个词(就是你搜"姚明"右边出来的那个信息卡)。Google 明确说:**我们不搞 OWL 那套推理,我们就是要大规模、脏一点没关系、能用就行。**

这一派的做法:从网页/数据库里抽三元组,堆成巨大的图,不写本体,不跑推理机。代表产物:Freebase、Wikidata、DBpedia,以及每个大厂自己的业务图谱。

**"知识图谱"这个词的现代含义,是 B 定义的,不是 A。** 这是最关键的一点。

**支流 C:图数据库 & 图算法(2007–)** Neo4j 2007 年出现,带来"属性图"模型。图算法(PageRank、社区检测、最短路)从社交网络分析领域被搬进来。

**GraphRAG(2024)= B 的数据模型 + C 的算法 + LLM。跟 A 完全没关系。**

所以后面我讲的全是 B 和 C。A 那条线,你已经知道它存在、知道它为什么重、知道你为什么用不上——**这就够了,到此为止。**

# 二、数据模型:两种图,你都得认识

## 1. RDF 三元组(来自支流 A/B)

一切知识都拆成 `(主语, 谓语, 宾语)`:

```
(马斯克, 创办, 特斯拉)
(特斯拉, 总部位于, 奥斯汀)
(马斯克, 出生于, 南非)
```

一条三元组 = 图上的一条边。整个知识库 = 一大堆三元组。

**它的麻烦:边本身不能带属性。** 你想说"马斯克 2004 年加入特斯拉、职位是 CEO",怎么办?RDF 得搞一个"具体化"(reification)的丑陋技巧——凭空造一个中间节点:

```
(事件001, 类型, 任职)
(事件001, 人物, 马斯克)
(事件001, 公司, 特斯拉)
(事件001, 年份, 2004)
```

难看,而且查询变复杂。这是 RDF 的原罪。

## 2. 属性图(来自 Neo4j)

节点和边**都能带属性字典**:

```
节点: (马斯克 :Person {name:"Musk", born:1971})
节点: (特斯拉 :Company {name:"Tesla", hq:"Austin"})
边:   (马斯克)-[:任职 {since:2004, role:"CEO"}]->(特斯拉)
```

一条边就装下了全部信息。**GraphRAG 用的是这个模型**(虽然它内部常存成 parquet 表而不是真图数据库)。

**你的取舍:属性图是默认选择。** RDF 只在你要对接公开知识库(Wikidata、DBpedia)或做严格本体时才需要。**先学属性图。**

# 三、查询语言:Cypher(半天就够)

Cypher 的设计思想极其简单——**用 ASCII 画图**:

```cypher
// 找马斯克创办的所有公司
MATCH (p:Person {name:"Musk"})-[:创办]->(c:Company)
RETURN c.name

// 两跳:马斯克创办的公司,总部在哪个城市
MATCH (p:Person {name:"Musk"})-[:创办]->(c:Company)-[:总部位于]->(city)
RETURN c.name, city.name

// 可变长路径:马斯克 1~3 跳能到的所有东西
MATCH (p:Person {name:"Musk"})-[*1..3]->(x)
RETURN DISTINCT x
```

`()` 是节点,`-[]->` 是边,`:Label` 是类型,`{}` 是属性。**就这些。** 你看懂上面三条,Cypher 就入门了。

SPARQL 是 RDF 那边的对应物,长得像 SQL,**先跳过**,需要时再学。

# 四、图是怎么建起来的:抽取 Pipeline

这是**工程上最花时间、最容易翻车**的一步。传统做法(2015–2022):

1. **命名实体识别(NER)** — 从文本里找出"马斯克""特斯拉"这些实体
2. **关系抽取(RE)** — 判断它们之间是什么关系
3. **实体链接/消歧(EL)** — "苹果"是水果还是公司?"Musk"和"埃隆·马斯克"是同一个人吗?
4. **共指消解** — "他创办了..."里的"他"指谁?

以前这四步每步都要单独训模型,是整个 NLP 半壁江山。**2023 年之后,LLM 把这四步一锅端了。**

GraphRAG 的抽取本质上就是一个 prompt:

```
给你一段文本。请抽取:
- 所有实体:名称、类型、一句话描述
- 所有关系:源实体、目标实体、关系描述、强度(1-10)
输出 JSON。

文本:{chunk}
```

**这就是为什么 GraphRAG 在 2024 年才可能出现**——不是图技术变了,是抽取这一步终于便宜到能大规模用了。

抽完之后还有一步很关键:**实体消解(entity resolution)**。不同 chunk 抽出来的"Musk""Elon Musk""马斯克"要合并成一个节点,他们的描述要用 LLM 再总结成一段。这一步做不好,图就是碎的。

# 五、为什么需要 GraphRAG:普通 RAG 的死穴

普通 RAG 的逻辑:把问题变成向量 → 找最相似的 k 个文本块 → 塞给 LLM。

**它擅长**:"公司的报销上限是多少?" —— 答案就躺在某一个 chunk 里,捞出来就行。

**它彻底失败的两类问题:**

**(1) 需要多跳串联的问题**

> "马斯克创办的公司里,哪些的 CTO 是斯坦福毕业的?"

答案不在任何单个 chunk 里。它散落在几十个 chunk 里,需要**串**起来。向量检索捞不到,因为没有哪个 chunk 和这个问题"相似"。

**(2) 需要全局归纳的问题(GraphRAG 论文管这叫 query-focused summarization)**

> "这批 5000 份客服工单里,反映出的主要问题类型有哪些?"

这问题的答案**需要读完全部 5000 份**才能得出。向量检索只能给你 top-10,你永远拿不到全局视图。

**GraphRAG 就是为这两类问题设计的。**

## 索引期的关键:社区检测 + 分层摘要

这是 GraphRAG 最核心、也最聪明的一招,值得单独说。

**社区检测(Leiden 算法)** 干的事:在图上找出"内部连接紧密、彼此之间连接稀疏"的节点团。比如一个新闻语料的图里,可能自动聚出"美国大选相关""半导体产业相关""俄乌战争相关"几个团。

关键是 **Leiden 是分层的**:

- 第 0 层:几百个小社区(细粒度,比如"某个具体丑闻")
- 第 1 层:几十个中社区
- 第 2 层:几个大社区(比如"国内政治")

**然后对每一层的每一个社区,让 LLM 写一段摘要。** 底层社区的摘要基于原始实体和边;上层社区的摘要基于**下层社区的摘要**——递归地往上总结。

这就等于把整个语料**压缩成了一棵摘要树**。回答"主要问题类型有哪些"时,不需要读原文,读几十段社区摘要就够了。**这就是普通 RAG 做不到的全局视野。**

## 查询期的两种模式

**Local search(局部搜索)** —— 回答具体问题

1. 从问题里找出提到的实体("马斯克")
2. 在图上定位这个节点
3. 沿边扩散,把邻居节点、相关边、这些实体所属社区的摘要、以及原始文本片段一起捞出来
4. 全塞给 LLM 生成答案

**它解决的是多跳问题**:你问"马斯克的公司的 CTO",向量检索捞不到,但图上走两跳就到了。

**Global search(全局搜索)** —— 回答归纳问题

1. 取某一层的**所有**社区摘要
2. **Map**:对每段摘要单独问一次 LLM"这段里有哪些和问题相关的点?打分"
3. **Reduce**:把所有得分高的点汇总,让 LLM 生成最终答案

这就是个 **MapReduce**。所以全局搜索**很贵**——一次提问可能调几十上百次 LLM。这是 GraphRAG 最大的实用障碍。

# 七、代价与变体(这段能帮你避坑)

**GraphRAG 的成本高得离谱。** 索引一个中等语料可能烧掉几十上百美元,因为每个 chunk 都要 LLM 抽取,每个社区都要 LLM 摘要。全局搜索的每次提问也贵。

所以 2024–2025 出了一堆变体,你至少要知道名字:

- **LazyGraphRAG** — 微软自己出的省钱版:索引期**不调 LLM**,只用便宜的 NLP 抽名词短语建图;把 LLM 的开销**推迟到查询时**才花。成本降到原版的 0.1%,效果接近。
- **LightRAG** — 双层检索(低层查具体实体,高层查主题),比原版轻,支持增量更新。
- **HippoRAG** — 用 PageRank 在图上做检索,灵感来自海马体的记忆机制。
- **纯 Neo4j + Cypher 的方案** — 不做社区检测,就是抽三元组进图库,查询时让 LLM 生成 Cypher(Text2Cypher)。工程上最轻,很多公司实际在用这个。

**一个诚实的判断:GraphRAG 不是万能药。** 有不少评测显示,在纯事实问答上,它并不比调优好的向量 RAG 强,还贵得多。**它的价值集中在"全局归纳"和"多跳推理"这两类问题上。** 如果你的场景不需要这两类,别上 GraphRAG。

**第 1–2 天** — 属性图 + Cypher。装个 Neo4j Desktop,跑官方的电影数据集,把上面那几个 Cypher 查询敲一遍。不用看书,官方 sandbox 够了。

**第 5–7 天** — 读微软 GraphRAG 论文(arXiv 2404.16130),然后跑官方仓库的 quickstart。重点看它 `settings.yaml` 里的 prompt,和 output 目录里生成的那些 parquet 表——**打开看一眼实体表、关系表、社区表长什么样,整套东西立刻具象化。**

**第 11–14 天** — 读 LazyGraphRAG 和 LightRAG,理解它们在省什么钱。到这一步你已经能判断"我的场景该用哪个"了。

**全程不需要碰的:** OWL、SPARQL、RDF、描述逻辑、推理机、本体工程。
