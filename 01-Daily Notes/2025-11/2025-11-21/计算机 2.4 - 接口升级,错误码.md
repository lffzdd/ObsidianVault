# ① **错误信息没有“统一结构”**

现在你的结果大概像这样：

```json
{
  "ok": false,
  "stage": "SEND",
  "error": "失败"
}
```

虽然能用，但对于长期维护、前端展示、日志分析来说还不够强。

我们接下来要把错误结构升级成一个**标准错误对象**：

```json
{
  "ok": false,
  "error": {
    "code": "SEND_FAILED",
    "message": "发券接口返回失败：xxx",
    "detail": { ... }   // 可选
  },
  "stage": "SEND"
}
```

这样前端能一眼看：

- 这是发券失败
- 失败原因是什么
- 是 SEND 阶段还是 PUSH 阶段
- detail 是否需要开发进一步分析

这是工程化最重要的一步。

---

# ② **错误不应该只通过“字符串”向前端传递**

你未来的前端如果要做国际化 / 文案优化 / 不同语言提示 / 错误码分类
就会希望看到 **error code**，而不是一大段文字。

比如：

```json
{
  "error": {
    "code": "COUPON_RULE_MISS",
    "message": "无法根据金额匹配到券规则"
  }
}
```

或者：

```json
{
  "error": {
    "code": "DB_UPDATE_FAILED",
    "message": "数据库更新状态失败"
  }
}
```

这是一个你已经快要触及到的“成熟系统特征”。
