### 第一部分：历史脉络与底层逻辑 —— 为什么要“拉群开会”？

在 2023 年中旬，随着单一 Agent（如早期的 AutoGPT）被投入到复杂的长线任务中，顶级英文学术界和开源社区发现了单体架构的几个致命物理瓶颈：

1. **注意力崩溃 (Attention Collapse) 与提示词膨胀**：
    
    如果你想让一个单体 Agent 写代码、写测试用例、还要负责代码审查。你的 System Prompt 可能会长达几千字。研究表明，大模型在处理过长的、包含相互冲突角色（既要创新又要挑刺）的 Prompt 时，会出现“精神分裂”或“中间文段遗忘（Lost in the middle）”。
    
2. **“斯坦福小镇”的启示 (April 2023)**：
    
    斯坦福大学发表了现象级的论文 _Generative Agents: Interactive Simulacra of Human Behavior_。研究人员没有训练一个超级 AI 来控制 25 个 NPC，而是给了 25 个 NPC 各自极简的人设（Prompt），让他们在沙盒里自由交谈。结果涌现出了极其逼真的社会行为（比如自发组织情人节派对）。这向业界证明了：**多个简单 Prompt 的 Agent 互动，远胜于一个极其复杂的单体 Agent。**
    
3. **微软 AutoGen 的诞生 (August 2023)**：
    
    微软研究院发表了 _AutoGen_ 框架，正式将多智能体协同确立为工程范式。核心思想是：**“分而治之”**。让“程序员 Agent”只看代码文档，让“测试员 Agent”只负责报错，它们之间通过文本消息互相“辩论（Debate）”，直到得出完美结果。
    

### 第二部分：底层通信机制 (Topologies of Multi-Agent)

剥开所有框架的外衣，多个 Agent 协同的本质，就是**如何把大模型 A 的输出（Reply），作为大模型 B 的输入（User Message）**。

目前业界主要有三种底层的“沟通拓扑结构”：

- **线性接力 (Sequential / Chain)**：A 做完扔给 B，B 做完扔给 C。比如：`需求分析师 -> 程序员 -> QA测试`。
    
- **星型路由 (Hierarchical / Router)**：存在一个“经理 Agent（Manager）”，它不干活，只负责看用户的需求，然后决定把任务分发给底下的“专家 A”还是“专家 B”。
    
- **双边辩论 (Joint Debate / Cyclic)**：A 和 B 互相挑刺。比如：A 写了一段代码，B 负责挑错并打回，A 修改后再给 B，直到 B 输出 `APPROVED` 为止。这是提升代码质量最有效的手段。
    

### 第三部分：自底向上 —— 纯 Python 手写“双边辩论”多智能体

为了让你看透本质，我们不使用 AutoGen 或 CrewAI，直接用基础的 OpenAI API 手搓一个**“程序员与代码审查员的辩论循环”**。

你可以直接运行这段代码，观察两个大模型是如何在本地相互对话、修改代码的：

```Python
from openai import OpenAI

client = OpenAI(api_key="sk-你的真实API_KEY")

# ==========================================
# 1. 定义两个截然不同的 Agent 人设 (System Prompts)
# ==========================================
CODER_PROMPT = """
你是一个顶级的 Python 程序员。
你的任务是根据用户的需求或者 Reviewer 的反馈，编写或修改代码。
请只输出代码，不要多余的废话。
"""

REVIEWER_PROMPT = """
你是一个严苛的代码审查员 (Code Reviewer)。
你的任务是检查 Coder 提交的 Python 代码。
寻找潜在的 Bug、性能问题或不优雅的写法。
如果你发现了问题，请指出并要求修改；
如果代码完美无缺，请直接回复大写的 "APPROVED"。
"""

# ==========================================
# 2. 基础 LLM 调用函数
# ==========================================
def ask_agent(role_prompt: str, chat_history: list) -> str:
    messages = [{"role": "system", "content": role_prompt}] + chat_history
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        temperature=0.2 # 编程任务保持低随机性
    )
    return response.choices[0].message.content

# ==========================================
# 3. 核心引擎：多智能体辩论循环 (The Debate Loop)
# ==========================================
def run_multi_agent_debate(task: str, max_turns: int = 3):
    print(f"🎯 初始任务: {task}\n" + "="*50)
    
    # 初始化两套独立的记忆（上下文）
    coder_history = [{"role": "user", "content": task}]
    
    for turn in range(max_turns):
        print(f"\n🔄 [第 {turn + 1} 轮辩论开始]")
        
        # 1. Coder 行动
        print("🧑‍💻 程序员 Agent 正在编写代码...")
        draft_code = ask_agent(CODER_PROMPT, coder_history)
        print(f"--- 程序员提交的代码 ---\n{draft_code}\n------------------------")
        
        # 将自己写的代码记入 Coder 的记忆
        coder_history.append({"role": "assistant", "content": draft_code})
        
        # 2. Reviewer 审查 (把 Coder 的输出作为 Reviewer 的输入)
        print("🕵️‍♂️ 审查员 Agent 正在 Review...")
        reviewer_history = [{"role": "user", "content": f"请审查以下代码：\n{draft_code}"}]
        review_feedback = ask_agent(REVIEWER_PROMPT, reviewer_history)
        print(f"--- 审查员反馈 ---\n{review_feedback}\n------------------")
        
        # 3. 仲裁：是否通过？
        if "APPROVED" in review_feedback:
            print("\n✅ 审查通过！多智能体协作完成。")
            break
            
        # 4. 如果没通过，把 Reviewer 的反馈塞给 Coder，进入下一轮
        print("\n❌ 审查未通过，打回给程序员修改...")
        coder_history.append({"role": "user", "content": f"Reviewer的反馈：{review_feedback}。请据此修改代码。"})
        
    else:
        print("\n⚠️ 达到最大辩论轮数，强制终止。")

# 运行测试：故意给一个容易写错或写得不够优雅的数学任务
run_multi_agent_debate("写一个 Python 函数，计算斐波那契数列的第 N 项。")
```

**这段代码揭示的底层真相：**

多智能体协同，在代码层面上，**其实就是你在同时维护多个不同的 `messages` 数组（对话历史）**。你把 A 数组最后生成的文本，`append` 到了 B 数组的末尾，然后请求 B。这就是所谓“协同”的全部秘密。

# Grok

**Multi-Agent（多代理系统）** 是指由**多个 AI Agent** 协作完成复杂任务的系统，而不是只依赖单个 Agent。

它把一个大任务拆分成多个专门角色，让不同的 Agent 各司其职、相互沟通、协同完成，就像一个“AI 团队”在工作。

### 1. Single Agent vs Multi-Agent 对比

| 维度               | Single Agent（单代理）                          | Multi-Agent（多代理）                              |
|--------------------|------------------------------------------------|--------------------------------------------------|
| **结构**           | 一个 Agent + 多个工具                          | 多个专门化 Agent + 协调机制                      |
| **适用场景**       | 简单或中等复杂度任务（如查天气、写报告）       | 复杂、多步骤、需要多领域知识的任务               |
| **优点**           | 实现简单、速度快、成本低、易调试               | 专业化强、可并行处理、容错更好、可扩展性强       |
| **缺点**           | 容易上下文过长、难以处理极复杂任务             | 协调复杂、调试困难、成本更高、可能出现“混乱”行为 |
| **控制方式**       | 一个循环（ReAct / Tool Calling）               | Supervisor / Graph / Handoff 等协调机制          |
| **典型例子**       | 一个客服 Agent 处理所有查询                    | 研究团队：Planner + Researcher + Writer + Critic |

**什么时候用 Multi-Agent？**
- 任务需要多种不同专长（研究 + 写作 + 验证 + 总结）
- 需要并行处理（同时搜索多个来源）
- 希望有审查/纠错机制（一个 Agent 输出后，另一个 Agent 审查）
- 任务很长、容易出错，需要分工明确

**什么时候不需要？**
大多数简单任务用一个功能强大的 Single Agent + 好工具就够了。不要为了 Multi-Agent 而用 Multi-Agent（会增加不必要的复杂性）。

### 2. Multi-Agent 的常见架构模式（2026 年主流）

1. **Supervisor（监督者模式）**  
   一个 Supervisor Agent 负责整体协调，根据任务把子任务分发给不同的 Specialist Agents，最后汇总结果。  
   最常用、最易控制。

2. **Hierarchical（层级模式）**  
   有 Boss Agent → Manager Agents → Worker Agents 的层级结构，类似公司组织架构。

3. **Swarm / Collaborative（群体/协作模式）**  
   多个 Agent 共享上下文，自由讨论、协作完成任务（类似头脑风暴）。

4. **Router + Sub-agents**  
   主 Agent 把不同意图路由给对应的子 Agent。

5. **Custom Workflow（用 Graph 构建）**  
   用 **LangGraph** 显式定义 Nodes（每个 Agent 是一个 Node）和 Edges（转移规则），这是目前生产环境中最推荐的方式。

### 3. 在 LangGraph 中实现 Multi-Agent

LangGraph 是目前构建 Multi-Agent 系统的主流框架（远超经典 LangChain 的 AgentExecutor）。

- 每个 Agent 可以是一个 **Node**（节点）
- Agent 之间的交接/协作通过 **Edges**（边，包括条件边）定义
- 所有 Agent 共享一个 **State**（状态），支持持久化（checkpoint）
- 支持循环、重试、human-in-the-loop、并行执行等

**典型 Multi-Agent 示例**（研究工作流）：
- **Planner Agent**：把用户问题拆分成多个子任务
- **Researcher Agent**：使用搜索工具收集信息
- **Writer Agent**：根据收集的信息撰写报告
- **Critic Agent**：审查报告质量，提出修改意见
- **Supervisor**：决定流程走向，最终输出

整个流程用 LangGraph 的 Graph 串起来，状态在各个 Agent 之间流动，非常清晰且可观测。

### 4. 其他流行 Multi-Agent 框架（2026 年）

- **LangGraph**：最强控制力、生产级首选（显式 Graph + State）
- **CrewAI**：更简单、像定义“角色和任务”一样写 Multi-Agent，适合快速上手
- **AutoGen / AG2**：强调 Agent 之间的自然对话式协作
- **OpenAI Agents SDK**、**Google ADK**、**Anthropic Agent SDK** 等官方 SDK 也在快速成熟

### 总结建议

- **入门**：先把 Single Agent（带 Tool Calling + 你的手写状态机思路）做扎实。
- **进阶**：当 Single Agent 明显力不从心时，再引入 Multi-Agent，用 **LangGraph** 构建（因为它和我们之前讨论的状态机 + Node + Edge 思路高度一致）。
- **核心原则**：**能用 Single Agent 解决的，就不要用 Multi-Agent**。Multi-Agent 的强大伴随着更高的复杂度和调试成本。
