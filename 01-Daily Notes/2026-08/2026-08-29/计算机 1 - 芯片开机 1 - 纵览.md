# 一

你的感觉完全没有错！很多人刚接触树莓派、香橙派（Orange Pi）这类 ARM 开发板时，都会以为“刷机就是拿工具把一个 `.img` 文件写进 SD 卡，就像给电脑装 Ghost 系统一样简单”。

但当你真正去编译系统、排查启动故障，或者自己移植系统时，就会发现**ARM 板子的启动其实是一场严密的“硬件接力赛”**。

我们按照你的要求，**自底向上、一步步来**。今天这一节，我们先搞清楚两个最核心的问题：
1. **为什么平时看到的是“一个镜像”，实际上却是“多段代码”？**
2. **第一阶段：从芯片通电到内存可用（BootROM 与 SPL）**

---

### 一、 为什么以前你以为“只有一个镜像”？

你在官网上下载的 `Orangepi.img`，在操作系统层面上被称为 **全盘原始镜像（Raw Disk Image）**。

它本质上是一个**按物理扇区精确排列好的“压缩包”**。烧录工具（如 BalenaEtcher 或 `dd` 命令）做的事情非常简单：**无脑把这个镜像从 SD 卡的第 0 个字节开始，一字不差地逐字节写入卡里**。

但如果把这张烧录好的 SD 卡内部解剖开看，它并不是一个单一文件，而是被精密切割成几部分：
```text
SD卡 / eMMC 物理扇区分布示意：
+-------------------------+----------------------+--------------------+--------------------+
| 芯片保留区 / MBR 分区表   | 引导阶段各二进制组件   | Boot 分区 (FAT32)   | Rootfs 分区 (ext4)  |
| (Sector 0 ...)          | (SPL, ATF, U-Boot...) | (内核 Kernel, DTB) | (Ubuntu/Debian系统) |
+-------------------------+----------------------+--------------------+--------------------+
```
因为官方镜像已经帮你把这几轮要跑的代码**打包缝合在了一起**，所以你平时察觉不到它们是独立分开的。

---

### 二、 为什么不能直接通电就启动 Linux？

在 PC（X86 电脑）上，主板上有独立的 BIOS/UEFI 芯片，硬件标准化程度极高。
但在香橙派这种 ARM 嵌入式设备上，面临一个根本性的致命矛盾：

1. **刚通电的一瞬间，板子上的外接内存（如 4GB/8GB 的 LPDDR4/DDR5）是处于“瘫痪不可用”状态的！**
2. 任何外接内存，都必须先由一段特定的程序去配置时序、电压、频率，才能正常读写数据。
3. 一个完整的 Linux 内核动辄几十兆（MB），根文件系统几百兆到几个吉（GB）。**既然内存还没法用，这么庞大的系统要加载到哪里去？**

因此，CPU 只能通过**“滚雪球 / 接力赛”**的方式，从小代码拉起稍大的代码，一步步把硬件点亮。

---

### 三、 接力赛第 0 棒：芯片固化代码（BootROM / BROM）

* **位置**：直接刻死在 SoC（如全志 H616、瑞芯微 RK3588）芯片内部硅片上的只读存储区，出厂后任何人无法修改。
* **可用资源**：此时外接大内存不可用，CPU 只能使用芯片内部极小的一块临时高速缓存（片上 SRAM，通常只有几十 KB 到几百 KB）。

#### 它做什么？
当你插上电源按下开关，CPU 硬件逻辑自动执行的第一行代码就是 **BootROM**：
1. **检查启动介质**：根据板子上的引脚电平配置，依次去检查：SPI Flash、SD 卡、eMMC、USB 还是网络。
2. **搬运下一棒**：比如检测到 SD 卡，它会去读取 SD 卡上**固定物理偏移位置**（例如从第 8KB 或第 64 个扇区开始）的一小段代码，把它搬运到芯片内部的 SRAM 里。
3. **交出控制权**：跳转执行这一小段代码。

---

### 四、 接力赛第 1 棒：次级引导程序（SPL）与 安全固件（ATF）

因为片上 SRAM 空间非常小，BootROM 搬运上来的代码体积不能超过几十 KB。这段小代码通常被称为 **SPL**（*Secondary Program Loader*，即 U-Boot 的第一阶段极简版）。

#### SPL 的最核心使命：
* **初始化 DDR 内存控制器！**
* 针对当前板子焊接的内存芯片（不同批次可能是三星、海力士或长鑫），配置正确的参数，把内存点亮。

#### 协同选手：ATF（ARM Trusted Firmware / BL31）
在 64 位 ARM 架构中，SPL 通常还会顺带加载 ATF：
* 它是运行在 ARM 最高安全权限级别（EL3）下的底层安全固件。
* 负责处理电源管理（如 CPU 变频、待机休眠）、安全监控等最底层的硬件特权操作。

#### 第 1 棒结束时的状态：
此时，板子上那块 **几 GB 的大内存终于被唤醒激活了！**
接下来，SPL 终于有能力去存储介质里读取一个**体量更大（数兆字节）、功能更完整**的程序——也就是大名鼎鼎的 **U-Boot（第二阶段）**，并把 U-Boot 扔进刚刚初始化好的大内存中运行。

---

### 小结与思考

我们现在走到了这一步：
```text
[通电开机] 
   ⬇
【第 0 棒: BootROM】(芯片出厂刻死，从 SD卡搬运几十KB代码到片上SRAM)
   ⬇
【第 1 棒: SPL + ATF】(在SRAM中运行，成功点亮 4GB/8GB DDR内存)
   ⬇
【准备进入第 2 棒: 完整的 U-Boot...】
```

你可以先消化一下这段内容。如果对 **BootROM**、**SRAM 限制**、**为什么必须先由 SPL 初始化 DDR** 有任何疑问，我们可以随时讨论；如果感觉完全跟得上，告诉我一声，我们继续聊下一棒：**U-Boot 到底是干什么的？它又是怎么把 Linux 内核和设备树拉起来的？**

# 二

好，我们紧接着上一节，继续自底向上往上走！

上一节我们讲到：**SPL 已经成功把板子上的几 GB DDR 内存点亮了**。
此时，CPU 终于有了充裕的内存空间，接力棒交到了第二棒手里——**完整的 U-Boot**。

---

### 五、 接力赛第 2 棒：完整的 U-Boot（Bootloader 的核心大管家）

* **位置**：由 SPL 从 SD 卡/eMMC 中读出，加载并运行在**真正的 DDR 内存**中。
* **它的本质**：你可以把它理解为一个**没有图形界面的“微型操作系统”**。

#### 1. U-Boot 拥有什么能力？
在加载真正的 Linux 操作系统之前，U-Boot 会初始化更多日常外设：
* **文件系统驱动**：它能读懂 SD 卡上的 `FAT32` 和 `ext4` 分区（所以内核不再需要按固定扇区摆放，而是可以像普通文件一样存放在 `/boot` 目录下）。
* **串口与交互终端**：如果你接了 USB 转串口线（TTL），在开机倒计时按下回车，就能进入 U-Boot 命令行，进行网络刷机、改配置、测硬件等操作。
* **网络与 USB 驱动**：它甚至可以通过插网线（TFTP/NFS）或者插 U 盘来下载内核。

#### 2. U-Boot 的核心任务：
U-Boot 的最终目标非常专一：
1. 从存储卡（比如 `/boot` 分区）中找到两个关键文件：
   * **Linux 内核镜像**（通常叫 `Image` 或 `zImage`）
   * **设备树二进制文件**（通常叫 `xxx.dtb`）
2. 把这两个文件**搬运到内存（RAM）中的指定地址**。
3. 把启动参数（`bootargs`，比如串口波特率、根目录在哪个分区）传递给内核。
4. **一脚油门跳转到内核入口**，U-Boot 自己彻底退出历史舞台，由内核接管整个硬件。

---

### 六、 插播一个关键概念：什么是“设备树”（Device Tree / DTB）？

很多人在 ARM 板子上最搞不懂的就是：**“为什么总有个叫 `.dtb` 的文件？它跟内核是什么关系？”**

#### 为什么 PC 电脑不需要设备树，而香橙派必须需要？
* **PC 电脑（X86）**：主板上有标准的 PCI/PCIe、ACPI 总线标准，电脑开机时，操作系统只要往总线上“广播”喊一声：“谁插在上面？”，显卡、网卡、声卡就会自动报出自己的型号和资源配置（即**硬件自发现**）。
* **ARM 开发板**：为了节省芯片成本和功耗，SoC 内部的大量外设（I2C 控制器、SPI、PWM、网卡物理层、GPIO 引脚）都是直接连在芯片内部总线上的，**根本无法自动探测**。

#### 设备树就是给 Linux 内核的“硬件接线图与说明书”：
Linux 内核本身是通用的，但它不知道这块具体的香橙派板子上：
* 状态指示灯接在哪个 GPIO 引脚上？
* 哪一路 I2C 挂载了实时时钟（RTC）芯片？
* 内存芯片的基地址是从哪里开始的？

工程师会先写一份文本说明书（**`.dts`，Device Tree Source**），然后编译成二进制的 **`.dtb`（Device Tree Blob）**。
**Linux 内核开机时读取这份说明书，才知道如何去配置板子上的每个硬件模块。**

---

### 七、 接力赛第 3 棒：Linux 内核（Kernel）

当 U-Boot 执行最后一跳后，CPU 开始运行 **Linux Kernel**：

1. **解压与初始化**：建立虚拟内存管理机制（MMU）、初始化中断控制器、调度器。
2. **查阅设备树**：解析 U-Boot 传给它的 `.dtb` 文件，按照上面的说明，逐个加载并初始化硬件驱动（显卡、网卡、USB、音频、WiFi）。
3. **寻找并挂载“根文件系统”（RootFS）**：
   * 内核会根据 U-Boot 传递的参数（例如 `root=/dev/mmcblk0p2`），找到 SD 卡的第 2 个分区。
   * 把这个分区挂载为系统的根目录 `/`。

---

### 八、 接力赛第 4 棒：用户空间与系统初始化（RootFS & systemd）

一旦内核挂载好根分区，内核的底层引导工作就全部完成了。

1. **诞生 1 号进程**：内核会在根文件系统里找到并执行第一个用户态程序（通常是 `/lib/systemd/systemd` 或传统的 `/sbin/init`），这是整个 Linux 系统的 **PID 1** 进程。
2. **拉起整个操作系统世界**：
   * 启动 `sshd`（让你能通过 SSH 连进去）；
   * 启动网络管理服务（自动连 WiFi 或分配 IP）；
   * 启动桌面管理器（如果你刷的是桌面版系统，此时 HDMI 屏幕亮起显示桌面）；
   * 打印最后的 `login:` 提示符。

---

### 全流程全景总结（从通电到看见系统）

我们用一张完整的全景图把整场接力赛串起来：

```text
【硬件上电】
    │
    ▼
[0. SoC BootROM]     (固化在芯片内部，从 SD卡搬运几十KB的 SPL 到片上 SRAM)
    │
    ▼
[1. SPL + ATF]       (在 SRAM 运行，初始化 DDR 内存，加载大体积的 U-Boot 到内存)
    │
    ▼
[2. U-Boot]          (在 DDR 内存运行，读取 /boot 分区，把 内核 与 设备树 搬进内存)
    │
    ▼
[3. Linux 内核]      (解析设备树驱动硬件，挂载 SD卡上的 rootfs 根分区)
    │
    ▼
[4. 用户空间 systemd] (拉起所有后台服务，打印登录界面，系统完全启动！)
```
