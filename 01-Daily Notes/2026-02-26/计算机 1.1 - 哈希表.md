这个问题问得非常好，你已经在从“使用层”走向“内存模型层”了。

先给你一个明确结论：

> bucket 是 **一整块连续内存中的连续数组**  
> 不是“离散分布”  
> 真正离散的是 node

---

# 一、bucket 到底是什么？

在主流实现（libstdc++ / libc++）中，可以抽象成：

```cpp
node** buckets;
size_t bucket_count;
```

也就是：

```text
buckets -> 一块连续内存
```

假设 bucket_count = 8

内存长这样：

```
地址
0x1000  [node*]
0x1008  [node*]
0x1010  [node*]
0x1018  [node*]
0x1020  [node*]
0x1028  [node*]
0x1030  [node*]
0x1038  [node*]
```

它就是一个普通数组：

```cpp
node* buckets[8];
```

连续，非常连续。

---

# 二、为什么“根据 node 算 bucket 索引”？

其实并不是根据 node 算。

流程是：

```
hash(key)
→ index = hash % bucket_count
→ buckets[index]
```

不是：

```
node -> bucket
```

而是：

```
key -> hash -> bucket
```

node 只是：

```
挂在 bucket[index] 链表上
```

---

# 三、那为什么感觉像“离散分布”？

因为 node 是离散的。

真实结构是：

```
连续 bucket 数组
↓
每个 bucket 存一个 node* 头指针
↓
node 在堆上单独分配
↓
node->next 形成链表
```

图示：

```
buckets (连续)

[0] -> nodeA -> nodeB
[1] -> null
[2] -> nodeC
[3] -> nodeD -> nodeE
...
```

nodeA / nodeB / nodeC 在内存中完全可能是：

```
0x5000
0x9000
0x3000
```

彼此毫无连续性。

---

# 四、为什么 bucket 必须连续？

因为：

```
index = hash % bucket_count
```

这是 O(1) 访问：

```
buckets[index]
```

如果 bucket 不是连续数组，而是离散存储：

- 你无法通过 index 做 pointer arithmetic
- 就无法 O(1) 定位

连续数组的好处是：

```
地址 = base + index * sizeof(node*)
```

CPU 一步算出来。

---

# 五、rehash 时发生什么？

假设 bucket_count 从 8 扩成 16：

1. 分配新的连续 bucket 数组
2. 遍历所有 node
3. 重新算 hash % 16
4. 重新挂链

node 本身不动，只改 next 指针。

所以：

```
bucket 连续
node 离散
```

这个结构非常经典，叫：

> separate chaining hash table（链地址法）

---

# 六、对比开放寻址（比如 Python dict）

开放寻址是：

```
连续数组里直接存元素
```

而 C++ 是：

```
连续数组存指针
元素在外部
```

区别：

|结构|bucket|element|
|---|---|---|
|C++ unordered_map|连续|离散|
|Python dict|连续|连续|

---

# 七、你现在的理解可以升级为：

不是：

> bucket 在一小片连续空间中离散分布

而是：

> bucket 是连续数组  
> node 是离散分配  
> bucket 只是 node 链表的入口

---

# 八、真正影响性能的是什么？

由于 node 离散：

- cache 命中率低
- 指针跳转多
- TLB miss 多

这就是为什么：

```
absl::flat_hash_map
```

比

```
std::unordered_map
```

快很多。

因为它用的是开放寻址 + 连续存储。
