大致可以分成三层来看:**数据侧变复杂了、检索侧变成两阶段、而最大的变化是「检索从写死的一步,变成了模型自己调的工具」**。

## 1. 范式转变:from pipeline RAG to agentic retrieval

这是最本质的变化。原始 RAG 是硬编码的控制流:

```
query → embed → top_k → stuff into prompt → generate
```

问题是这个流程强制假设「每个问题都需要检索,且检索一次就够,且第一次的 query 就是最好的 query」。这三个假设经常都不成立。

现在主流做法是把检索暴露成 **tool**,由模型决定:要不要检、检几次、用什么关键词、检哪个库、结果不够好要不要换个说法再检一遍。形成 search → read → reason → search again 的循环。

一个很有说服力的例子是代码助手类产品:很多都没有向量库,直接给模型 grep / glob / read_file,让它像人一样翻代码。在结构化程度高、有天然导航结构的语料上,agentic search 往往打得过向量检索。

MCP 这类协议进一步把「数据源」标准化成可插拔的 tool server,检索逻辑从应用代码里搬出去了。

代价是延迟和 token 成本高很多,所以实践中常分级:简单 query 走一次性快路径,复杂的才进 agent loop。

## 2. 入库侧:从手动脚本到持续管道

- **增量同步**:CDC / webhook / 对象存储事件驱动,而不是跑一次脚本。文档更新要能反映到索引,还要能删。
- **解析**:PDF 解析这块进步很大,现在普遍用 layout-aware 或直接多模态模型读版面(Unstructured、LlamaParse、Docling、MinerU 这类),表格和图表单独抽出来处理。
- **切分**:从固定长度 → 按文档结构(标题层级)切;以及 contextual retrieval —— 用 LLM 给每个 chunk 生成一段「这段在讲什么、属于哪个文档的哪部分」的前缀,再一起 embed,能显著降低检索失败率。late chunking 也是同类思路。
- **一个 chunk 多种表征**:原文 + 摘要 + 生成的假设性问题,分别建索引。
- **权限**:ACL 跟着文档进索引,检索时按调用者身份过滤。企业场景这是硬需求,漏了就是事故。

## 3. 检索侧:召回 + 重排两阶段

现在近乎标配的组合:

1. **Hybrid**:dense 向量 + BM25/稀疏检索,用 RRF 融合。纯向量对专有名词、编号、罕见词很差,BM25 补这块。
2. **Metadata 前置过滤**:时间、租户、文档类型。
3. **Rerank**:第一阶段召回 100~200 条,用 cross-encoder 重排到 top 5~10。这一步性价比通常是整个链路里最高的。
4. **Query 改写**:多轮对话要把上下文压成独立 query;还有 multi-query、HyDE 之类。

## 4. 「上下文工程」取代了朴素的塞 prompt

长上下文 + prompt caching 便宜下来之后,决策变了:语料小的时候(几十万 token 以内),直接全塞进去配上缓存,比维护一套 RAG 系统更简单也更准。RAG 现在更多是「语料太大塞不下」时的压缩手段,而不是默认方案。

真正的工作变成了:什么该进窗口、什么顺序、怎么压缩历史、怎么避免 lost-in-the-middle。

## 5. 工程化:eval 和可观测性

这块是业余和生产的分水岭:

- **检索和生成分开评**。检索看 recall@k / nDCG,生成看 faithfulness / 引用准确率。端到端指标掉了,得知道是哪一环的锅。
- **golden set**:几百条人工标注的 query-答案对,每次改动跑一遍回归。
- **trace 每一次检索**(Langfuse / Phoenix / LangSmith 之类),线上出问题能还原当时召回了什么。
- **强制引用**:输出必须带可溯源的 span,既是产品需求也是降低幻觉的手段。

## 6. 选型现状

- 向量库:专用库(Qdrant / Milvus)热度其实在回落,很多团队直接用 pgvector 或 Elasticsearch/OpenSearch——理由是不想多运维一个系统,而且 ES 天然做 hybrid 方便。
- 框架:LangChain / LlamaIndex 适合快速验证,规模化之后不少团队会自己手写,因为抽象层在调优时反而碍事。

## 一个反直觉的观察

大部分收益来自三件基本功:**结构化的切分 + hybrid 检索 + rerank**。GraphRAG 之类在需要全局归纳(「这批文档整体的主题趋势是什么」)时确实有用,但构图成本高、更新麻烦,真正落地的比讨论的少得多。

如果你正在改造一个朴素 RAG,建议的顺序是:先建 eval set(不然改了不知道有没有变好)→ 加 rerank → 加 BM25 混检 → 改切分策略 → 最后才考虑 agentic 化。

RAG 这块迭代很快,上面是截至我知识范围内的情况,具体工具的版本和榜单最好再查一下最新的。

大方向对,但有两处我觉得会误导后面的判断,想拧一下。

**「上下文变长导致检索频率下降」——这个因果基本只在小语料成立。**

企业侧的语料是 TB 级的,再长的窗口也塞不下,长上下文对它没有任何影响。真正被长上下文吃掉的是那一档「几十上百个文档的问答」——这一档以前会被硬做成 RAG,现在直接全塞更省事更准。所以不是频率下降,是**下限被抬高了**:小语料不再需要 RAG,大语料照旧需要,而且需求还在涨。

另外全塞的成本也没有想象中低。prompt cache 只对稳定前缀有效,而且有 TTL,多租户、动态拼接的场景命中率很难看;首 token 延迟也随输入长度线性涨。所以「能塞得下」和「值得塞」是两件事。

**「硬编码是特定产品才用」——按部署量算,恐怕正好反过来。**

agentic retrieval 是能力上限高的那条路,但按线上跑的 QPS 算,一次性检索仍然是绝大多数。原因很实际:客服、文档问答、站内搜索这类场景,domain 窄、意图可枚举、要求 P99 在一两秒内、单次调用成本要压到几厘。让模型自己 loop 三五轮,延迟和成本都翻好几倍,换来的准确率提升在窄域上很可能是零——因为一次检索就够了。

比较准确的划分是按**任务开放度**而不是产品类型:意图可枚举 → 固定管道;需要多跳、需要边读边决定下一步查什么(深度research、代码库导航、跨系统排查)→ agentic。很多成熟系统是两条路都留,用一个轻量分类器路由。

**GraphRAG 那句我基本同意,但别一棍子打死。**

低 ROI 的是它最初那个形态:全语料抽实体、建社区、生成层级摘要。这套构建成本高、增量更新几乎等于重建,而收益集中在「全局归纳型」问题上,而这类问题在真实流量里占比很低。

但去掉「Graph」这个包装,里面有几个东西是活的:实体消歧和链接、把结构化库(用户表、工单表、组织架构)和非结构化文档 join 起来查、以及沿引用/依赖关系做多跳。合规审查、金融关联方识别、反欺诈、药物机理这些实体密度极高的领域,确实靠这个吃饭。只是它们通常不叫自己 GraphRAG,就是普通的知识库工程。

所以更准的说法可能是:**重型 GraphRAG 是个被过度营销的解法,但它试图解决的多跳问题是真的**,只是多数团队用更便宜的方式(query 分解 + 多轮检索)绕过去了。
