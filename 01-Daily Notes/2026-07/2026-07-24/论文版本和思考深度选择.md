| 论文环节 | 建议档位 |
|---|---|

两个实操提醒：

一是**别默认拉到最高**。OpenAI 自己的建议是从默认强度起步，任务确实需要更深的规划或分析时再往上调；官方人员也提到5.5 和 5.6 的推理档位并不是一一对应的，从 5.5 换过来的话，同样的任务先降一档试，效果不够再往上加。润色类任务开高档，输出反而容易变啰嗦、爱加你没要的东西。

目标检测这个场景很吃"长链路调试"，配置策略跟纯写代码不太一样。

**先确认基础设置**：Codex 的默认是 gpt-5.6-sol + medium reasoning，CLI 里用 `/model` 切换模型和推理强度，也可以启动时用 `--model` / `-m` 指定。<cite index="24-1">推理强度一共六档（none、low、medium、high、xhigh、max），另外还有 Ultra 模式，它会并行跑四个 agent。</cite>

按你的实际任务分：

| 任务 | 建议 |
|---|---|
| 环境配置、mmdet/detectron2 的 config 改写、COCO↔YOLO 格式转换 | Terra / Luna，low–medium |
| 写 dataloader、数据增强、评估脚本 | Terra medium |
| 改 backbone/neck/head、加新模块 | Sol medium–high |
| **loss 不收敛、mAP 异常、NaN 这类调试** | Sol high 或 xhigh，**别开 Ultra** |
| 批量跑消融实验脚本、大范围重构 | Ultra |
| 写论文 LaTeX、画图表 | Terra |

中间那条最重要。Max 是让一个模型在单个难题上花更长时间，Ultra 是多个子 agent 并行处理一个大问题的不同部分——调试 mAP 掉点这种事，所有线索（数据增强、anchor 匹配、NMS 阈值、类别 id）必须待在同一条推理链里才能串起来，拆给四个 agent 反而会各说各话。反过来，"把这五组消融配置各跑一遍并整理结果"天然可拆，Ultra 才划算。

**三个目标检测特有的坑，提前跟 agent 说清楚：**

1. **评估脚本本身可能是错的。** 目标检测最阴的失败是静默的——类别 id off-by-one、bbox 坐标格式（xyxy/xywh/归一化）搞混、增强后 bbox 没跟着变换。模型再强也不会主动怀疑你的 `eval.py`。让它先写一个可视化检查：把增强后的图和 bbox 一起画出来存盘，你肉眼过一遍再开始调。

2. **不要接受"我改了超参，性能提升了"这类结论。** 要求它每次给可复现的 diff、固定 seed、记录完整 config，否则消融表格写进论文会站不住。

3. **AGENTS.md 里如果写过"回答简洁点"，删掉。** GPT-5.6 的输出本来就比 5.5 短，旧的 concise 指令现在会让它省掉你需要的解释。

**两个运维细节**：Codex 客户端版本太旧就看不到新模型，需要 CLI 0.144.0 以上；另外 Codex 和 ChatGPT Work 共用同一个用量池，所以别在低价值任务上挂 xhigh 跑一下午，临近 deadline 调 bug 时额度不够很难受。

起手建议：Sol + medium 当默认，卡住了升到 high，还卡住再上 xhigh。绝大多数改模型的活儿到 high 就到顶了。

不过说句实在的：**对"想创新点"这件事，这两档的差别基本可以忽略。**

推理强度提高解决的是"想得够不够周全"，不是"想得够不够新"。你把 xhigh 开满，它只会把一个平庸的想法论证得更细致、代码写得更完整，不会因此跳出训练数据里那些已经被写烂的套路。目标检测这个领域尤其明显——你问它怎么改进模块，八成会给你：加个注意力（SE/CBAM/坐标注意力）、改一下 FPN 的融合方式、换个损失函数（focal→varifocal/EIoU）、上可变形卷积。这些组合在近几年的检测论文里出现过太多次，审稿人和答辩老师一眼就认得出来，而且很多在你自己的数据上根本不涨点。

**真正管用的顺序是反过来的：先做误差分析，再让它出主意。**

拿 baseline 在你的数据集上跑一遍，把失败案例分桶统计——小目标漏检占多少、密集遮挡占多少、长尾类别占多少、边界框回归不准占多少、域偏移占多少。这一步 Codex 能帮你写脚本和可视化，很快。

然后带着结论去问：与其问"目标检测有什么创新点"，不如问"我这个场景里 40% 的漏检来自面积小于 32×32 的目标，且集中在遮挡区域，针对这个具体现象有哪些技术路线，各自的代价是什么"。同样的模型、同样的档位，后一种问法出来的东西可用性完全不是一个量级。

另外两个用法比"让它想点子"性价比高得多：

- **让它当审稿人。** 把你的想法丢过去，要求"指出这个设计最可能被质疑的三点，以及审稿人会要求补什么实验"。模型批评能力比生成能力强，这是它的舒适区。
- **让它压缩实现周期。** 你想到五个方向，Codex 的价值在于让你两天内把五个都做成可跑的消融，而不是替你产生那五个方向。创新点最终要靠实验筛出来的。

最后提醒一句实际的：创新点得能在答辩时讲出动机。导师问"你为什么这么设计"，答"实验涨了 1.2 个点"是撑不住的，得说得出为什么这个结构对你观察到的那个失败模式有效。这个因果链只有你自己做过误差分析才建立得起来——这也是为什么我建议把顺序倒过来。

- **次选：主表用全量 RDD2022（跟文献可比），ChinaDrone 作为专门的子实验。** 这个还有个现实好处——CRDDC'2022 有公开的成绩可对标，最好的模型在六国全集上 F1 达到 76.9%，你有基线可比。而只做 ChinaDrone，文献里几乎找不到可比对象，审稿人会问你"跟谁比"。

最后一句实在话：如果你的模块在全量上涨、在 ChinaDrone 上不涨，**这个对比本身就是论文里很有价值的一段**，说明它学到的是通用特征而非无人机特性。别把它藏起来，写出来反而显得你做过分析。
