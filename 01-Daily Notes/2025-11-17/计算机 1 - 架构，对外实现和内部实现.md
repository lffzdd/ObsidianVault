> 将来需求变动时，你需要改几处代码、改几层。

## 1. 你现在的做法，其实是一个“合理的 V1”

你现在的发送逻辑是：

```python
send_coupon_for_order(trade_nos: List[str])
    -> 从数据库再查一次
    -> 用规则重新算券
    -> 调发券接口 + 推送接口
```

对应的是这种业务假设：

- 前端不能改券参数，只能决定“这几条发 / 不发”
- 券的规则完全由后端控制，发什么由后端说了算

在没有前端“改券值”需求的前提下，这个设计是很干净的：

- 入参简单（就一个 trade_no 列表）
- 所有逻辑都在后端可控
- 安全、口径统一

**所以现在不急着为了“可能有的需求”去复杂化设计，这叫避免过度设计。**

---

## 2. 将来需求变了，成本大不大，取决于一件事

不是取决于你现在参数是不是 trade_no，而是：

> **“发券这件事，只在一个地方实现，还是散落一堆地方？”**

如果你做到这点：

- 所有“发券 + 推送 + 更新状态”的流程
	- 只在 `services.py` 的一个函数里实现，比如 `send_coupon_for_order(...)`
	- `app.py` 只调用它，不直接操作 `db.py` / `api.py`
	- 其他地方也不直接发券（禁止在别的文件乱调 `ApiClient.send_coupon`）

那将来你要支持“前端可改券值”时，改动大概是这个级别的：

1. 改 `send_coupon_for_order` 的**函数签名**（比如从 `trade_nos` 改成 `requests`，或者多加一个参数）
2. 改它内部从“自己算券” → “部分采用前端传入值”
3. 改 `app.py` 对它的调用方式（比如从 `trade_nos` 改成传 JSON 结构）

**注意：db 层、api 层、coupon_rule 层都不用动**，因为它们的接口没有变。

这就叫“改一个用一个”，变化被你“关在 service 边界里”。

## 3. 怎么现在就降低未来改动成本？只要做两件小事

你现在可以先完全按“只要 trade_no 的 V1”实现，但在结构上轻轻留两个“缝”，将来会省很多事：

### 3.1 让“发送的核心逻辑”只在一个函数里

比如这样分：

```python
# 对外给 app.py 用的 V1：基于 trade_no 的接口
def send_coupons_by_trade_nos(trade_nos: List[str]) -> List[SendResult]:
    # 1. 查库 -> 得到 record 列表
    # 2. 把 record 转成 requests（内部结构随你定义）
    requests = build_requests_from_records(records, trade_nos)
    # 3. 调用“真正干活的核心函数”
    return _send_coupons(requests)


# 核心逻辑：真正干“发券 + 推送 + 更新状态”的函数
def _send_coupons(requests: List[SendRequest]) -> List[SendResult]:
    for req in requests:
        # 用 req 调 api.send_coupon / api.issue_coupon
        ...
```

将来如果前端可以直接传参数，你只需要：

```python
# 新的对外接口：前端直接传 requests
def send_coupons_from_frontend(requests: List[SendRequest]) -> List[SendResult]:
    return _send_coupons(requests)
```

核心 `_send_coupons` 一行没改，只是多了一个新的入口而已。
这就是“提前把变化收敛到一个点”的做法。

---

### 3.2 让“预览结构”和“发送结构”明确区分

现在你有一个预览用的结构：

```python
{
    "trade_no": ...,
    "old_code": ...,
    "vip_phone": ...,
    ...
    "coupon_value": ...,
    "beg_date": ...,
    "end_date": ...,
}
```

就先把这个当成 **Preview DTO**，给前端展示用；
将来如果你需要一个 **Send DTO**（允许修改后的值），你就新建一个结构，不要把两个用途混在一起。

这样未来就不会出现：

- 前端也拿这个结构展示
- 发券也用同一个结构
- 想加字段时一改全崩

而是：

- `preview_unissued_orders()` → 返回 Preview DTO 列表
- `send_coupons_xxx(...)` → 接收 Send DTO 列表（将来要改就改这块）

现在你可以先没有 Send DTO，等需求来了再加，但你脑子里已经意识到：**预览和发送的数据结构是两类东西**，这就足够避免很多坑了。

## 4. 回答你的原话：成本会大吗？

在你现在这种项目规模下（十来个文件、单一业务流程），**只要你做到：**

- 发券流程只在 `services.py` 一个地方实现
- app.py、db.py、api.py、coupon_rule.py 都通过清晰的函数调用
- 不在别的地方“偷偷发券”

将来从：

```python
send_coupon_for_order(trade_nos: List[str])
```

改成：

```python
send_coupons(requests: List[Dict])
```

成本大概就是：

- 改 1 个函数签名
- 改 1 个内部流程
- 改 1 个调用它的路由函数

**这是非常可控的，不是毁天灭地级别的重构。**

真正可怕的是这种情况：

- 在三个不同文件里都写了调用 `ApiClient.send_coupon` 的逻辑
- 有的地方直接从数据库拿值，有的地方从请求拿值
- 没有统一的 service 层，所有东西搅在一起

那不管你现在参数设计得多“高级”，将来改的成本都很大。

> ✅ 真正决定重构成本的是“边界划得清不清”，不是“参数今天选 trade_no 还是 JSON”。
