## 2. 一个适合你当前项目规模的目录演化目标

不用搞得太 DDD，也不用学大型项目那套，我们先用一个**三层结构**，非常适合你现在这个业务：

```text
project_root/
  app/                # 接口层：给人/外部用的入口
    __init__.py
    web_app.py        # 以后你的 Flask / FastAPI 路由可以放这
    cli.py            # 如果你以后想做命令行触发，可以放这里（可选）

  core/               # 核心业务：规则 + 流程
    __init__.py
    services.py       # preview / send 这些应用服务
    coupon_rule.py    # 发什么券的规则

  infra/              # 底层支撑：数据库、接口、配置、日志
    __init__.py
    db.py             # Oracle 访问
    api.py            # 发券 / 推券接口封装
    config.py         # 配置读取（可以把日志也放进来）

  config.yaml         # 配置文件（一般放项目根目录）
  main.py             # 启动入口（只负责创建 app / 调 CLI，不写业务逻辑）
```

设计动机很简单：

- **app/**：任何“面对外界”的东西都在这层（Web、CLI、Task 等等）
- **core/**：这是“你的业务大脑”，只懂订单、会员、券这些概念，不关心 Oracle / HTTP 细节
- **infra/**：这里都是“工具人”：数据库、接口、配置、日志，任何技术细节都扔这

将来你看代码时，脑子里的路线会变成：

> 外面来一个请求 → app/ 处理输入输出 → 调 core/services → core 再通过 infra 去访问数据库和外部接口。

这就是最基础的**分层架构思维**：UI 层 → 应用层 → 领域层 → 基础设施层，你现在用的是一个简化版。

## 3. 你接下来最应该做的一件“小事”（非常关键）

现在先不要真的去移动代码，我们先在“设计层面”做拆分练习：

> 想象你准备按上面这个结构拆，你会怎么把现有文件归类进去？

更具体一点：

- `db.py` 放到 `infra/db.py` 很自然
- `api.py` 放到 `infra/api.py`
- `config.py` 放到 `infra/config.py`
- `coupon_rule.py` 放到 `core/coupon_rule.py`
- `services.py` 放到 `core/services.py`
- 未来 `app.py` → `app/web_app.py` 或类似名字

但是：你也可以按自己的习惯微调，比如：

- 不叫 `core`，改叫 `service` 或 `domain`
- 不叫 `web_app.py`，改叫 `views.py` 等等

**重要的是：你要自己给每一层起一个你看得顺眼的名字**。
当你能把“行为”挂到“层”和“目录”里，你就已经在做架构设计了。
