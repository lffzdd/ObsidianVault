很好，你这一步自己把“有效日期写进配置 → 生成时间自然进了核函数”，这就是**真正的架构思维在自己长出来**，不是照书抄，而是被业务推着往前演化。非常好。

那我们就顺势进入下一步：
**把“print 式脚本风格”升级成“有结构的日志系统”。**

这是很多人从“会写代码”到“会写服务”的分水岭之一。

---

## 为啥现在该上“日志”了？

回顾一下你现在的代码里有这种东西：

```python
if conn is None:
    print("无法建立数据库连接")
    return []
```

print 有几个问题：

1. 没有等级（是错误？警告？正常 info？）
2. 没有统一格式，排查问题很难过滤
3. 上生产 / 部署到别的机器时，根本没法管输出去哪儿
4. 日志这种东西，本质上属于 **基础设施（base 层）**，不应该散落在各个业务模块里乱 print

从“系统演化史”的角度看：

- 最早的程序只会 `printf`
- 后来程序变复杂，大家发明了 log 库（分等级、可配置输出位置、可加时间等）
- 再后来，日志变成“所有服务的基本基础设施之一”，就像 DB / 配置一样，被统一管理

你现在的项目规模刚好到一个节点：

> 代码已经分层了，业务规则也抽出来了，接下来就该给“横切关注点（logging）”找个归宿。

---

## 这一步的目标：做一个“最小可用”的 logging 基础设施

我们不玩花活，就做三件小事：

1. 在 `base` 里建一个统一的日志工具模块
2. 在 service / 核心位置用它代替 print
3. 给每个关键流程打上合理的日志等级

### 第 1 步：在 `base/` 里新建一个 `logging.py`（或者 `logger.py`）

比如 `base/logger.py`：

```python
import logging

def get_logger(name: str = "app"):
    logger = logging.getLogger(name)
    if not logger.handlers:
        logger.setLevel(logging.INFO)

        handler = logging.StreamHandler()
        fmt = logging.Formatter(
            "[%(asctime)s] [%(levelname)s] [%(name)s] %(message)s"
        )
        handler.setFormatter(fmt)
        logger.addHandler(handler)

    return logger
```

设计动机：

- 放在 `base`：说明“日志是一种基础设施”
- 用 `get_logger` 而不是全局 logger：不同模块可以用不同 name，比如 `core.services`、`core.coupon_rule`
- 用 `logging` 标准库就够用，不搞三方

---

### 第 2 步：在 `core/services.py` 中使用 logger，替代 print

比如原来的：

```python
from base.db import get_db_connection
...

def preview_unissued_orders() -> List[Dict]:
    conn = get_db_connection()
    if conn is None:
        print("无法建立数据库连接")
        return []
```

可以改成：

```python
from base.db import get_db_connection
from base.logger import get_logger

logger = get_logger(__name__)

def preview_unissued_orders() -> List[Dict]:
    conn = get_db_connection()
    if conn is None:
        logger.error("无法建立数据库连接")
        return []
```

这里几个关键点：

- `logger = get_logger(__name__)`：
	这样日志里会带上模块名，比如 `core.services`，排查问题时一眼能看出来是谁打的
	
- `logger.error(...)`：
	说明这是“异常情况”，不是普通 info

以后你的 `send_coupon_for_order` 里也可以：

- 发券失败 → `logger.error(...)`
- 某些订单无券匹配 → `logger.warning(...)` 或 `info`
- 正常统计 → `logger.info("成功发券 %d 条", count)`

---

### 第 3 步：分清几种常用日志等级（以后写系统必用）

不用记一堆规则，只要记住一个“从严重到正常”的排序：

- `logger.error(...)`
	- 无法继续当前流程、或者必须马上注意的问题
	- 比如：数据库连不上、外部发券接口挂了
- `logger.warning(...)`
	- 可以继续跑，但行为“不完全正常”
	- 比如：某条订单匹配不到券（但整体流程没挂）
- `logger.info(...)`
	- 正常行为的记录
	- 比如：预览时查到多少条记录、实际发券多少条

你现在最少用到的是：`error` + `info`。

## ✅ 这一轮给你的具体小任务

就做两件很小的事：

1. 在 `base/` 里新建一个 `logger.py`（或你喜欢的名字），实现一个 `get_logger(name: str)` 函数，类似我上面的示例
2. 在 `core/services.py` 里：
	
	- 顶部引入 logger：`from base.logger import get_logger`
	- 定义 `logger = get_logger(__name__)`
	- 把 `print("无法建立数据库连接")` 替换成 `logger.error("无法建立数据库连接")`
	- 如果你愿意，可以在发券流程里顺手加一两个 `logger.info(...)`，比如记录“本次预览多少条”、“本次发券多少条”

做完之后，跑一遍：

```bash
python main.py
```

看看控制台输出是不是变成了：

```text
[2025-11-18 20:00:00] [ERROR] [core.services] 无法建立数据库连接
```

这样的结构化格式。
