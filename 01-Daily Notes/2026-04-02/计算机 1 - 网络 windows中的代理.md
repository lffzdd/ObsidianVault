这是一个非常敏锐的问题！你直觉上认为的“老实”，恰恰触及了计算机网络发展史上的一个大分歧。

简短的回答是：**恰恰相反。在 Windows 的世界里，真正“老实的”（原生的）Windows 软件，根本不看环境变量，而是去看 Windows 注册表。** 依赖环境变量 `HTTP_PROXY` 去走代理的，反而是具有 Unix/Linux “血统”的跨平台软件。

为了让你彻底理解这个冲突，我们需要从这两大阵营的历史脉络和底层标准讲起。

### 1. 微软阵营：注册表与 WinINet（Windows 的“老实人”）

在 20 世纪 90 年代，随着 Internet Explorer 的崛起，微软希望在 Windows 系统层面统一所有的网络请求和代理设置。于是，微软开发了一套底层的网络 API：**WinINet**（后来发展出 WinHTTP）。

- **它的机制是：** 所有网络配置（包括代理服务器的 IP 和端口、排除列表）都被死死地写在 **Windows 注册表** 中。
- **什么是 Windows 上的“老实软件”？** 比如 Edge 浏览器、Windows Update、Office 套件，以及所有使用 C#/.NET 原生 `HttpClient` 开发的传统 Windows 桌面软件。它们在发起网络请求前，会乖乖调用 WinINet API，系统会自动把注册表里的代理配置塞进去。
- **你平时点击的“开启系统代理”：** 当你在代理软件（如 Clash、v2rayN）中点击“开启系统代理”时，代理软件在底层做的事情，其实就是**修改 Windows 注册表**，让 WinINet 知道代理服务器在 `127.0.0.1:7897`。

### 2. Unix/Linux 阵营：环境变量（跨平台的“老实人”）

与微软大包大揽的作风不同，Unix/Linux 社区崇尚“松耦合”和简单文本。在 Linux 系统中，没有注册表这种庞然大物。

- **它的机制是：** 社区约定俗成地使用**环境变量**（Environment Variables）来传递配置。也就是你熟悉的 `HTTP_PROXY`、`HTTPS_PROXY` 和 `NO_PROXY`。
- **跨平台软件的基因：** 像 Node.js (OpenClaw 的底层)、Python、Git、curl、Go、Rust 这些技术，它们要么诞生于 Unix/Linux，要么为了保证跨平台的一致性，默认遵循 Unix 的标准。
- **水土不服：** 当 Node.js 运行在 Windows 上时，它依然保留着 Unix 的习惯。它会去检查 Windows 的环境变量里有没有 `HTTP_PROXY`，但它**绝对不会**去调用 Windows 的 WinINet API，也不会去读注册表里的代理设置。

### 3. 为什么 OpenClaw 会“漏流”？

现在，我们把你的操作和底层原理对应起来，问题就水落石出了：

1. **代理软件只管了微软阵营：** 你的代理软件（挂在 7897 端口）开启“系统代理”后，修改了 Windows 注册表。Edge 浏览器等原生软件走代理了。
2. **环境变量缺失：** 虽然有些代理客户端会尝试同时修改 Windows 的系统级环境变量，但这通常需要你**重启终端（甚至重启电脑）**才能让新打开的 `pwsh` 读取到。如果环境变量没生效，`pwsh` 里是空的。
3. **Node.js 扑空：** OpenClaw (Node.js) 在 `pwsh` 中启动，它按照它的“老实”标准去寻找 `HTTP_PROXY` 环境变量，发现是空的。然后它去看 Windows 注册表？不，它不认识那东西。于是它认为当前没有代理，直接发起直连。

### 4. 终极的“不老实”：WebSocket 协议的特殊性

即便你在 `pwsh` 中手动设置了 `HTTP_PROXY`，满足了 Node.js 的 Unix 胃口，OpenClaw 的 WebSocket 依然可能连不上。这涉及到了代码实现层面的问题：

在 Node.js 中，原生的 `http`/`https` 请求库在后来的版本中对环境变量有了较好的支持。但是，**WebSocket 并不是普通的 HTTP 请求**。

WebSocket 在完成初始的 HTTP 握手后，会升级为一个持久的 TCP 长连接。在 Node.js 生态中，常用的 WebSocket 第三方库（如 `ws`），**默认情况下完全无视任何代理环境变量**。

如果要让 WebSocket 走代理，开发者必须在 OpenClaw 的源代码里写一段特定的逻辑：

> “读取 `HTTP_PROXY` -> 引入一个叫做 `https-proxy-agent` 的库 -> 把这个 Agent 强行注入到 WebSocket 的连接参数中。”

如果 OpenClaw 的开发者偷懒了，或者漏写了这段专门针对 WebSocket 的代理路由逻辑（这在开源项目中非常常见），那么无论你怎么设置环境变量，它的 WebSocket 流量都会像脱缰的野马一样强行直连。

---

**总结**

你在 Windows 上遇到的并不是“软件不老实”，而是**两套截然不同的操作系统网络哲学发生了碰撞**。OpenClaw 遵循了 Unix 的标准（环境变量），却忽视了 Windows 的标准（注册表），并且在代码层面可能没有为 WebSocket 做好代理适配。

这也正是为什么我在上一个回答中，最强烈推荐你使用 **TUN 模式（虚拟网卡）**。因为 TUN 模式工作在网络层（OSI 模型的第 3 层），它直接接管所有发往网卡的 IP 数据包。管你是遵守注册表的微软系，还是遵守环境变量的 Linux 系，甚至是代码写得很糟糕的 WebSocket 库，只要你的数据包想出网卡，统统会被 TUN 模式在底层截获并送入代理通道。这是降维打击。
