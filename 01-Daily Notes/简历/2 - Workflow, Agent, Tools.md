下面把这篇笔记的核心内容拆解成多张表格，覆盖定义、对比、设计原则、运行机制、编排模式和组合方式。贯穿全文的一句话是：**三者最本质的区分维度只有一个——「下一步该干什么」这个决策由谁来做。**

### **一、三者核心定义与本质**

| 概念 | 本质定义 | 核心职责 | 形象类比 |
|---|---|---|---|
| **Tools** | 按 LLM 可读的 schema（名字、描述、参数类型）暴露的函数，除这层「说明书」外与普通函数无异 | 只负责「被调用时干什么」，本身**不知道自己该在何时被使用** | 瑞士军刀上的每一个刀片 |
| **Agent** | 以 LLM 为大脑的完整决策系统 | 自主判断：要不要调工具、调哪个、够不够、停不停 | 拿着刀、决定抽哪个刀片的那只手 |
| **Workflow** | 更上层的编排框架，把流程「骨架」写死在代码里 | 让 LLM／Agent／Tools 各做一个节点，但整体走向由开发者代码决定 | 把所有人组织起来的总指挥 |

补充一句关键纠错：Workflow **不是「多个 Agent 串联」**，它的节点可以是 LLM 调用、Tools 或 Agent，重点不在节点类型，而在控制流由谁掌握。

### **二、核心维度全面对比**

| 维度 | Tools | Agent | Workflow |
|---|---|---|---|
| **决策能力** | 无，只执行不决策 | 有，LLM 运行时自主动态决策 | 无，开发者在代码里提前写死 |
| **执行方式** | 被动，等待被调用 | 主动，自主循环直到完成 | 按开发者定义的顺序／分支流转 |
| **确定性** | 高，输入固定则输出固定 | 低，同样输入可能走不同路径 | 高，行为完全可预测 |
| **灵活性** | 低，只做一件事 | 高，能应对预料之外的情况 | 低，流程提前写死，难动态调整 |
| **调试难度** | 容易，单一函数 | 难，执行路径不确定、难复现 | 容易，链路清晰可逐步追踪、打断点 |
| **适用场景** | 封装单一具体能力 | 路径未知的复杂任务 | 流程相对固定的业务系统 |

### **三、Tools 工程设计原则**

很多 Agent 系统表现差，根源不是 LLM 不行，而是工具设计有问题。

#重点

| 设计原则 | 具体要求 | 反例 → 正例 |
|---|---|---|
| **职责单一** | 一个工具只做一件事，模型靠描述判断该不该调用，职责太杂就难精确触发 | 「查天气 + 发邮件」混在一起 → 拆成两个独立工具 |
| **描述要精确** | 模型完全靠 description 理解工具能力，含糊会导致误调用 | 「查询数据」→「查询公司内部销售数据库，支持按日期和产品类别筛选，返回销售额和订单数」 |
| **错误信息清晰** | 失败时返回 LLM 能看懂的信息，便于其自行修正参数重试 | 「Error code 400」→「参数 city 不能为空」 |
| **参数设计简洁** | 能少传就少传，能给默认值就给默认值，参数越多越易出错 | 必填一堆参数 → 设默认值、精简必填项 |

行业趋势：Anthropic 在 2024 年底提出 **MCP（Model Context Protocol）**，把工具的注册、描述、调用标准化，相当于工具世界的「USB 接口」，让不同 Agent 框架与工具提供方互通，不必每接一个新工具就写一套适配代码。

### **四、Agent 运行机制与停止条件**

Agent 的运行是一个反复循环：**想清楚（Thought）→ 行动（Action）→ 看结果（Observation）→ 再想 → 再行动……** 直到 LLM 判断任务完成。代码上体现为一个 `while True` 循环，**跑几轮开发者完全不知道，由 LLM 实时决定**——这正是它和普通代码最不一样的地方，也带来「行为不确定」的副作用（同一任务两次执行可能走完全不同的路径）。

正因为是 `while True`，生产环境必须有明确的停止机制，防止失控：

| 停止条件 | 触发方式 | 作用 |
|---|---|---|
| **LLM 主动判断完成** | 模型认为目标已达成，输出最终答案 | 最理想的情况 |
| **最大循环次数** | 例如最多跑 15 轮，超过强制停止并返回现有结果 | 防止无限循环 |
| **总 token 预算上限** | 消耗接近预算即停止 | 防止成本失控 |
| **超时机制** | 整体运行超过例如 60 秒就终止 | 防止长时间挂起 |

实际工程中这几种机制通常同时存在，哪个先触发就用哪个。此外，由于路径不确定、出错难复现，很多团队会给 Agent 加详细执行日志，记录每一步思考与工具调用结果以便追溯。

### **五、Workflow 常见编排模式（Anthropic 实践总结）**

| 编排模式 | 核心思路 | 适用场景 |
|---|---|---|
| **Prompt Chaining（提示链）** | 把大任务拆成多个小步骤，前一步输出作为后一步输入，像流水线串起来 | 步骤明确、可线性分解的任务 |
| **Routing（路由）** | 先用 LLM 做分类判断，再把请求分发到不同处理分支 | 客服系统按意图分流等 |
| **Parallelization（并行化）** | 把可同时进行的子任务并行执行，最后汇总结果 | 多维度分析、多数据源同时检索 |
| **Orchestrator-Workers（编排者-工人）** | 中央编排者分配任务，多个 Worker 各自完成子任务 | 任务可分解且子任务相互独立 |
| **Evaluator-Optimizer（评估者-优化者）** | 一个 LLM 生成输出，另一个 LLM 评估质量，不通过就反馈重做，循环至通过或达上限 | 输出质量要求高，如营销文案、法律条款、写代码（注意：评估标准须在代码里定义清楚，不能让评估者自由发挥） |

这些模式并不互斥，实际项目常混合使用。

### **六、三者如何组合：Agentic Workflow 是生产主流**

「我该用哪个」其实是个伪命题——真实项目里三者**同时存在、相互嵌套**。

| 方案 | 做法 | 优劣判断 |
|---|---|---|
| **纯 Agent 自主决策** | 全交给 LLM 动态决定 | 行为难控制、出问题难排查、调用轮数多导致成本易失控，**很少用于生产** |
| **纯 Workflow 写死** | 所有路径在代码里穷举 | 太脆，遇到预料之外的输入易失败或给出很差结果 |
| **Agentic Workflow** | 用 Workflow 固定主流程骨架，在需灵活判断的节点嵌入 Agent，其余固定节点直接用 LLM 或 Tools | **当前生产主流**：骨架确定→可控易调试，关键节点灵活→能应对复杂情况，两个优点都有、两个缺点都被削弱 |

从性能成本看：纯 Agent 一个复杂任务可能跑十几到几十轮，每轮都要发完整上下文，token 线性增长、延迟累积；而 Workflow 流程固定，可精确控制每个节点的 token 预算、按需并行，延迟和成本都更可控——这也是团队从原型阶段（纯 Agent 快速验证）过渡到生产阶段时，普遍把系统重构为 Agentic Workflow 的原因。

总结成一句面试话术：**Tools 不做决策只执行，Agent 由 LLM 运行时自主决策，Workflow 是开发者把决策提前写死在代码里；三者不是三选一，而是以 Agentic Workflow 的形式嵌套组合,兼顾可控性与灵活性。**
