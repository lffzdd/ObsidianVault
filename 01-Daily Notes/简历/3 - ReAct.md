这是对当前页面《Agent 推理模式 / ReAct》面试笔记的详细拆解，按"为什么需要推理模式 → CoT → ReAct → Plan-and-Execute"的逻辑用多个表格逐层展开，保留原文的具体细节和例子。

### **一、四种推理模式总览对比**

| 模式 | 核心思路 | 工具交互 | 优势 | 局限 |
|---|---|---|---|---|
| 直接输出 | 没有中间推理，一口气预测答案 | 无 | 快、简单 | 多步推理时误差在隐式步骤中累积，答案"感觉对"但常错 |
| CoT（思维链） | 先把推理过程写出来再给答案 | 无（纯文字） | 推理过程显式化、准确率更高、过程可见 | 纯文字推理，拿不到实时数据、不能执行计算/访问数据库 |
| ReAct | 在 CoT 基础上加"行动"，交替输出思考与工具调用 | 有（原生交织） | 推理可见 + 能动态调用外部工具，两个优点都有 | 循环漂移、错误传播 |
| Plan-and-Execute | 先规划出完整计划，再逐步执行 | 有 | 全局视野、不易跑偏，适合复杂多步任务 | 简单任务时初始规划是多余开销 |

### **二、为什么需要"推理模式"**

| 要点 | 具体说明 |
|---|---|
| 根本困境 | LLM 是一个 token 一个 token 往后预测；多步问题"一口气"作答时，中间推导是隐式的，无法强制每步都正确 |
| 误差来源 | 误差在中间暗处悄悄累积，最终暴露在答案里 |
| 类比 | 心算"123×456"易错；把每一步写在纸上（123×6=738、123×50=6150…）出错率大大降低 |
| 本质作用 | 通过不同方式把隐式思考显式化，让下一步预测建立在已写清的正确前文上，减少累积误差 |

### **三、CoT 的两种触发方式**

| 类型 | 具体做法 | 优点 | 缺点 |
|---|---|---|---|
| Zero-shot CoT | 在 prompt 末尾直接加"让我们一步步思考"，无需示例 | 零成本、即插即用 | 推理格式和深度全靠模型发挥，不稳定，有时详细有时跳步 |
| Few-shot CoT | 在 prompt 里给几个带完整推理过程的例子让模型模仿 | 效果更稳定，适合输出格式固定的场景 | 需提前准备高质量示例，示例本身也占用 token |

### **四、为什么 ReAct 优于纯 CoT 和纯 Act-only**

| 方案 | 做法 | 核心问题 |
|---|---|---|
| 纯 CoT | 只在"脑子里"推理 | 推得再好也拿不到真实数据，遇到实时信息就抓瞎，且无外部事实校准、易产生幻觉 |
| 纯 Act-only | 直接输出工具调用序列，不写任何思考 | 动作之间无推理链条连接，"闷头干活不动脑"；HotpotQA 多跳问答上准确率明显低于 CoT 和 ReAct，某步搜到无关内容后续动作全跑偏 |
| ReAct | 推理与行动交织 | Thought 提供方向、Action 落地决策、Observation 带回事实，三者互补成闭环——这是它更好用的根本原因 |

### **五、ReAct 循环的核心要素**

| 要素 | 含义 | 由谁产生 |
|---|---|---|
| Thought | 推理：分析当前局势、决定下一步该做什么 | LLM |
| Action | 决定调用哪个工具 | LLM |
| Action Input | 工具的输入参数 | LLM |
| Observation | 工具执行后返回的真实结果 | 系统/代码填入（模型不用写） |
| Final Answer | 任务完成的终止信号 | LLM |

下面用原文"2024 年苹果与谷歌市值谁更高"的例子，把循环过程具体化：

| 轮次 | Thought | Action / Action Input | Observation |
|---|---|---|---|
| 第 1 轮 | 需要两家实时市值，先查苹果 | search / 苹果公司 2024 年市值 | 苹果约 3.5 万亿美元 |
| 第 2 轮 | 苹果有了，再查谷歌 | search / 谷歌 2024 年市值 | 谷歌约 2.1 万亿美元 |
| 第 3 轮 | 两数都有，苹果更高，差 1.4 万亿 | Final Answer | 苹果约 3.5 万亿、谷歌约 2.1 万亿，苹果更高，差约 1.4 万亿美元 |

### **六、ReAct 实现原理：模型与代码的分工**

这是面试最容易踩坑的地方——循环不是模型自己在转，而是由代码驱动。

| 环节 | LLM 负责 | 代码框架负责 |
|---|---|---|
| 每轮动作 | 根据当前历史，只输出下一步的 Thought + Action | 检测输出、判断有没有 Final Answer |
| 工具执行 | 不执行工具，只决定调什么 | 解析出 Action 与 Input，执行对应工具拿到结果 |
| 历史管理 | 把完整历史当作"记忆"做推理 | 把 Observation 填回历史，再次带完整历史调用 LLM |
| 终止控制 | 判断任务完成时输出 Final Answer | 检测终止条件、控制最大步数（如 max_steps） |

一句话概括：**模型负责推理，代码负责驱动**。真正的"智能"全在每轮 Thought 里，代码做的是管理对话历史、执行工具、检测循环终止。

### **七、经典实现 vs 现代 Function Calling**

| 对比项 | 经典实现 | 现代 Function Calling / Tool Use |
|---|---|---|
| 驱动方式 | 靠 prompt 格式约束 + 文本解析（解析 `Action: xxx`） | 模型直接输出结构化 JSON 工具调用 |
| 适用模型 | 早期模型 | GPT-4、Claude 3 之后基本原生支持 |
| 可靠性 | 易因输出格式不规范而解析失败 | 更干净、更可靠 |
| 循环本质 | "思考→行动→观察"循环不变，只是"行动"从解析文本变为解析结构化 JSON | 同左 |

### **八、ReAct 的两大实战局限**

| 局限 | 比喻 | 具体表现 | 根源 |
|---|---|---|---|
| 循环漂移 | 没导航的旅行者，被沿途风景吸引拐进岔路 | 让它查"苹果近三年营收趋势"，却因搜索结果提到三星竞争关系而跑去查三星，步骤越多历史越长越易偏离 | 每步都基于当前历史重新决策，无全局计划约束 |
| 错误传播 | 一步错、步步错 | 中间某步信息错误或工具返回有误，后续推理全被带跑；且无"回头检查"机制，默认前面 Observation 都对一路往前冲 | 纯"前向推理"，无反思机制纠错 |

两者的共同根源：ReAct 是纯前向推理，走一步看一步，既没有全局规划约束方向，也没有反思机制纠正错误。

### **九、Plan-and-Execute 的两个阶段**

| 阶段 | 名称 | 做什么 | 关键点 |
|---|---|---|---|
| 第一阶段 | 规划 Planner | 把任务交给 LLM，站在全局想清楚分几步、每步做什么、步骤依赖关系，输出结构化执行计划 | 只做规划、不执行任何工具，注意力全在"想清楚" |
| 第二阶段 | 执行 Executor | 拿着计划按顺序逐步执行，单个子任务内部仍可用 ReAct 跑"思考→行动→观察" | 执行器始终知道自己在整体计划的哪一步，不会漫无目的漂移 |

额外关键设计是**动态重规划**：计划是"活的"，每执行完一步检查实际结果与预期是否一致；若某步出乎意料（如要查的 API 已下线），就把已有结果和剩余步骤重新交给 Planner 调整后续计划，类似导航遇到封路自动重新规划路线。

### **十、ReAct vs Plan-and-Execute 选型**

| 维度 | ReAct | Plan-and-Execute |
|---|---|---|
| 优势 | 灵活，每步都能根据最新情况决策 | 有全局视野，不易跑偏 |
| 适用场景 | 任务边界不明确、需探索性获取信息，如开放式问答、信息搜索 | 目标明确、需多步骤协作的复杂任务，如深度研究、长文写作、多工具数据分析 |
| 代价 | 易漂移；每步都带完整历史调 LLM，步骤多了 token 消耗线性增长 | 初始规划需额外一次 LLM 调用，简单任务（一两步）时反成多余开销 |

实际工程中两者常**混合使用**：用 Plan-and-Execute 做全局规划、用 ReAct 做每步执行；规划阶段用能力更强的大模型（如 GPT-4、Claude Opus）保证计划质量，执行阶段用便宜的小模型跑具体工具调用。这种大小模型搭配的架构可降低约 **70%~90%** 的 LLM 调用成本，是非常实用的工程技巧。

如果你正在准备面试，这页最该记住的两句话是：**ReAct 的本质是"思考→行动→观察"的循环**，以及**这个循环由代码框架驱动、模型每轮只输出 Thought + Action**——把这两点说清，再补上两个局限和 Plan-and-Execute 的应对，回答就很有深度了。
