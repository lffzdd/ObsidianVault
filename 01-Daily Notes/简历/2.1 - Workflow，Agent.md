### **一、Workflow 与 Agent 的本质区别**

最核心的区别是「谁来决定下一步」：Workflow 是开发者提前把流程写死，Agent 是把决策权交给 LLM。

| 维度          | Workflow                              | Agent                                             |
| ----------- | ------------------------------------- | ------------------------------------------------- |
| 决策者（谁决定下一步） | 开发者，流程硬编码写死，LLM 只是某个节点的执行工具           | LLM，运行时动态决策                                       |
| 控制流         | 代码提前定好「第一步做 A，A 完了做 B，B 失败走分支 C」，每步固定 | loop 里只有 `llm.decide()`，调哪个工具、是否继续、何时完成都由 LLM 实时选 |
| 确定性         | 高，行为完全可预测                             | 低，同样的输入可能走出不同路径                                   |
| 灵活性         | 低，遇到没预料到的情况会走入死胡同                     | 高，能处理事先没设计进去的情况                                   |
| 调试/复现       | 容易，链路清晰，出问题能精确定位是哪个节点                 | 困难，行为概率性，线上出问题很难复现                                |
| 测试覆盖率       | 高，容易测试                                | 低，天然覆盖率就低                                         |
| 角色比喻        | 开发者在驾驶                                | LLM 在驾驶，开发者在副驾驶设了一些安全限制                           |
| 适用场景        | 流程相对固定的业务                             | 需要灵活判断的复杂任务                                       |

### **二、Agent 三种设计范式**

| 范式 | 核心机制 | 优点 | 缺点 / 代价 | 适用场景 |
|------|----------|------|-------------|----------|
| **ReAct**（Reasoning + Acting） | 推理与行动交替，构成 Thought → Action → Observation 循环，不断重复直到 LLM 判断「信息够了」才给出最终答案 | 先想后做，避免「冲动决策」；Thought 过程可见，方便定位是在哪一步想歪了；决策质量更稳定 | 「走一步看一步」，每步只是局部最优；复杂任务（如十几步）易迷失方向、忘记初始目标，或在几个工具间反复打转 | 步骤不多、每步相对独立的任务 |
| **Plan-and-Execute** | 规划与执行彻底解耦：一个 LLM 专门做规划、输出完整步骤列表，另一个 LLM（或同模型不同角色）逐步执行；关键是**动态重规划**——每执行一步把结果反馈给规划器，判断是否偏离、是否需要调整或插入新步骤 | 复杂任务整体结构清晰；执行前可人工审核计划是否合理；既保全局视野又不会因死板而失效 | 多了规划和重规划的 LLM 调用，延迟和成本都增加；若初始规划方向就错了，后面再调执行细节也难挽回 | 很复杂、步骤间有依赖、需要全局统筹的任务 |
| **Reflection**（反思） | 在完成一步或整个任务后，再让一个 LLM（同模型或专门评估模型）判断做得好不好、是否符合预期，不通过就重试或换策略，相当于加一层「质量保障」 | 显著提升输出质量，在代码生成、文案写作这类「质量要求高但一次做对很难」的场景尤其明显 | 每加一轮反思就多一次甚至多次 LLM 调用，token 消耗和延迟都增加，需要在「质量提升」与「成本增加」间取舍 | 对输出质量要求特别高、允许多花时间和成本的场景 |

**ReAct 每一轮的三个步骤（具体到例子）：**

| 阶段 | 做什么 | 举例 |
|------|--------|------|
| Thought（推理） | LLM 先把当前情况分析一遍，把推理过程写出来 | 「用户想查竞品信息，我应该先用搜索工具查一下竞品 A 的最新动态」 |
| Action（行动） | 根据思考结论决定调用哪个工具、传什么参数 | 调用搜索工具并传入查询参数 |
| Observation（观察） | 工具返回结果反馈给 LLM，读取后进入下一轮 Thought | 读取搜索结果，重新分析局面、决定下一步 |

**Reflection 与其变体 Reflexion 的区别：**

| 对比项 | 基础 Reflection | Reflexion（变体） |
|--------|----------------|-------------------|
| 做法 | 评估结果好不好，不通过就「重做一遍」 | 不只是重做，而是生成一段具体的「反思总结」，记录失败原因和改进建议 |
| 经验传递 | 简单重试，不积累经验 | 把反思总结作为额外上下文传给下一次尝试（类似「写错题本」，带着教训再做一次） |
| 效果（有数据支撑） | 提升质量 | 在 HumanEval 代码生成基准上，GPT-4 直接做准确率约 80%，加 Reflexion 后提升到 91% |

### **三、三种范式如何选型**

核心看两个维度：**任务复杂度**和**质量要求**。三者并不互斥，实际项目常混合使用。

| 场景 / 需求 | 推荐做法 |
|-------------|----------|
| 步骤不多、每步比较独立 | ReAct，简单直接 |
| 任务很复杂、步骤间有依赖、需要全局统筹 | Plan-and-Execute |
| 对输出质量要求特别高、允许多花时间和成本 | 在前面基础上叠加 Reflection |
| 综合大型系统 | 混合使用，例如用 Plan-and-Execute 做整体规划，每步内部用 ReAct 执行，关键步骤再加 Reflection 把关 |

### **四、工程实践：Agentic Workflow（生产环境主流）**

纯 Agent 模式在生产里其实用得不多，因为太难控制。更常见的是 **Agentic Workflow**：整体用 Workflow 框住主流程保证可控，只在需要灵活处理的节点嵌入 Agent 能力。

| 要点 | 说明 |
|------|------|
| 核心思路 | Workflow 框住主流程，灵活节点内部用 Agent 动态决策 |
| 客服系统示例 | 「意图识别 → 知识检索 → 回答生成」主链路是固定 Workflow；但「知识检索」节点内部用 Agent 动态决定检索几轮、用哪些工具 |
| Anthropic 原则 | **能用 Workflow 解决的问题，就不要用 Agent**——生产环境里可控性比灵活性更重要 |
| 落地策略 | 从最简单的 Workflow 开始，只有当某节点确实需要灵活决策、写死逻辑覆盖不全时，才把该节点升级成 Agent（从简单到复杂、按需升级） |

这道题的三个高分要点也可以记一下：三种范式（ReAct / Plan-and-Execute / Reflection）各有适用场景、Reflection 是正式的运行时机制而非调试工具（代价是 token 和延迟）、以及能主动说出「为什么纯 Agent 在生产里有局限、应优先 Agentic Workflow」。
