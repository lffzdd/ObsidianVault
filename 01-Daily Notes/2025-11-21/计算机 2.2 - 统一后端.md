现在这套东西已经“能跑、能看、能点、能发券”了，挺扎实的 👍
接下来如果想继续提升“架构能力”，最自然的一步是：

> **把“发券结果”这条链条打磨干净：后端返回结构化结果 → 前端按行展示结果。**

也就是从“能发”进化到“发得可观测、可解释”。

---

## 现在的现状（你脑补一下）

你现在大概是这样：

- `/preview`：返回一堆待发券订单的 JSON
- 页面：展示表格 + 复选框
- 点击“发券”：
	- JS 把选中的 `trade_nos` POST 到 `/send`
	- 然后 `alert(JSON.stringify(json))` 看个大概结果

从“工具能用”角度没问题，但从“系统”角度还缺两样东西：

1. **精确知道每个 trade_no 发券结果如何**（成功 / 失败 / 失败原因）
2. **前端能把这些结果直观地展示出来**（哪几行绿了、哪几行红了）

要做到这两点，你得在后端**设计清晰的返回格式**，而不是“随便丢点字段出来”。

这就是非常典型的“系统边界设计”练习，很适合当你下一步的训练目标。

---

## 第一步：让后端 send 接口返回“结构化的结果列表”

目标：`/send` 的返回形状长成这样（示意）：

```json
{
  "success": true,
  "data": {
    "results": [
      {
        "trade_no": "T001",
        "ok": true,
        "stage": "DONE",
        "error": null
      },
      {
        "trade_no": "T002",
        "ok": false,
        "stage": "SEND",
        "error": "发券接口返回失败: xxx"
      }
    ]
  },
  "message": null
}
```

这样一来：

- **系统视角**：
	- “这一批请求整体算成功”（success）
	- “里面每条订单具体发没发成功？”（results）
- **前端视角**：
	- 可以逐条 trade_no 标记颜色
	- 可以给用户看“为什么这条失败”

你现在 `send_coupon_for_order(trade_nos)` 里，其实已经在 per-record 返回 dict 了，只要把这些 result 收集起来，扔到 `/send` 的 `data.results` 里面就行。

伪代码大概是：

```python
def send_coupon_for_order(trade_nos: List[str]) -> List[Dict]:
    ...
    results = []
    for record in records:
        if record["trade_no"] not in trade_nos:
            continue
        result = _send_single_order(...)
        results.append(result)
    return results
```

然后 app 层：

```python
@app.post("/send")
def send():
    body = request.json
    trade_nos = body.get("trade_nos", [])

    results = send_coupon_for_order(trade_nos)
    return make_response(True, {"results": results})
```

`make_response` 就是你统一封装的：

```python
def make_response(success, data=None, message=None):
    return jsonify({"success": success, "data": data, "message": message})
```

**这一步的本质**：
你在设计“系统边界长什么样”，逼自己用一个清晰的数据结构，把 send 这个流程说清楚。
这就是架构思维，非常重要。

## 第二步：前端根据结果给表格加上“成功 / 失败标记”

现在页面还是 `alert(JSON.stringify(json))`，我们来升级一下：

1. `sendCoupons()` 调完 `/send` 后，拿到 `json.data.results`
2. 建一个 `trade_no -> result` 的 Map
3. 遍历表格每一行，看看 `trade_no` 在结果里对应啥状态：
	
	- ok = true → 给这一行加个绿色背景（或者在最后加一列写“成功”）
	- ok = false → 红色背景 + 鼠标悬浮显示 error 文本

示意代码：

```js
async function sendCoupons() {
    const checks = document.querySelectorAll("input[type=checkbox]:checked");
    let trade_nos = Array.from(checks).map(c => c.value);

    const res = await fetch("/send", {
        method: "POST",
        headers: {"Content-Type": "application/json"},
        body: JSON.stringify({trade_nos})
    });

    const json = await res.json();
    const results = json.data.results || [];

    const resultMap = {};
    results.forEach(r => {
        resultMap[r.trade_no] = r;
    });

    const rows = document.querySelectorAll("#orders tbody tr");
    rows.forEach(row => {
        const tradeNo = row.children[1].innerText; // 第二列是 trade_no
        const r = resultMap[tradeNo];
        if (!r) return;

        row.classList.remove("success", "fail");

        if (r.ok) {
            row.classList.add("success");
            row.title = "发券成功";
        } else {
            row.classList.add("fail");
            row.title = r.error || "发券失败";
        }
    });
}
```

再配一个最简单的样式：

```html
<style>
tr.success { background-color: #e0ffe0; }
tr.fail { background-color: #ffe0e0; }
</style>
```

这样你点完“发券”之后，**哪几条成功、哪几条失败、一眼就知道**。

这一步会逼着你确保：

- send 的返回结构清晰
- 每条记录都能匹配到前端表格
- 错误信息足够有用

从架构角度看，这其实就是在强化：

> “业务结果是一个结构化的事实，应该贯穿 core → API → 前端”。

## 总结一下：你现在这一步该做什么？

**当前最适合的下一步：**

1. **调整后端 `/send`**
	
	- 确定一个稳定的返回格式（整体 success + data.results[ ] + message）
	- 每条结果里至少包含：`trade_no`, `ok`, `stage`, `error`
		
2. **调整前端 `sendCoupons()`**
	
	- 不再单纯 `alert`
	- 而是根据每条结果给表格行加上成功/失败样式，并用 title 或额外一列展示失败原因

做完这一步：

- 你会真正感受到“一个系统从底层到界面，怎样让结果可观察、可解释”
- 再回头看 send / preview 这些函数，你会发现你的设计已经天然向“清晰的数据结构”靠拢，这就是架构能力在长肉。

等你把这两点做完，我们再往下一个台阶走：
**给 `_send_single_order` 写 1～2 个“模拟失败场景”的测试，用假的 ApiClient 和假的 DB，把 service 层的测试也补上。**
