### **正则表达式的本质,是用一种紧凑的字符串语法,描述"哪些字符串属于某个集合"——它背后是 1950 年代数学家发明的有限自动机理论,后来被一步步工程化成今天程序员每天敲的 `\d+`、`[a-z]*`、`(foo|bar)`,是少有的"纯数学产物 → 大规模工业应用"的完美案例。**

你之前已经懂了 grep、glob 这些用正则的工具,这一轮我们直接钻进正则本身。我会从 1940 年代神经科学的一个数学模型讲起,经过乔姆斯基的语言学、Thompson 的工程实现,一路讲到今天为什么 JavaScript 正则可能让你的服务器卡死(ReDoS)。读完之后,你看 `\d+@\w+\.com` 这样一行字,会看到背后五层抽象。

---

### **第 0 层:问题的起源——什么字符串"算"一个东西**

正则表达式要解决的根本问题,用人话说就是:

> **给定一个字符串集合(可能无限大),如何用一段有限的、紧凑的描述,准确地说清"这个集合里都有哪些字符串"?**

比如:
- "所有偶数长度的 01 串":集合是 `{"", "00", "01", "10", "11", "0000", ...}`,无限大,但有规律
- "合法的邮箱地址":集合也是无限大的,但你能"感觉到"它的形状
- "Python 标识符":字母或下划线开头,后面是字母数字下划线

这种"用有限规则描述无限集合"的需求,数学上叫**形式语言**(formal language)。正则表达式就是描述这类语言的一种工具。

记住这个视角:**正则表达式不是"模式匹配",它本质是在定义一个字符串集合**。当我们说"这个字符串匹配这个正则",真正的意思是"这个字符串属于这个正则定义的集合"。这是整个理论的根。

### **第 1 层:1943 年——神经元模型,正则的史前史**

故事得从一个跟计算机无关的领域开始:**神经科学**。

1943 年,神经生理学家 Warren McCulloch 和数学家 Walter Pitts 发表了一篇划时代的论文,叫 *"A Logical Calculus of the Ideas Immanent in Nervous Activity"*。他们试图用数学描述神经元的工作方式,提出了一种叫 **McCulloch-Pitts 神经元** 的模型——可以理解为最早的"人工神经元"。

这个模型有个性质:**多个神经元连接起来,可以表达某些"事件序列模式"**——比如"先 A 后 B"、"A 或 B"、"A 重复多次"。

十年后(1951 年),数学家 **Stephen Cole Kleene**(克莱尼)在兰德公司写了一份报告,把 McCulloch-Pitts 神经元能识别的所有事件模式,**用一套代数符号系统总结了出来**。这套符号系统就是**正则表达式的祖先**,Kleene 称它们为 **"regular events"**(正则事件)。

Kleene 定义的三个核心操作,直到今天还活在你的正则里:

| Kleene 操作 | 含义 | 现代正则写法 |
|------------|------|-------------|
| 连接(concatenation) | A 后面跟 B | `AB` |
| 并(alternation) | A 或 B | `A\|B` |
| 闭包(closure / Kleene star) | A 重复 0 次或多次 | `A*` |

**`*` 这个符号就叫 Kleene star**,以他的名字命名。每次你写 `.*`,你都在用一个 1951 年的数学符号。

至此,正则表达式作为**纯数学概念**诞生了。它跟编程毫无关系,纯粹是描述"神经网络能识别哪些模式"的工具。

### **第 2 层:有限自动机——正则的"硬件实现"**

Kleene 同时证明了一件极其重要的事,这件事是整个正则理论的基石:

> **正则表达式能描述的字符串集合,恰好等于有限自动机(finite automaton)能识别的字符串集合。**

这就是著名的 **Kleene 定理**。它意味着:**正则表达式是一种语言,有限自动机是它对应的"计算机器",两者表达能力完全等价**。

什么是有限自动机?极简的理解:**一个有有限多个状态的小机器,读入一个字符就根据规则跳转到下一个状态,读完整个字符串后,看最终停在哪个状态——如果停在"接受状态",就说这个字符串被接受了**。

举个具体例子。"以 0 结尾的 01 串"这个集合,可以用一个 2 状态机器描述:

```
       0           1
   ┌──────┐    ┌──────┐
   ▼      │    ▼      │
 ┌───┐ ──0──▶ ┌───┐
 │ q0│        │*q1│
 └───┘ ◀──1── └───┘
```

- `q0` 是初始状态(也是接受状态前的中转)
- `q1` 是接受状态(打星号)
- 读到 0 就往"接受方向"走,读到 1 就往回走
- 字符串读完后停在 q1,就说接受;停在 q0,就说拒绝

有限自动机有两种:

**DFA(Deterministic Finite Automaton,确定性有限自动机)**
每个状态对每个输入字符,**只有一条**确定的转移路径。机器运行就像走迷宫,每一步路径唯一。

**NFA(Nondeterministic Finite Automaton,非确定性有限自动机)**
每个状态对一个输入字符可以有**多条**可能的转移路径,甚至可以"什么字符都不读就跳转"(ε-转移)。机器运行就像同时走多条路。

关键定理:**任何 NFA 都能转换成等价的 DFA**(可能状态数会爆炸,但理论上可行)。所以两者表达能力相同。

为什么这层这么重要?因为后面所有正则引擎的实现差异,本质都是**"我们到底用 DFA 还是 NFA、用什么策略模拟它"** 这个选择带来的。

### **第 3 层:1956 年——乔姆斯基把正则放进语言学版图**

1956 年,语言学家 **Noam Chomsky**(乔姆斯基,你可能更熟悉他作为政治评论家的身份)发表了著名的 [Chomsky hierarchy](https://en.wikipedia.org/wiki/Chomsky_hierarchy)——形式语言的四级阶梯:

| 等级 | 语言类型 | 对应的"计算机器" | 例子 |
|------|---------|----------------|------|
| Type 3 | **正则语言** | 有限自动机 | `a*b*`、邮箱粗略形式 |
| Type 2 | 上下文无关语言 | 下推自动机(带栈) | 括号匹配、大多数编程语言语法 |
| Type 1 | 上下文相关语言 | 线性有界自动机 | 自然语言的一部分 |
| Type 0 | 递归可枚举语言 | 图灵机 | 一切可计算的 |

这个层级揭示了一个**非常重要的事实**:

> **正则语言是表达能力最弱的一层**。它**无法**描述"成对出现"的结构——比如"匹配任意深度的括号嵌套"、"匹配完整的 HTML"、"判断回文"。

这就是为什么 Stack Overflow 上有一个传奇答案:["You can't parse HTML with regex"](https://stackoverflow.com/a/1732454)——因为 HTML 是上下文无关语言(Type 2),需要带栈的下推自动机才能正确解析,而正则(Type 3)在数学上就**没这个能力**。任何用正则匹配 HTML 的尝试,都是在用一个数学上不够强的工具硬撑,迟早出错。

你应该把这条"能力天花板"刻进脑子:**正则只能匹配"非嵌套"的扁平模式**。一旦遇到需要"配对"和"嵌套"的结构,你需要的就是解析器,不是正则。

### **第 4 层:1968 年——Thompson 把正则带进计算机**

理论到这里已经很完整了,但还没人在计算机里**实现**它。

1968 年,**Ken Thompson**(后来的 Unix 之父之一,你在第一个问题里见过他)在 [Communications of the ACM](https://dl.acm.org/doi/10.1145/363347.363387) 发表了一篇论文 *"Regular Expression Search Algorithm"*,做了一件影响深远的工程:

> **他设计了一种算法,把任意正则表达式编译成 NFA,然后高效模拟这个 NFA,从而判断字符串是否匹配。**

这个算法后来被叫做 **Thompson 构造法**(Thompson's construction)。它的思路极其优雅:**递归地组合 NFA 片段**。

- 单个字符 `a`:两个状态,一个箭头。
- `AB`(连接):把 A 的接受态用 ε 连到 B 的初始态。
- `A|B`(并):新建一个起点,用 ε 同时连到 A 和 B 的起点。
- `A*`(星号):新建起点和终点,用 ε 互相连接,形成"可循环可跳过"的结构。

无论多复杂的正则,通过递归应用这四条规则,都能机械地构造出对应的 NFA。

更关键的是 Thompson 的**模拟策略**:不像传统 NFA 那样用回溯(走错路再退回来),而是**同时追踪所有可能的状态**——读入一个字符,就让"当前所有活跃状态"集体转移一步。

这个策略保证了一个梦寐以求的性质:

> **无论正则多复杂,匹配长度为 n 的字符串,时间复杂度都是 O(mn)**(m 是正则大小,n 是字符串长度)。**完全没有回溯,没有指数爆炸,没有正则灾难**。

Thompson 把这个算法写进了 1968 年的 QED 编辑器,然后又写进了 1973 年的 ed,然后……你已经知道了,就是 `g/re/p`,grep 诞生了。**正则表达式从此从学术界走向工业界**,而 Thompson 算法成了"做正则的正确方式"的黄金标准。

GNU grep、ripgrep、Go 的 `regexp` 包、Rust 的 `regex` crate——所有走"线性时间路线"的现代正则引擎,本质上都是 Thompson 算法的后代。

### **第 5 层:1986 年的岔路——Perl 与回溯式引擎**

如果故事到这里就结束,世界会简单很多。但 1986 年,事情拐了一个弯。

**Larry Wall** 创造了 Perl 语言。Perl 把正则表达式做成了语言的一等公民——直接写在代码里,无需调用函数,像这样:

```perl
if ($line =~ /(\w+)@(\w+\.com)/) {
    print "user: $1, domain: $2";
}
```

为了让正则"更好用",Perl 加入了很多 Thompson 的纯正则**无法表达**的特性:

| 新特性 | 例子 | 数学意义 |
|--------|------|---------|
| 反向引用 | `(\w+)\s+\1` 匹配"重复的单词" | **超越了正则语言!** |
| 环视(lookaround) | `(?=...)` `(?<=...)` `(?!...)` | 仍在正则能力内,但实现复杂 |
| 懒惰量词 | `.*?` | 改变匹配策略 |
| 命名捕获组 | `(?<year>\d{4})` | 工程便利 |
| 递归正则 | `(?R)` | **远远超越正则!** |

注意第一行:**反向引用** `\1` 让"正则表达式"不再是正则语言了!"两个相同的子串"在乔姆斯基阶梯里属于**上下文相关语言**(Type 1),理论上需要图灵机级别的能力才能识别。

为了实现这些特性,Perl 的正则引擎放弃了 Thompson 算法,改用**回溯式 NFA**(backtracking NFA):

> **遇到分支或量词,选一条路走;走不通,回退到分支点,换另一条路;再走不通,继续回退……**

这个策略**牺牲了 Thompson 的线性时间保证**,换来了表达力的爆炸式增长。后来 Perl 的正则语法被独立成了 **PCRE(Perl Compatible Regular Expressions)**,被 PHP、Python、Java、JavaScript、Ruby、.NET 等几乎所有主流语言采纳。

**这就是今天正则世界的大分裂**:

| 路线 | 引擎代表 | 表达力 | 时间保证 |
|------|---------|--------|---------|
| **Thompson 派**(NFA 模拟) | grep、ripgrep、Go regexp、Rust regex、RE2 | 严格的正则语言 | 严格 O(mn) |
| **回溯派**(Perl 风格) | PCRE、Python re、JS、Java、.NET | 超越正则语言 | 最坏指数级 |

### **第 6 层:ReDoS——回溯派的"原罪"**

回溯式引擎有一个非常危险的副作用,叫 **正则灾难**(catastrophic backtracking),工程上叫 **ReDoS**(Regular Expression Denial of Service)。

举个经典例子。正则 `(a+)+b`,用回溯引擎匹配字符串 `"aaaaaaaaaaaaaaaaaaaa!"`(20 个 a,没有 b):

引擎会尝试**所有可能的"分组方式"**——20 个 a 可以怎么分成多个 `a+` 的连接?
- (aaaaaaaaaaaaaaaaaaaa)
- (a)(aaaaaaaaaaaaaaaaaaa)
- (aa)(aaaaaaaaaaaaaaaaaa)
- (a)(a)(aaaaaaaaaaaaaaaaaa)
- ……

这个数量是 $2^{19}$,约 50 万次尝试。20 个 a 还好,**30 个 a 就是 10 亿次,40 个 a 就是 1 万亿次**——你的 CPU 会直接卡死。

**真实世界的案例**:
- **2016 年,Stack Overflow 全站宕机 34 分钟**,原因是一个用于裁剪空白的正则在某个 thread 上触发了 ReDoS。事故报告: [Outage Postmortem](https://stackstatus.tumblr.com/post/147710624694/outage-postmortem-july-20-2016)
- **2019 年,Cloudflare 全球服务中断 27 分钟**,原因是 WAF 规则里一条带嵌套量词的正则,在某个特定请求下走了几十亿次回溯,把全球边缘节点的 CPU 打满。事故报告: [Cloudflare Outage](https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/)

而 Thompson 派的引擎(ripgrep、Go、Rust)**在数学上不可能发生 ReDoS**——这是它们越来越受欢迎的根本原因之一。

### **第 7 层:正则的内部数据流——一次匹配到底发生了什么**

把上面所有抽象落到一次具体的匹配上,引擎做的事大致是:

**阶段 1:词法分析(Lexing)**
把正则字符串 `\d+@\w+\.com` 拆成 token 流:
```
\d  +  @  \w  +  \.  c  o  m
```

**阶段 2:语法分析(Parsing)**
构造**抽象语法树**(AST):
```
        Concat
       /  |  \  \  \  \
   Plus  @  Plus  \.  c  o  m
    |        |
   \d        \w
```

**阶段 3:编译(Compilation)**
把 AST 翻译成内部表示。Thompson 派翻译成 NFA(或继续转 DFA);回溯派翻译成一种**字节码**,由一个虚拟机执行。比如 RE2 的字节码长这样:
```
CHAR \d
SPLIT 0 → loop back, or → continue
CHAR @
...
```

**阶段 4:执行**
- **Thompson 派**:维护一个"当前活跃状态集合",读入字符就让所有状态集体转移一步,直到读完。状态集合大小有上限(NFA 状态数),所以时间线性。
- **回溯派**:递归地尝试每条路径,记录回溯点,匹配失败就回退。

**阶段 5:提取结果**
如果匹配成功,把捕获组对应的位置切出来返回。

这就是 `re.match("\d+@\w+\.com", "1@a.com")` 在 Python 内部一瞬间发生的事。

### **第 8 层:优化技巧——为什么 ripgrep 这么快**

现代正则引擎在算法骨架之上,还堆了大量**工程优化**。这些优化让"理论 O(mn)"在实际中变成"接近读取磁盘的速度":

**(1) 字面量提取(Literal Optimization)**
正则 `\bfn\s+(\w+)` 里,`fn` 是必定出现的字面量。引擎先用**专门为单字面量优化的扫描算法**(Boyer-Moore、SIMD memchr)在文本里飞快找 `fn`,只在候选位置才启动完整正则机器。

**(2) DFA 缓存**
NFA 模拟时,某些"活跃状态集合"会反复出现。引擎把"状态集合 → 下一个状态集合"的转移结果缓存起来,**等价于把 NFA 动态地转成了 DFA**,但只为热路径付出转换成本。RE2 和 Rust regex 都用了这招。

**(3) 多模式 + Aho-Corasick / Teddy**
搜索 `foo|bar|baz` 这种多个字面量备选时,引擎用 [Aho-Corasick 算法](https://en.wikipedia.org/wiki/Aho%E2%80%93Corasick_algorithm) 或 SIMD 加速的 Teddy,一次扫描同时匹配所有备选。

**(4) ASCII 快速路径**
`\w` 在 Unicode 下要考虑成千上万个字符,要查表;但如果引擎能推断输入是 ASCII,就直接用一张 128 字节的 bitmap 判断,快几十倍。

**(5) JIT 编译**
PCRE2、V8 的 Irregexp 引擎会把正则编译成**机器码**直接执行,跳过虚拟机开销。代价是编译时间,所以一般只对"会被用很多次"的正则做 JIT。

这些技巧叠加,就解释了为什么同一个正则在 ripgrep 里跑得飞快,在 Python `re` 里慢一截,在某个糟糕的 JS 实现里又能差几个数量级。

### **第 9 层:几个值得理解的常见构造**

回过头看你每天用的正则元素,套到上面的理论框架里:

| 写法 | 数学本质 | 引擎做的事 |
|------|---------|-----------|
| `a` | 单字符,自动机一条边 | 读一个字符,匹配比较 |
| `ab` | 连接,两个自动机串起来 | 顺序匹配两个字符 |
| `a\|b` | Kleene 的"并",分支 | NFA 两条分支,回溯派选一条试 |
| `a*` | Kleene star,环 | NFA 状态自环,可循环可跳过 |
| `a+` | `aa*` 的语法糖 | 至少一次的循环 |
| `a?` | `(a\|ε)` 的语法糖 | 二选一,其中一条是空 |
| `[abc]` | `a\|b\|c` 的高效写法 | 一张 bitmap/区间表 |
| `.` | "除换行外任意字符" | 一张大 bitmap |
| `\d` | `[0-9]`(或 Unicode 数字) | 同上,但表更大 |
| `^` `$` | 锚点,**不消耗字符** | 检查位置而非字符 |
| `(...)` | 捕获组 | 记录匹配位置区间 |
| `\1` | 反向引用 | **超越正则,引擎必须额外维护组内容** |
| `(?=...)` | 正向先行断言 | 在不消耗字符的前提下尝试匹配 |
| `*?` | 懒惰量词 | NFA 中"优先跳过"而非"优先循环" |

懒惰量词这个值得多说一句。`.*?` 和 `.*` 在**匹配的字符串集合**上**完全一样**,差别只在**匹配哪一个**(最长 vs 最短)。这说明懒惰量词不是"另一种正则",而是同一个正则下的**不同搜索策略**——纯粹是工程层面的事。

### **第 10 层:一个完整的小例子,把所有层穿起来**

我们拿你天天写的邮箱正则 `[\w.]+@[\w.]+\.\w+` 当例子,完整过一遍:

**数学层面**:这是一个正则语言,描述"一段单词字符或点,然后 @,然后一段单词字符或点,然后点,然后一段单词字符"。

**NFA 层面**:Thompson 构造法把它编译成大约 10\~15 个状态的 NFA。`[\w.]` 是一个字符类,对应一组并行边;`+` 引入一个回环;`@` 是单边;`\.` 也是单边。

**引擎层面**:
- ripgrep / Go regexp:用 NFA 模拟 + DFA 缓存,线性扫描你的日志文件,毫秒级返回所有匹配。
- Python re / JS:回溯引擎。这个正则没有嵌套量词,不会触发 ReDoS,但如果你写成 `([\w.]+)+@...`,在某些边界字符串下就可能爆炸。
- Rust regex:可能用 Teddy 算法找 `@` 字符当锚点(它是唯一的字面量),只在含 `@` 的窗口附近启动正则机器。

**理论局限**:这个正则**远远无法**真正验证邮箱合法性,RFC 5322 定义的合法邮箱地址需要一个**完整的解析器**——包括允许引号、注释、嵌套括号等等。所以"邮箱正则"在工程上永远是个**近似品**,这是正则语言能力天花板的体现。

### **回到顶层:一句话总结这趟旅程**

> **正则表达式是 1943 年神经科学家发明的、1951 年被数学家代数化、1956 年被语言学家归类、1968 年被 Thompson 工程化、1986 年被 Perl 扩展(并污染)、2010 年代被 RE2/ripgrep 重新现代化的一种"用字符串描述字符串集合"的语言;它在乔姆斯基阶梯上属于最弱的一层,所以它快、它可判定、它能被自动机模拟——但也因此它永远无法解析嵌套结构;今天主流的两大实现路线(Thompson 派 vs 回溯派)之间的选择,本质是"线性时间 vs 表达力"的工程权衡。**

下次你敲下 `\d+`、看到代码 review 里同事说"别用正则解析 HTML"、或者收到一个 ReDoS 安全告警,你应该已经知道它们各自指向上面这条 80 年技术长河里的哪个节点了。从 1943 年那张神经元图,到你今天写的 `^[a-z]+$`,中间是一条连续的、清晰的、几乎每一步都可以追溯到具体论文的演化路径——这在计算机科学里是非常罕见的、近乎艺术品级别的整洁。
