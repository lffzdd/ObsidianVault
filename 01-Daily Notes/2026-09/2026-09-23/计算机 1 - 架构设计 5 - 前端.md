到了最容易让人精神分裂的 **第 4 关：前端流派里的 `container` 和它的亲戚们**。

很多后端转前端、或者刚学前端的同学，看到 `containers` 这个词瞬间就懵了：“这玩意儿跟 Docker 容器有什么关系？还是放什么东西的箱子？”

其实，它跟 Docker 毫无关系。它是前端架构史上一个非常著名的设计模式：
**“聪明组件与傻瓜组件”（Smart vs Dumb Components）**。

---

### 一、痛点：前端工程师遇到的灾难

假设你在做一个电商网页，需要做一个 **“商品卡片”**：
卡片上有图片、价格、标题，还有一个【加入购物车】的按钮。

如果初学者来写，通常会把所有东西全写在一个文件里：
1. 自己写 HTML 和 CSS 样式；
2. 自己写 `fetch('/api/cart/add')` 去调后端接口；
3. 自己判断如果报错了弹个提示框。

**灾难发生了：**
下周产品经理说：“我们在‘后台管理系统’和‘用户收藏夹’里，也要用一模一样的商品卡片样式，但是点击按钮不要加购物车，而是‘下架商品’或者‘取消收藏’。”

你傻眼了：**你的卡片和“加购物车”的接口死死绑定在一起了，样式根本没办法复用！**

---

### 二、破局：把人分成“模特”和“经纪人”

为了解决这个问题，React 社区（Dan Abramov）提出了著名的容器模式，把前端代码彻底拆成两拨：

```text
src/
├── components/   <-- 【傻瓜组件 / 展示组件 (Presentational)】
└── containers/   <-- 【聪明组件 / 容器组件 (Container)】
```

它们的分工非常清晰：

#### 1. `components/`（只负责美貌的“模特”）
* **特点**：**没脑子，没有感情**。
* **它做什么**：
  * 只管 **HTML 结构和 CSS 样式**，长得好不好看全看它。
  * **绝不允许自己在里面调 API 接口**，绝不允许直接读全局 Store。
  * 它的数据必须全靠外部像喂饭一样（通过 `props` / 参数）喂给它。
  * 用户点了按钮，它自己不处理，只喊一声：“有人点我了！”（触发回调函数）。
* **代码感觉**：
  ```tsx
  // components/ProductCard.tsx
  // 它就是个纯 UI 外壳，谁给它数据，它就展示谁
  export function ProductCard({ title, price, onBtnClick }) {
    return (
      <div className="card">
        <h3>{title}</h3>
        <p>¥{price}</p>
        <button onClick={onBtnClick}>点击操作</button>
      </div>
    );
  }
  ```

---

#### 2. `containers/`（幕后运筹帷幄的“经纪人”）
* **特点**：**有脑子，但不管长相**。
* **它做什么**：
  * 它几乎**没有自己的 CSS 样式**，自己不画复杂的 UI。
  * 它负责**动脑子**：去调后端的 API 查数据、处理报错、管理 State 状态。
  * 数据拿到后，它把数据打包塞给 `components/` 里的“模特”去展示。
* **代码感觉**：
  ```tsx
  // containers/ShopProductContainer.tsx
  // 它负责业务：查接口、定行为
  export function ShopProductContainer() {
    const [data, setData] = useState(null);

    // 1. 负责从后端拉数据
    useEffect(() => { api.getGoods().then(setData); }, []);

    // 2. 负责定义按钮的具体动作（加购物车）
    const handleAddCart = () => { api.addToCart(data.id); };

    // 3. 把数据和动作，喂给纯展示组件
    return <ProductCard title={data.name} price={data.price} onBtnClick={handleAddCart} />;
  }
  ```

> 💡 **妙处在哪？**
> 明天在收藏夹里想复用这个卡片时，你只需要再写一个新的 `FavoriteContainer`，按钮动作改成“取消收藏”，而 `ProductCard` 这个 UI 组件一行代码都不用改！

### 三、演进：为什么有些现代项目看不到 `containers/` 了？

你现在去看一些最新的 React / Vue 项目，可能会发现：咦，怎么没有 `containers/` 目录了？

这是因为前端后来又演进了一步：

1. **改叫 `views/` 或 `pages/`**：
   大家发现，绝大部分的“容器组件”其实就是一个完整的**页面**（比如 `pages/OrderPage.tsx`）。所以很多团队把 `containers/` 直接重命名为了 **`pages/`** 或 **`views/`**，本质角色完全一样。
2. **有了 Hooks（组合式函数）**：
   现在可以把拉取数据、按钮逻辑写成一个 `useCart()` Hook，直接塞进页面里，不用专门套一层 Container 类了。

但无论名字怎么换，**前端工程的核心骨架依然是这套逻辑**：

```text
src/
├── pages/ (或 views/, 早期叫 containers/)  # 【大脑】页面级组件：管数据流、调 API
├── components/                           # 【颜值】通用纯 UI 组件：按钮、弹窗、卡片
├── hooks/ (Vue叫 composables/)           # 【抽离的逻辑】把状态和 API 逻辑单独打包
├── services/ (或 api/)                   # 【网络通信】专门发 Axios / Fetch 请求
└── store/                                # 【全局内存】存放全应用共享的状态（登录信息等）
```

### 回顾你的最初疑惑

现在再回头看你最开始问的那几个词：
* `domain`：**后端 DDD 的灵魂**（纯业务规则与充血实体）
* `service`：**后端的业务流程经办人**（或者前端封装的 API 请求层）
* `base` / `core`：**横向技术底座**（面向对象的继承基类 vs 系统级启动骨架）
* `container`：**前端的大脑组件**（负责拉数据、给 UI 模特喂饭）
