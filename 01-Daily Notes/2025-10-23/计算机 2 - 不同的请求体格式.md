# 不同的请求体

这个截图展示的是在 Postman 或 Hoppscotch 里常见的 **HTTP Body 类型选项**。

每个选项对应的是 HTTP 请求体（Body）的**编码方式**——也就是客户端（你）怎么把数据“打包”发给服务器。

这些选项其实是历史演化的痕迹：

它们反映了 Web 从“HTML 表单”到“API 通信”再到“结构化协议”的演变。

我们可以从「为什么有这些方式」→「各自怎么工作」→「现代怎么选」三个层面来讲。

---

## 一、为什么会有不同的 Body 类型

在最初的 Web 时代，浏览器只会发两种形式的数据：

1. 用户填写网页 `<form>` 表单；
2. 浏览器自动提交它。

于是 W3C 规定了两种表单提交格式：

- **application/x-www-form-urlencoded**：最传统，最基础；
- **multipart/form-data**：为上传文件而生。

后来，随着 Ajax、JSON、API 出现，开发者开始绕开表单，直接用脚本发任意格式的请求，于是又有：

- **raw（原始数据）**：纯文本、JSON、XML、任意字符串；
- **binary（二进制流）**：直接传文件内容；
- **GraphQL**：一种专门的查询语言格式。

所以你看到的这些选项，其实对应了「HTTP 请求体格式的演化史」。

---

## 二、每种类型的含义与底层结构

### 1. **none**

顾名思义：没有请求体。

常用于 `GET`、`DELETE` 请求。

请求行和 header 里已经包含足够信息，不需要 body。

---

### 2. **form-data（multipart/form-data）**

这是**表单上传模式**，通常用于“带文件上传”的 POST 请求。

每个字段都带有边界标识（boundary），比如：

```pgsql
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryX
```

请求体结构类似：

```pgsql
------WebKitFormBoundaryX
Content-Disposition: form-data; name="username"

william
------WebKitFormBoundaryX
Content-Disposition: form-data; name="avatar"; filename="pic.png"
Content-Type: image/png

<二进制文件内容>
------WebKitFormBoundaryX--
```

特点：

- 可同时传文本字段和文件；
- 结构清晰、但体积较大；
- 主要用于网页表单或文件上传接口。

---

### 3. **x-www-form-urlencoded**

这是**最经典的表单格式**，在 HTML `<form>` 默认就是这种。

格式类似 URL 的查询参数，只不过放在请求体中：

```pgsql
Content-Type: application/x-www-form-urlencoded
```

请求体：

```pgsql
username=william&password=123456&age=30
```

特点：

- 纯文本；
- 易解析；
- 不支持文件；
- 常见于老式接口、OAuth 登录、支付回调等。

可类比成“POST 版的 query string”。

---

### 4. **raw**

这是现代 API 最常用的格式，因为它可以直接传 JSON。

常配合：

```pgsql
Content-Type: application/json
```

请求体：

```json
{
  "username": "william",
  "password": "123456"
}
```

特点：

- 结构清晰；
- 支持嵌套、数组；
- 适合 RESTful API；
- 便于服务器自动解析。

现在几乎所有现代后端框架默认支持 JSON body（Express、Django、Spring Boot 等）。

---

### 5. **binary**

这是“直接发原始文件内容”的方式，没有额外包装。

比如上传图片、PDF、音频时，Body 就是一整个二进制流。

对应的 header 通常是：

```pgsql
Content-Type: application/octet-stream
```

服务器收到后直接保存成文件，自己决定怎么处理。

常用于文件接口、云存储上传。

---

### 6. **GraphQL**

GraphQL 是 Facebook 设计的一种 API 查询语言，用 POST 请求发 JSON：

```json
Content-Type: application/json
```

请求体：

```json
{
  "query": "{ user(id: 1) { name, email } }"
}
```

特点：

- 用结构化查询语言替代 REST；
- 前端可以一次请求多个资源；
- 服务器端根据 query 返回精确字段。

在 Hoppscotch 里，这个选项其实就是帮你自动设置好 header 和格式。

---

## 三、如何选择合适的类型（现代实践）

|目的|推荐类型|原因|
|---|---|---|
|上传文件|`form-data`|支持多部分上传|
|普通表单（登录、注册）|`x-www-form-urlencoded`|与浏览器表单兼容|
|RESTful 接口（JSON 数据）|`raw`（JSON）|清晰、现代、可嵌套|
|发送二进制文件流|`binary`|最简洁高效|
|GraphQL 接口|`GraphQL`|框架规定格式|
|GET/DELETE 请求|`none`|不带 body|

---

## 四、小结逻辑线

- 早期 Web：`x-www-form-urlencoded` 与 `form-data` 是为表单用户设计的；
- API 时代：`raw (JSON)` 取代表单，成为主流；
- 文件传输仍靠 `form-data` 或 `binary`；
- 新体系（GraphQL）在上层定义自己的格式。

可以说，每种 Body 类型都是某个“时代的语言”：

> `x-www-form-urlencoded` 属于浏览器时代，
> `raw (JSON)` 属于 API 时代，
> `GraphQL` 属于 Schema 时代。

# 不同请求体的处理

这是一个非常关键的理解点。你问得很准：

当我们在请求中指定不同的 `Content-Type` 时，**到底是谁改变了行为**？

是“内容格式不同”那么简单，还是“浏览器和服务器在底层都做了不同封装和解析”？

答案是：

> **“内容不同”只是表层结果，真正不同的是——客户端和服务器在编码（封装）与解码（解析）层面都根据 `Content-Type` 的规范改变了行为。**

我们从底层数据流的角度，一步步讲清楚。

---

## 一、HTTP 本身只是“信封”，`Content-Type` 告诉收件人“里面是什么”

HTTP 协议对 Body 的态度非常开放：

它就像一个邮局信封，只管帮你送信，但不懂信的内容。

真正决定“内容怎么包装、收件人怎么读”的，是 `Content-Type`。

比如：

```mermaid
Content-Type: application/json
```

就相当于信封上写着“这是一封 JSON 信”；

浏览器和服务器据此决定：

- 发送前要把对象序列化成 JSON；
- 接收后要把字节流反序列化成对象。

---

## 二、浏览器端：编码方式确实会变化

以浏览器或 Postman 为例，不同 `Content-Type` 会触发不同的**封装逻辑**。

### 1. `application/x-www-form-urlencoded`

浏览器会自动把键值对序列化成：

```mermaid
key1=value1&key2=value2
```

再进行 URL 编码（空格→`+`，特殊符号→`%XX`）。

示例：

```js
fetch(url, {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({ name: 'William', age: 20 })
})
```

生成的请求体是纯文本：`name=William&age=20`。

浏览器自动封装，不需要你手动转字符串。

---

### 2. `multipart/form-data`

浏览器或 Postman 会为你：

- 生成随机的“边界字符串”（boundary）；
- 在每个字段前后插入 `--boundary` 分隔；
- 对文件字段加上 `filename`、`Content-Type`；
- 自动在 header 里加上：

	```mermaid
    Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryabc123
    ```

这一切都是浏览器帮你完成的“封装”逻辑。

你只要写：

```js
const form = new FormData();
form.append('name', 'William');
form.append('file', fileInput.files[0]);
fetch(url, { method: 'POST', body: form });
```

浏览器就会自动构造复杂的二进制请求体。

---

### 3. `application/json`

浏览器不会帮你自动处理对象，必须**手动序列化**：

```js
fetch(url, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'William', age: 20 })
})
```

否则 Body 就会变成 `[object Object]` 之类的错误数据。

封装上，这种类型最简单：纯文本 JSON。

---

### 4. `application/octet-stream`

这表示你直接上传原始二进制流。

浏览器不会包裹任何结构，也不会加边界。

Body 就是裸的文件内容。

---

## 三、服务器端：解码逻辑也完全不同

服务器在收到请求后，并不会“自动理解” Body。

它要看 `Content-Type` 决定用什么解码器（parser）。

### 1. `application/x-www-form-urlencoded`

框架会用解析器拆成键值对：

```mermaid
name=William&age=20
→ { name: "William", age: "20" }
```

在 Express、Flask、Django 等框架中，这通常映射为 `req.body`。

---

### 2. `multipart/form-data`

服务器会扫描 `boundary`，逐段提取出字段名、文件内容、类型。

文件会被暂存到磁盘或内存中，其它字段作为表单字段解析。

框架会暴露成：

```js
req.files['avatar']
req.body['username']
```

解析器内部其实做了流式边界识别，非常复杂。

---

### 3. `application/json`

服务器会读取整段字节流，然后用 JSON 解析器反序列化：

```mermaid
"{\"name\":\"William\",\"age\":20}"
→ { name: "William", age: 20 }
```

如果内容不是合法 JSON，就会抛错。

---

### 4. `application/octet-stream`

服务器不会解析，直接把字节流交给开发者处理（保存文件、转码等）。

---

## 四、所以回答你的问题：

|内容|浏览器封装方式|服务器解码方式|本质区别|
|---|---|---|---|
|`x-www-form-urlencoded`|自动序列化键值对并编码|解析成键值对对象|表单式文本编码|
|`multipart/form-data`|自动加边界和文件描述|分段解析文件与字段|混合多部分格式|
|`application/json`|需手动 JSON.stringify|JSON.parse|结构化文本|
|`application/octet-stream`|直接发二进制|直接读字节流|原始流数据|

所以不是“封装都一样只是内容不同”——

而是**Content-Type 决定了客户端的编码规则和服务器的解析策略**，两端都要遵守同一个 MIME 协议规范，否则就会出现“收发不匹配”。

---

## 五、总结一句话

> HTTP 不关心内容，但浏览器和服务器会根据 `Content-Type` 改变它们的“打包和拆包逻辑”。

如果两端对 Content-Type 的理解不一致，就像一个寄信人寄了“外语信”，收信人不会读——

服务器就只能报错：“Unexpected token” 或 “Unsupported Media Type”。
