### 一、 核心痛点：HTTP 的“裸奔”时代

在 HTTPS 普及之前，互联网主要使用的是 **HTTP (HyperText Transfer Protocol)**。

#### 1. 原理层面的缺陷

HTTP 是**明文传输**协议。如果把网络通信比作寄信：

- **HTTP 就像寄明信片**：信件内容（密码、信用卡号）写在背面，邮递员（路由器）、分拣员（运营商）、甚至路人（黑客）在传输过程中都能一眼看到。
- **三大安全风险**：
    
    1. **窃听 (Eavesdropping)**：第三方可以截获并阅读通信内容。
    2. **篡改 (Tampering)**：第三方可以修改内容（例如在你下载的软件中插入病毒，而你毫不知情）。
    3. **冒充 (Impersonation)**：你以为你在访问 Google，但实际上连到了黑客搭建的假基站，HTTP 无法验证对方身份。

为了解决这些底层安全问题，**HTTPS (HTTP Secure)** 应运而生。简单来说：**HTTPS = HTTP + SSL/TLS（加密层）**。

### 二、 历史与发展：从 Netscape 到全网加密

了解历史能帮我们理清 SSL 和 TLS 的关系。

#### 1. 史前时代与 SSL 的诞生 (1994)

- **背景**：90 年代初，随着电商（如亚马逊）萌芽，网上支付的安全问题迫在眉睫。
- **诞生**：网景公司 (Netscape) ——当时的浏览器霸主，设计了 **SSL (Secure Sockets Layer)** 协议。
    - **SSL 1.0**：因存在严重漏洞从未公开发布。
    - **SSL 2.0 (1995)**：随 Netscape Navigator 1.1 发布，但很快被发现有缺陷。
    - **SSL 3.0 (1996)**：这成为了后续现代加密协议的基础架构。

#### 2. 标准化与 TLS 的接棒 (1999 - 2008)

互联网工程任务组 (IETF) 介入，不希望标准被一家公司（Netscape）垄断，于是将协议更名为 **TLS (Transport Layer Security)**。

- **TLS 1.0 (1999)**：本质上就是 SSL 3.1，只是换了个名字。
- **TLS 1.1 (2006) & TLS 1.2 (2008)**：修补了大量安全漏洞，引入了更强的加密算法（如 AES）。**TLS 1.2** 统治了互联网长达十年之久。

#### 3. 现代加密与斯诺登效应 (2013 - 至今)

- **转折点**：2013 年爱德华·斯诺登曝光“棱镜计划”，显示在此之前，很多流量虽被窃取但因加密未被破解。这促使科技巨头（Google, Apple, Mozilla）推动“HTTPS Everywhere”。
- **TLS 1.3 (2018)**：这是最新、最激进的一次升级。它砍掉了所有旧的、不安全的算法，大幅减少了握手时间（速度更快），是目前的黄金标准。

> **注意**：虽然现在技术上用的是 TLS，但大家习惯上还是统称 SSL 证书或 SSL/TLS。

### 三、 底层原理：HTTPS 是如何工作的？

HTTPS 的核心在于它在 TCP 和 HTTP 之间加了一层 **SSL/TLS 层**。这层做了三件大事：**加密**、**身份验证**、**完整性校验**。

它是如何做到的？这涉及三个关键的密码学概念：

#### 1. 对称加密 (Symmetric Encryption) —— “速度快”

- **原理**：只有一把钥匙，加密和解密都用它。
- **问题**：我要怎么把这把钥匙安全地发给你？如果发钥匙的过程中被截获，加密就白费了。

#### 2. 非对称加密 (Asymmetric Encryption) —— “解决传钥匙问题”

- **原理**：有两把钥匙，**公钥 (Public Key)** 和 **私钥 (Private Key)**。
    - 公钥大家都可以拿。
    - 私钥只有你自己有。
    - **魔法在于**：用公钥加密的东西，只有私钥能解开；用私钥加密的东西，公钥可以验证。
- **用法**：客户端用服务器的**公钥**加密“对称密钥”，发给服务器。服务器用**私钥**解开。这样，双方就安全地拥有了同一把“对称密钥”。

#### 3. 数字证书 (Digital Certificates) —— “证明你是你”

- **问题**：如果黑客把你原本想发给 Google 的请求截获了，并发给你黑客自己的公钥，你用了黑客的公钥加密数据，黑客就能解密。这就是**中间人攻击 (MITM)**。
- **解决**：我们需要一个权威机构 (**CA**, Certificate Authority) 来做担保。
    - 服务器把自己的公钥给 CA。
    - CA 用自己的私钥给这个公钥盖个章（签名），生成**证书**。
    - 你的浏览器内置了权威 CA 的公钥，能验证这个章是不是真的。如果是真的，说明这个服务器的公钥是可信的。

### 四、 交互流程：TLS 握手 (Handshake)

当你在浏览器输入 `https://www.example.com` 时，背后发生了如下过程（以 TLS 1.2 为例）：

1. **Client Hello**：浏览器告诉服务器：“我支持 TLS 1.2 和 1.3，我有这些加密算法，咱们聊聊？”
2. **Server Hello**：服务器回答：“好，那咱们用 TLS 1.2，选用这个算法。”同时，服务器把它的**数字证书**发给浏览器。
3. **验证证书**：浏览器检查证书是否由受信任的 CA 签发？有没有过期？域名对不对？（如果不对，浏览器就会弹红框警告）。
4. **密钥交换**：
    
    - 浏览器生成一个随机密码（预主密钥）。
    - 浏览器用证书里的**公钥**加密这个密码，发给服务器。
        
5. **生成会话密钥**：服务器用自己的**私钥**解密，拿到了随机密码。现在，双方都有了同一个密码。
6. **加密通信**：之后的 HTTP 请求（HTML, 图片, JSON 数据）全部用这个共享密码进行**对称加密**传输。

_(注：TLS 1.3 优化了这个流程，把上述步骤合并，减少了一次往返 RTT，速度更快。)_

### 五、 总结与现状

|**特性**|**HTTP**|**HTTPS**|
|---|---|---|
|**安全性**|明文，极易被窃听|加密，防窃听、防篡改|
|**端口**|80|443|
|**性能**|理论上稍快（无握手）|现代硬件下差异几乎可忽略，且支持 HTTP/2 速度更快|
|**SEO**|搜索引擎权重低|Google 优先收录，权重更高|

为什么要用 HTTPS？

除了安全，现代 Web 的高级功能（如 HTTP/2 多路复用、PWA Service Workers、获取地理位置、麦克风权限等）强制要求必须在 HTTPS 环境下才能运行。
