# 拼图模式

- ? epoll 要等到有事件就绪才继续运行,这是阻塞,运行就绪的事件时读写 io 可以设置为非阻塞?但是这里我有点没看明白,读写 io 设置为非阻塞意味着没读出数据也继续,但是还有数据没传过来呢,如果继续下一步那接下来到的数据怎么办

这个问题问到了异步/非阻塞编程中最让初学者头疼的一个核心难点：**“数据的不连续性”与“应用层缓冲（Application Buffering）”**。

你的担心非常合理：如果我读了一半，发现没数据了（`EAGAIN`），程序继续往下跑去干别的事了，那剩下的一半数据来了怎么办？会不会丢？

答案是：**绝对不会丢，但你需要换一种写代码的思路——“拼图模式”。**

---

### 1. 核心误解：read 并不是“读完”才返回

在传统的阻塞模式下，我们习惯了这种逻辑：

> “我要读 1000 字节，读不到 1000 字节你就别回来。”

在非阻塞（Non-blocking）模式下，逻辑变成了：

> “有多少给多少。如果现在只有 100 字节，你就先给我 100。剩下的我下次再来拿。”

所以，剩下的数据去哪了？

它们还在网线上，或者正在排队进入操作系统的内核缓冲区。只要你没读走，它们就会安安全全地待在那里，或者由 TCP 协议保证重传。

---

### 2. 怎么处理“断断续续”的数据？

既然数据是一块一块到的，你的程序就不能指望一次 `read` 就能拿到完整的 HTTP 请求或完整的 JSON 包。

你需要引入一个中间层：**应用层缓冲区（User Space Buffer）**。

#### 场景模拟：你在下载一个 2MB 的图片

1. **第一次 Epoll 唤醒：**
    
    - Epoll 说：“Socket A 有数据来了！”
    - 你调用 `read`（非阻塞）。
    - 系统给你 10KB 数据，然后返回 `EAGAIN`（没货了）。
    - **你的动作：** 你把这 10KB 存入你自己定义的变量 `buffer_A` 中。**你不进行业务处理**（因为图片还不完整），你直接退出当前函数，回到主循环。
        
2. **回到主循环 (While True)：**
    
    - 你继续调用 `epoll_wait`。
    - 此时，你可以去处理 Socket B、Socket C 的请求。
    - _这就是非阻塞的意义：等待 Socket A 剩余数据的空档期，你在服务别人。_
        
3. **第二次 Epoll 唤醒：**
    
    - 过了 100ms，Socket A 的后半截数据到了。
    - Epoll 再次告诉你：“Socket A 又有数据了！”
    - 你再次调用 `read`。
    - 这次拿到了 50KB。
    - **你的动作：** 把这 50KB **追加（Append）** 到 `buffer_A` 的屁股后面。
        
4. **检查完整性：**
    
    - 每次读完，你都要检查 `buffer_A`：“现在够 2MB 了吗？”
    - 如果够了 -> **开始处理业务**（解析图片、存盘等），清空 buffer。
    - 如果不够 -> **继续回主循环等**。

---

### 3. 代码逻辑对比

为了看清区别，我们对比一下伪代码：

#### A. 阻塞模式（简单，但容易卡死）

C

```
// 假设我们要读取固定的 100 字节
char buf[100];
// 这一行会死等，直到凑够 100 字节才往下走
// 如果网络卡顿，整个线程就卡在这里 10 秒
read(fd, buf, 100); 

process(buf); // 处理业务
```

#### B. 非阻塞 + Epoll 模式（拼图模式）

这是一个循环状态机的过程：

C++

```
// 全局映射：每个连接都有自己的“半成品”缓存
map<int, string> user_buffers; 

void handle_event(int fd) {
    char temp_buf[1024];
    
    // 1. 尝试读取数据 (非阻塞)
    while (true) {
        int n = read(fd, temp_buf, sizeof(temp_buf));
        
        if (n > 0) {
            // A. 读到了数据：存起来！
            user_buffers[fd].append(temp_buf, n);
        } 
        else if (n == -1 && errno == EAGAIN) {
            // B. 暂时没数据了：
            // 不要傻等！立刻停止读取。
            break; 
        }
        else {
            // 出错或连接断开
            close(fd); return;
        }
    }

    // 2. 检查数据是否完整 (比如检查是否包含 \n 或者定长包头)
    if (check_complete(user_buffers[fd])) {
        // C. 拼图完成！处理业务
        process(user_buffers[fd]);
        user_buffers[fd].clear(); // 清空，准备接下一个请求
    } else {
        // D. 还没完？那就什么都不做
        // 函数结束，回到 epoll_wait 去等下一波数据
        return; 
    }
}
```

### 4. 关键点解答：接下来到的数据怎么办？

你问：“如果继续下一步那接下来到的数据怎么办？”

回答：

当你因为 EAGAIN 退出 read 函数后，你的程序回到了 epoll_wait 的主循环。

- **接下来的数据**（比如网络的后半截包）到达网卡后，操作系统会把它们存入内核缓冲区。
- **然后**，操作系统发现这个 Socket 变为了“可读”状态。
- **接着**，`epoll_wait` 会**再次**返回，告诉你这个 fd 有新事件。
- **最后**，你的代码会**再次**进入 `handle_event`，把剩下的数据读出来，拼接到之前的 buffer 后面。

### 5. 总结

非阻塞 IO 的核心哲学是：**“积少成多，绝不空等”。**

- **不会丢数据：** 还没读的数据由操作系统替你保管。
- **代价：** 你的代码变复杂了。你不能写流水账了，你必须维护一个 **Context（上下文/缓冲区）** 来记录每个连接“读到哪儿了”。

这就像**在线看视频**：

- **阻塞：** 必须等整个电影下载完（100%），播放器才开始播。
- **非阻塞：** 缓冲了 1%，播放器就开始播这 1%。播完了如果后面还没下载好，就转圈圈（等待 Epoll 唤醒），下载好了继续接着播。

# 判断拼图完成

这个问题直击了网络编程中最容易被忽视、但又最重要的概念：**应用层协议设计（Application Layer Protocol Design）**。

简单直接的回答是：

操作系统（内核）和 TCP 协议完全不知道什么叫“拼图完成”。只有你自己（程序员）和你制定的“协议规则”知道。

这涉及到 TCP 的本质：**TCP 是“流式”协议（Stream Oriented），不是“包”协议。**

### 1. 为什么会有这个问题？（自来水管比喻）

想象 TCP 连接是一根**自来水管**。

- **发送端**：把数据（像水一样）灌进去。
- **接收端**：拿着杯子（Buffer）去接水。

你接了一杯水，这杯水是属于“第一条消息”的？还是“第二条消息”的？还是“第一条的一半加上第二条的一半”？

水管（TCP）不负责告诉你这些。 水管只保证水没漏、顺序没乱。

你需要自己设计一套规则，来判断“水”流到什么时候算是一次完整的“灌溉”。这就叫**“拆包/粘包”处理**。

---

### 2. 只有四种方法判断“拼图完成”

在工业界，判断数据接收完毕（消息边界）通常只有以下四种通用方案：

#### 方案一：特殊符号分隔（Delimiter Based）

**规则：** 只要读到某个特定的字符（比如换行符 `\n`），就认为这一段结束了。

- **例子：** 简单的聊天室、SMTP（邮件协议）、FTP、**HTTP 的 Header 部分**。
- **应用逻辑：**
    
    C++
    
    ```
    // 每次 read 完，都去遍历 buffer
    if (buffer.find("\n") != string::npos) {
        // 找到了！拼图完成！
        string message = buffer.substr(0, position_of_newline);
        buffer.erase(0, position_of_newline + 1); // 删掉已处理的
    }
    ```
    
- **缺点：** 如果你的数据内容里刚好也有 `\n` 怎么办？（需要转义，比较麻烦）。

#### 方案二：固定长度（Fixed Length）

**规则：** 规定每一条消息必须正好是 100 字节。

- **例子：** 一些银行的老旧系统、硬件传感器数据。
- **应用逻辑：**
    
    C++
    
    ```
    if (buffer.size() >= 100) {
        // 够了！切出前 100 个字节
        process(buffer.substr(0, 100));
    }
    ```
    
- **缺点：** 极其不灵活。数据只有 5 个字节也要补 0 凑够 100，浪费带宽。

#### 方案三：头部定长 + 长度字段（Length Field Based / TLV） —— **最推荐**

这是最专业、最高效的做法。

规则： 消息分为两部分：[包头] + [包体]。

- **包头：** 固定长度（比如 4 字节），里面存一个整数，告诉后面包体有多长。
- **包体：** 实际数据。

例子：

假设你要发送 "Hello"。

1. 先算 "Hello" 长度是 5。
2. 发送数据流：`0005` (头) + `Hello` (体)。

**接收端逻辑（拼图逻辑）：**

C++

```
// 假设 buffer 是应用层的缓存 string/vector
void check_and_process(string& buffer) {
    while (true) {
        // 第一步：先看头部够不够（假设头部是用 4 字节存长度）
        if (buffer.size() < 4) {
            return; // 连长度都不知道，继续等 epoll 读数据吧
        }

        // 第二步：解析头部，获取“包体长度”
        // 假设前4个字节转成 int 是 body_len
        int body_len = parse_header(buffer.substr(0, 4));

        // 第三步：看 buffer 剩下的数据够不够 body_len
        if (buffer.size() < 4 + body_len) {
            return; // 还没传完，继续回 epoll 等剩下的拼图
        }

        // 第四步：终于够了！切包！
        string complete_msg = buffer.substr(4, body_len);
        process(complete_msg); // 业务处理

        // 第五步：从 buffer 里把这坨已处理的数据删掉
        buffer.erase(0, 4 + body_len);
        
        // 循环继续，因为 buffer 里可能粘着下一条消息的一部分
    }
}
```

#### 方案四：关闭连接（EOF）

**规则：** 只要连接断开了（read 返回 0），就说明数据发完了。

- **例子：** HTTP 1.0 的短连接模式（服务器发完网页直接断网）。
- **缺点：** 每次只能发一条消息，发完就得重连，效率低。

---

### 3. 一个具体的“拼图”案例

假设你用 方案三（长度头）。

你需要接收一个 2000 字节的数据包。头部占 4 字节，写着 2000。

1. **Epoll 第一次唤醒：**
    
    - 你 read 到了 `1000` 字节。
    - **检查：** buffer 有 1000 字节。
    - **解析：** 前 4 字节说总长要是 2004 字节。
    - **判断：** 1000 < 2004。拼图未完成。
    - **动作：** 退出，回 `while` 循环继续 `epoll_wait`。
        
2. **Epoll 第二次唤醒：**
    
    - 你 read 到了 `1500` 字节（剩下的 1004 字节 + 下一条消息的 496 字节，这就叫**粘包**）。
    - **追加：** buffer 现在有 1000 + 1500 = 2500 字节。
    - **检查：** 需要 2004 字节。
    - **判断：** 2500 >= 2004。**拼图完成！**
    - **动作：**
        
        1. 切下前 2004 字节处理业务。
        2. buffer 剩下 496 字节（这是下一条消息的头部和一部分）。
        3. 再次循环逻辑，检查这 496 字节是不是又够一条新消息了（显然不够，继续等）。

### 总结

- **Epoll 只管搬运：** 它只负责把网线上的比特流搬到内存里，不负责解释含义。
- **协议定义边界：** 你必须在代码里写死一种规则（比如“前 4 字节是长度”）。
- **While 循环检查：** 每次读完数据，都要去检查你的 Buffer 符不符合那条规则。

这就是为什么写高性能网络框架（如 Netty, Muduo, Golang net）难的地方，不仅要搞定 Epoll，还得写一套健壮的**Buffer 管理和拆包算法**。
