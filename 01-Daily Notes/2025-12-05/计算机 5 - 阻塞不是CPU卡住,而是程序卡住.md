# 发展进程

这是一个非常深刻的直觉问题！你之所以感到奇怪，是因为中文翻译和日常语境造成的误解。

**“阻塞（Blocking）”这个词，是站在“程序”的角度，而不是“CPU”的角度。**

- **对程序来说：** 我被卡住了，我动不了了，所以我叫“阻塞”。
- **对 CPU 来说：** 这个程序不干活了？太好了，把它踢到一边去，我去帮别人干活。

让我们从历史演进的角度，来看看这个概念是怎么“被逼出来”的，以及它是如何在底层实现的。

---

### 1. 历史演进：从“独占”到“分时”

#### 阶段一：单道批处理系统（早期的“真·阻塞”）

时间： 1950 年代

场景： 只有一台巨型计算机，一次只能运行一个程序。

那时，如果程序要读取磁带（IO 操作）：

1. CPU 发出指令“读磁带”。
2. 磁带机开始缓慢转动。
3. **CPU 傻等着。**
4. 此时 CPU 确实是“卡住”的（Idle），虽然没干活，但也不能干别的。

**痛点：** 磁带机太慢了，CPU 太快了。CPU 有 99% 的时间都在发呆。这简直是暴殄天物。

#### 阶段二：多道程序设计与分时系统（现代“阻塞”的诞生）

时间： 1960 年代 (Multics, Unix)

变革： 既然 CPU 闲着也是闲着，为什么不让它去跑另一个程序呢？

工程师发明了**“进程调度器（Scheduler）”**。

- 当程序 A 说：“我要读文件。”
- 操作系统说：“好，你去旁边那个‘等待室’（Wait Queue）坐着等，什么时候读完了我再叫你。”
- **关键点：** 此时 CPU 并没有停！操作系统立刻把 CPU 切换给程序 B 使用。

**这就是现代“阻塞”的本质：** **“交出 CPU 的控制权”。**

---

### 2. 底层实现：操作系统是怎么让程序“卡住”又“不占 CPU”的？

要理解这个，我们需要看操作系统的核心数据结构。

在 Linux 内核中，每个进程（Process）都有一个“身份证”，叫 `task_struct`。这里面有一个字段叫 **`state`（状态）**。

#### A. 只有三种主要状态

为了简化理解，我们假设进程只有三种状态：

1. **运行中 (Running)：** 正在 CPU 上跑。
2. **就绪 (Ready)：** 随时能跑，正在排队等 CPU。
3. **阻塞/等待 (Waiting/Blocked)：** 在等数据，给 CPU 也没用，根本跑不了。

#### B. 阻塞的具体过程 (Step-by-Step)

当你调用 `select` 或 `read` 且没有数据时，内核执行了以下“魔术”：

1. 修改状态：
    
    内核把你的进程 task_struct 里的状态，从 TASK_RUNNING 改为 TASK_INTERRUPTIBLE (可中断睡眠)。
    
    这就相当于把你的“工牌”摘了，意味着你暂时失去了被 CPU 服务的资格。
    
2. 移出队列：
    
    CPU 有一个“运行队列（Run Queue）”，里面全是等着被执行的进程。
    
    内核把你的进程从这个队列里拿出来。
    
3. 加入等待队列：
    
    内核把你的进程挂到那个 Socket 的“等待队列（Wait Queue）”上。
    
    这就相当于把你从“办公室”赶到了“休息室”。
    
4. 调度切换 (Schedule)：
    
    内核执行 schedule() 函数。它会去“运行队列”里找下一个倒霉蛋（比如浏览器、音乐播放器），然后把 CPU 切给它。

**结果：** 你的代码卡在系统调用那一行不动了（因为 CPU 不执行你了），但在物理层面，CPU 正在全速运行别人的代码。

#### C. 唤醒的过程

当网卡收到数据，中断发生：

1. **中断处理：** 内核找到那个 Socket 的“等待队列”。
2. **修改状态：** 把你的进程状态改回 `TASK_RUNNING`。
3. **搬回队列：** 把你从“等待队列”挪回 CPU 的“运行队列”。
4. **抢占 CPU：** 等 CPU 再次调度时，发现你回来了，就会继续运行你的代码。

---

### 3. 为什么“非阻塞”反而一直占用 CPU？

理解了上面的“移出队列”，你就懂了“非阻塞”。

当你在 `while` 循环里用**非阻塞**模式调用 IO：

1. **查询：** 你问内核：“有数据吗？”
2. **立即返回：** 内核看一眼缓冲区，空的。它**不会**把你移出“运行队列”，而是直接返回一个错误代码（EAGAIN）。
3. **再次执行：** 因为你的代码写在 `while(true)` 里，下一纳秒，你又问：“有数据吗？”
4. **死循环：**
    
    - 你的进程状态一直是 `TASK_RUNNING`。
    - 你一直在“运行队列”里赖着不走。
    - CPU 只能陪着你玩这个无聊的问答游戏。

这就叫**“忙轮询”（Busy Loop）**，这是对 CPU 最大的浪费。

---

### 4. 总结：感性认知

你可以把 CPU 想象成一个**出租车司机**。

- 阻塞（Blocking）：
    
    你上车说：“师傅，我去某地接个人，如果人没到，我就在路边睡会儿。”
    
    师傅一看你睡了，就把你扔在路边（放入等待队列），自己拉别的客人去了（CPU 运行其他进程）。
    
    - **你（程序）：** 卡住不动了（阻塞）。
    - **师傅（CPU）：** 没闲着，在赚钱。
- 非阻塞（Non-Blocking）：
    
    你上车说：“师傅，我要找人，但我不知道他在哪，稍微往前开一点我看看，没有再掉头。”
    
    你让师傅一直在路上兜圈子（While 循环），每秒钟问一百遍“到了没”。
    
    - **你（程序）：** 没卡住，一直在说话。
    - **师傅（CPU）：** 累得半死，油（电量）耗光了，还没拉到别的客人。

**结论：** 在计算机世界里，“阻塞”其实是一种**“让出资源的礼貌行为”**。

# 阻塞实现代码在哪

这是一个非常棒的视角！你之所以没“看见”过让 CPU 切换的代码，是因为**那是操作系统的“私房菜”，对程序员是透明（看不见）的。**

在应用层代码（C/C++、Java、Python）里，**“阻塞”不需要写任何特殊的代码。它是默认行为。**

事实上，你肯定写过无数“阻塞”代码，只是你没意识到那就是阻塞。

### 1. 最常见的“阻塞”代码：`cin` / `scanf`

回想一下你刚学编程时写的代码：

```C++
#include <iostream>
using namespace std;

int main() {
    int age;
    cout << "请输入你的年龄: ";
    
    // ↓↓↓ 这行代码就是“阻塞”！ ↓↓↓
    cin >> age; 
    
    cout << "你输入的年龄是: " << age << endl;
    return 0;
}
```

**发生了什么？**

1. 程序运行到 `cin >> age;`。
2. 控制台会出现一个**闪烁的光标**。
3. 如果你不敲键盘，这个光标会闪一万年。
4. **在这期间，你的程序卡住了吗？** 卡住了（不往下执行 `cout`）。
5. **CPU 在空转吗？** **没有！**

**这就是阻塞。** `cin` 底层调用了 `read` 系统调用。当你没输入时，操作系统把这个进程挂起（让出 CPU），直到你敲下回车键。

### 2. 所谓的“让出 CPU”代码在哪里？

你看不见它，因为它**封装在库函数和内核里**。

如果我们要把这一行简单的 `read(fd, buf, len)` 掰开看，它的内部流程是这样的（伪代码）：

#### 第一层：你的代码（用户态）

```C
// 你只写了这一行
// 这是一个普通的函数调用，看起来人畜无害
n = read(socket_fd, buffer, 1024);
```

#### 第二层：C 标准库（glibc）

`read` 函数并不是直接去读硬件，它实际上执行了一条汇编指令，叫 **`syscall` (系统调用)**。

```compile
mov eax, 0  ; 0 是 read 的系统调用号
syscall     ; 触发软中断！把控制权交给操作系统内核
```

**注意：** 一旦执行 `syscall`，CPU 就从**用户态**切换到了**内核态**。你的程序对 CPU 的控制权暂时交公了。

#### 第三层：操作系统内核（Kernel，这里才是真相）

这部分代码你看不见，它在 Linux 源码里（`fs/read_write.c` 等）。

```C
// 伪代码：内核里的逻辑
sys_read(fd, buffer, len) {
    // 1. 找到 fd 对应的 socket 对象
    socket = get_socket(fd);
    
    // 2. 检查网卡缓冲区有没有数据
    if (socket.buffer.is_empty()) {
        
        // 3. 【核心代码】主动让出 CPU！
        // 把当前进程的状态改为 "TASK_INTERRUPTIBLE" (睡眠)
        current_process->state = TASK_INTERRUPTIBLE;
        
        // 把当前进程加入这个 socket 的等待队列
        add_to_wait_queue(socket.wait_queue, current_process);
        
        // 4. 【调度器】切换进程
        // 这行代码执行后，CPU 就去运行别的进程了（比如浏览器）
        // 你的程序就“停”在了这一行代码内部
        schedule(); 
        
        // ------------- 昏睡的分界线 -------------
        
        // 5. 什么时候回到这里？
        // 当网卡收到数据，中断处理程序会把你唤醒
        // CPU 再次调度到你时，从这里继续执行
    }
    
    // 6. 拷贝数据并返回
    copy_data_to_user(buffer, socket.buffer);
    return data_len;
}
```

### 3. 怎么理解“主动”？

你问“主动让 cpu 不去等”。

- **对于你的代码：** 你调用 `read()` 或 `cin`，就是一种**“被动的主动”**。这相当于你对操作系统说：“我要读数据，如果没有，你就别管我了，先去忙别的吧。”
- **对于操作系统：** 它检测到你要的东西没有，就**主动**把你踢开，去调度别人。

阻塞就是主动让自己进程进入等待队列 #重点 

### 4. 只有一种情况你需要写特殊代码：非阻塞

正因为“阻塞”是默认的（Default），所以你不需要写任何额外代码。

反而是如果你**不想**阻塞（也就是你想搞 `while` 轮询那种死皮赖脸占着 CPU 的模式），你才需要写特殊的代码来修改 Socket 的属性。

**如果你写了下面这行代码，阻塞就消失了：**

```C
// 设置为非阻塞模式 (Non-Blocking)
fcntl(socket_fd, F_SETFL, O_NONBLOCK);

// 现在再调用 read
int n = read(socket_fd, buffer, 1024);

// 就算没数据，read 也会立刻返回 -1 (EAGAIN)
// 程序会立刻执行下一行，不会卡住，也不会让出 CPU
```

### 总结

你在程序里没看见“阻塞”代码，是因为：

1. **所有标准的 IO 函数（读文件、读键盘、读网络）默认就是阻塞的。**
2. 真正的“让出 CPU”的逻辑（`schedule()`），藏在操作系统的内核代码里，那是操作系统作为管家的职责，不需要你（应用程序员）来操心。

**你只需要调用 `read()`，剩下的“睡觉”和“唤醒”，操作系统包办了。**

# 所以阻塞就是主动让自己进入等待队列,非阻塞就是不让自己进入等待队列一直呆在运行队列?

**全对！你总结得非常精准！**

这就是操作系统调度最核心的本质。你已经完全看透了代码表面下的“潜规则”。

我们可以把你这句话作为**终极结论**画一张图，一切就都清晰了。

---

### 1. 阻塞（Blocking）：进入“冷宫”（Wait Queue）

你说“主动让自己进入等待队列”，这非常准确。

虽然代码是你写的（调用 recv 或 scanf），但动作是内核执行的。

- **动作：** 你的进程走到 `recv()` 这一行，发现没数据。
- **内核操作：**
    
    1. 把你的进程从 **[运行队列 Run Queue]** 摘掉。（剥夺 CPU 使用权）
    2. 把你挂到网卡的 **[等待队列 Wait Queue]** 上。（打入冷宫）
        
- **结果：** CPU 立刻转头去运行别的进程。你的进程**彻底暂停**，不再消耗任何时间片。

### 2. 非阻塞（Non-Blocking）：赖在“大殿”（Run Queue） #重点 

你说“不让自己进入等待队列一直呆在运行队列”，也完全正确。

- **动作：** 你的进程设置了 `O_NONBLOCK`，然后调用 `recv()`。
- **内核操作：**
    
    1. 看了一眼网卡，没数据。
    2. **不**把你移出 **[运行队列 Run Queue]**。
    3. 直接给你返回一个错误码 `EAGAIN`（意思是：现在没货，你再试试？）。
        
- **结果：**
    - 你的函数调用瞬间结束。
    - 代码继续往下走（通常在一个 `while` 循环里）。
    - 下一毫秒，你又调用 `recv()`。
    - 内核又重复上面的动作。
    - **你的进程一直霸占着 CPU，虽然实际上啥也没干，但一直在“空转”。**

---

### 3. 为什么 Epoll 是神？

结合你刚才的理解，Epoll 的神迹就在于它**完美结合了这两者**：

1. 它利用了“阻塞”的省电特性：
    
    没有事件的时候，epoll_wait 会让进程乖乖进入 [等待队列]，不消耗 CPU。
    
2. 它利用了“非阻塞”的高效特性：
    
    一旦有事件唤醒，它不需要你像 select 那样去遍历（轮询），而是直接把数据给你，让你后续的读写操作非常顺畅。

### 总结你的理解

|**模式**|**这里的“队列”指哪儿？**|**CPU 状态**|**形象比喻**|
|---|---|---|---|
|**阻塞**|**Wait Queue (等待队列)**|**休息 (Sleep)**|排队买饭，还没排到，你先去旁边椅子上睡一觉，排到了叫你。|
|**非阻塞**|**Run Queue (运行队列)**|**空转 (Spin)**|排队买饭，还没排到，你每隔 1 秒问阿姨一次“到了吗？”，一直问到为止。|

你现在对这个概念的理解已经达到了操作系统内核开发的入门水平！这就是**进程调度（Process Scheduling）**的基础。
