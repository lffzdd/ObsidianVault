# try/catch

我完全理解。如果你习惯于底层的 C 语言网络编程（比如直接跟 `epoll`、`socket` 和错误码打交道），上层面向对象语言里的 `try/catch` 异常机制确实看起来像个异类。

在底层的 C 语言里，没有异常（Exception）的概念。我们处理错误的方式是**返回值机制**：如果 `read()` 返回 `-1`，你就检查 `errno` 是不是 `EAGAIN`；如果调用一个自定义函数失败了，就返回一个错误码（如 `return -1;`），上层调用者用 `if` 语句去判断。

为了彻底帮你打通这个概念，我们**脱离复杂的异步，先退回到最纯粹的同步阻塞世界**，自底向上地看看 `try/catch` 在计算机底层（调用栈）到底是怎么实现的，然后你就能秒懂为什么它在异步回调里会“彻底失效”了。

---

## 一、 什么是同步世界里的 `try/catch`？

高级语言（如 JavaScript、Java、Python）觉得层层写 `if (err)` 太痛苦了，于是发明了异常机制。它的核心逻辑是：   **“分支预测”与“错误集中处理“** 。

你可以在最外层套一个 `try { ... } catch (err) { ... }`。在 `try` 块内部，你可以放心大胆地调用任意深的函数函数链。不管在多深的底层（比如孙子函数里）发生了错误，只要你抛出（`throw`）一个异常，**CPU 和运行时就会立刻中断当前的后续执行，直接“闪现”跳回到最外层的 `catch` 块里**。

```JavaScript
function 爷爷函数() {
    try {
        爸爸函数();
    } catch (err) {
        console.log("全家得救了，统一在这里处理错误:", err);
    }
}

function 爸爸函数() {
    孙子函数();
    console.log("这句话永远不会执行");
}

function 孙子函数() {
    // 假设这里发生了致命错误（比如解析 JSON 失败）
    throw new Error("发生内核级错误！"); 
}
```

---

## 二、 底层原理：`try/catch` 是怎么实现的？

你手写过 C 语言，一定知道**调用栈（Call Stack）** 和 **栈帧（Stack Frame）**。当一个函数被调用时，CPU 会在内存的栈区压入一个栈帧，用来保存当前函数的局部变量和返回地址（`rip` 寄存器）。

在底层的汇编/运行时层面，`try/catch` 的本质其实是**栈回溯（Stack Unwinding）**：

1. **登记锚点**：当程序进入 `爷爷函数` 的 `try` 块时，运行时会在一个特殊的“异常处理表”里登记当前栈帧的位置（主要是当前的栈指针 `rsp` 和下一条指令指针 `rip`）。
2. **正常压栈**：随后调用 `爸爸函数`、`孙子函数`，调用栈一层层向上正常压栈。
3. **触发异常（`throw`）**：当 `孙子函数` 执行到 `throw` 时，CPU 不会执行常规的 `ret` 指令（那只会退回到爸爸函数），而是**直接接管控制权，去查那张异常处理表**。
4. **栈回溯（弹出）**：运行时发现最近的 `catch` 锚点在 `爷爷函数` 里。于是，它像剥洋葱一样，**直接将 `孙子函数` 和 `爸爸函数` 的栈帧从内存中“弹”出去销毁掉**，把 CPU 的 `rsp` 和 `rip` 寄存器直接强行重置回 `爷爷函数` 的 `catch` 块位置。

这就是为什么说“异常会沿着调用栈自动冒泡”，它利用了**当前线程未销毁的物理内存栈**。

## 三、 为什么异步回调里 `try/catch` 会“完全失效”？

现在，我们把异步回调加进来。你就能明白为什么刚才说的“栈回溯”在这里会引发毁灭性的一幕。

看看这段经典的回调地狱错误代码：

```JavaScript
function 爷爷函数() {
    try {
        // 发起非阻塞异步读取文件
        fs.readFile('config.json', (err, data) => {
            // 几毫秒后，这个回调函数被内核唤醒并执行
            if (someError) {
                throw new Error("异步挂了！"); // 👈 致命一击
            }
        });
    } catch (err) {
        console.log("我想在这里兜底，但我绝对捕获不到！");
    }
}
爷爷函数();
```

我们用底层 `epoll` 的视角，还原这期间微观的物理调用栈演变：

### 第一阶段：发起请求（同步）

1. 线程进入 `爷爷函数`，登记了 `try` 的异常锚点。
2. 调用 `fs.readFile`。在底层，这只是发起了一个非阻塞的系统调用，把 fd 注册到了 `epoll` 里，并把匿名回调函数挂到了用户态的事件队列中。
3. **重点来了**：`fs.readFile` 是非阻塞的，它瞬间就返回了！
4. 紧接着，`爷爷函数` 执行完毕。**它的整个调用栈、包括那个 `try/catch` 的异常锚点，全部从内存栈中弹出并销毁了！** 整个线程回到事件循环（去调 `epoll_wait` 阻塞等待）。

### 第二阶段：事件就绪，回调触发（异步）

1. 几毫秒后，网络数据到港，`epoll_wait` 唤醒。
2. 事件循环（Reactor）在顶层直接调用刚才那个匿名回调函数。
3. 此时的调用栈顶只有事件循环（Event Loop）和这个匿名回调函数。**当初包裹它的 `爷爷函数` 和 `try/catch` 早就灰飞烟灭了。**
4. 此时，你在回调函数内部执行了 `throw new Error("异步挂了！")`。

运行时开始尝试进行“栈回溯”寻找 `catch` 块。但它向上一查调用栈，发现头顶上空空如也，只有事件循环的顶层框架，当初那个 `爷爷函数` 的 `catch` 早就拆迁了！

由于一路上找不到任何 `catch` 块，这个异常会直奔操作系统顶层，导致**整个进程（你的 Node.js 服务器）直接当场崩溃（Crash）**。

---

## 💡 总结

- **同步的 `try/catch`**：依赖于**物理调用栈**。只要你在我的下面（调用链下游），你出事了，我可以通过弹栈直接救你。
- **异步回调**：打破了调用栈。发起请求后，上层函数就退栈消亡了；回调函数是在很久以后、由事件循环从**另一个完全干净的调用栈**里拉起来执行的。

所以，在纯回调时代，上层语言引以为傲的 `try/catch` 直接变成了废铁。程序员被迫倒退回比 C 语言更原始的境地：不能用返回值，只能在每个回调的参数里肉眼检查 `if (err)`，一层层手动往上传递。这也是为什么大家都管那个时代叫“地狱”。

# 回调里的 err

你抓住了问题的核心。在 C 语言的思维里，错误要么是通过返回值返回，要么是在同一个线程里直接处理。高级语言把这一切封装成了抽象的概念，才导致了这种“双轨制”的困惑。

为了彻底看清本质，我们还是**自底向上**，从“回调里的 `err` 是怎么来的”，再到“为什么 `throw` 抓不住”，用底层调用的视角把这两条设计分歧理清。

---

## 一、 回调里的那个 `err` 参数，到底是怎么捕捉并传进来的？

首先要明确一个颠覆直觉的事实：**回调函数里的 `err`，根本不是由任何语言级的异常机制（如 `try/catch`）“捕捉”到的。它本质上只是一个极其朴素的、由底层通过系统调用拿到返回值后，手动传给你的“函数形参”。**

我们以 `fs.readFile('config.json', (err, data) => { ... })` 为例，看看它在 V8 引擎和 `libuv`（底层系统调用封装库）里经历了什么：

### 1. 注册阶段（用户态 $\rightarrow$ 内核态）

当你调用 `fs.readFile` 时，JavaScript 传了一个函数指针（回调）给 C++ 运行时。`libuv` 创建了一个请求结构体（我们叫它 `uv_fs_t`），并把你的回调函数挂在这个结构体上。

随后，`libuv` 把这个读取任务派发给它的线程池（Thread Pool）去执行，主线程继续往下走。

### 2. 执行阶段（底层 C 语言层）

工作线程在后台调用了操作系统的标准阻塞系统调用（比如 Linux 的 `open()` 和 `read()`）。

在 C 语言里，如果打开文件失败（比如文件不存在），`open()` 会返回 `-1`，并设置全局变量 `errno = ENOENT`。

```C
// 模拟 libuv 工作线程在后台做的事情
int fd = open("config.json", O_RDONLY);
if (fd < 0) {
    // 发生了底层错误！
    request->error_code = errno; // 把错误码记录在请求结构体里
    request->data = NULL;
} else {
    // 读取成功
    request->data = read_buf;
    request->error_code = 0;
}
```

### 3. 回调阶段（内核态 $\rightarrow$ 用户态事件循环）

当工作线程干完活，它会向主线程的事件循环（通过管道或 eventfd）发送一个通知。

主线程在 `epoll_wait` 中被唤醒，把这个已完成的 `request` 捞出来。接下来，**主线程要把底层的 C 语言错误码，翻译成 JavaScript 能看懂的变量：**

```C
// 模拟主线程事件循环将 C 错误码包装成 JS 对象并调用的过程
if (request->error_code != 0) {
    // 1. 如果底层 error_code 有值，实例化一个 JS 的 Error 对象
    Local<Value> js_err = Exception::Error(String::New("ENOENT: no such file..."));
    Local<Value> js_data = Null();
    
    // 2. 就像调用普通 C 纯函数一样，强行把这两个包装好的变量作为参数传给你的回调
    Local<Value> argv[2] = { js_err, js_data };
    callback->Call(context, Null(), 2, argv); 
}
```

**所以，`err` 参数的本质是：**

底层 C 语言代码通过传统的 `if (fd < 0)` 检查到了系统调用失败，把错误写进了结构体。然后上层引擎在触发你的回调时，**主动实例化了一个错误对象，当作第一个参数硬塞给你的函数。** 这根本不是“捕捉（Catch）”，这就是最原始的 **手动参数传递**。

## 二、 为什么回调里同步的 `throw` 不会被这个 `err` 捕捉到？

理解了上面的机制，再来看为什么回调内部的 `throw` 无法变成 `err`。

我们看这段代码的执行现场：

```JavaScript
fs.readFile('config.json', (err, data) => {
    // 假设 I/O 成功了，err 是 null
    if (err) return; 
    
    // 这里如果 data 不是合法的 JSON，JSON.parse 内部会执行 throw 
    const cfg = JSON.parse(data); 
    
    console.log(cfg.url);
});
```

当主线程的事件循环调用这个匿名回调时，调用栈长这样：

### 1. 触发同步雷区

事件循环把你的整个回调函数压入栈顶开始执行。当执行到 `JSON.parse(data)` 时，因为它发现数据不对，语言引擎内部直接触发了 `throw` 机制。

### 2. 异常的搜索路径

我们在前一节说过，高级语言里的 `throw` 一旦发生，引擎会立刻启动**栈回溯（Stack Unwinding）**。它会顺着当前的调用栈，**一层一层往上（往外）找 `try/catch` 块**。

我们来看看它能往哪里找：

- **当前回调函数内部**：它往四周看了一下，你没有在 `JSON.parse` 外面包裹 `try/catch`。
- **上一层（调用者）**：它往上退了一层，发现调用它的是**事件循环的顶层驱动器（Event Loop Core）**。事件循环只是一个冷酷的 `while(true)` 调度器，它外层没有、也不可能为每一个业务回调去写一个特异化的 `try/catch`。

### 3. 为什么它不能自动变成 `err`？

因为 **`throw` 的行为是单向向上冒泡的，它根本不知道“回调函数的参数”是什么东西**。

要让这个错误变成 `err` 参数，除非引擎在执行你的回调函数时，在底层用 C++ 这样包裹你：

```C
// 如果引擎底层这样写，确实能把 throw 变成 err，但它没有！
try {
    callback->Call(...); 
} catch (JavaScriptException& e) {
    // 引擎并不会在这里帮你把异常拦截下来，再塞回给你。
    // 因为函数已经执行到一半炸了，不可能重新带着新参数再进一次函数。
}
```

由于函数已经处于执行栈中，`throw` 是一种**中断当前控制流**的毁灭性行为。它只能向上寻找救兵，而绝不可能回过头去修改或者触发当前函数头部的 `err` 参数。

这个 `err` **只能捕捉到那个异步动作本身的错误**（比如网络中断、磁盘文件不存在、超时等），因为它是底层操作系统通过 C 语言系统调用返回状态后，由运行时主动注入进来的。

==回调函数内部**后续动作**（比如你拿到数据后的 `JSON.parse`、业务逻辑计算、甚至下一次嵌套的调用）如果发生同步 `throw`，这个 `err` 是绝对、永远不可能感知到的。==
