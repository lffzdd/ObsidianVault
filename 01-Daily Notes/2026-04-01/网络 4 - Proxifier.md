你提出的这两个问题，可以说是触及了网络代理架构中最核心的“魔法”与“冲突”。能想到这一层，说明你不仅已经完全掌握了前两层（应用层协议、网络层路由）的运作机制，还开始进行跨层的逻辑推演了。

我们依然用**自底向上**的方式，先拆解 Proxifier 的底层黑科技，再推演 Proxifier 遇到 TUN 模式时到底会发生什么。

### 第一部分：Proxifier 是怎么强迫“不老实”的应用走代理的？

你之前的理解非常准确：系统代理（环境变量/注册表）是“防君子不防小人”，应用不主动去看，它就失效了。

Proxifier 之所以能成为代理界的“神器”，正是因为它**根本不指望应用去读环境变量**。它使用的是一种更加底层的流氓手段（也是杀毒软件和外挂常用的技术）：**API Hook（API 钩子）**。

#### 1. 历史背景与底层原理：Winsock (Windows Sockets)

在 Windows 操作系统中，任何一个应用程序（不管是老实的浏览器，还是不老实的游戏）想要上网，最终都**必须**调用操作系统提供的网络编程接口，这就是著名的 **Winsock API**（通常封装在 `ws2_32.dll` 等系统库中）。

程序想要建水管，必须调用系统底层函数，比如：

- `socket()`：创建套接字。
    
- `connect()`：连接目标 IP 和端口。
    
- `send() / recv()`：发送和接收数据。
    

#### 2. Proxifier 的“狸猫换太子”

当你启动 Proxifier 并设置好规则后，它会在操作系统底层做这样一件极其硬核的事：**DLL 注入与函数拦截（Hooking）。**

1. **注入：** Proxifier 会把自己的代码（一个特制的 `.dll` 文件）强行注入到你电脑上正在运行的（或即将运行的）目标程序进程中。
    
2. **拦截：** 它把目标程序内存里的那个系统原装的 `connect()` 函数给“劫持”了，替换成了 Proxifier 自己写的 `My_connect()` 函数。
    

#### 3. 欺骗的艺术

现在，一个“不老实”的游戏运行了。它完全无视系统代理，准备直接连接自己的海外服务器（比如 `8.8.8.8`）。

1. 游戏调用 `connect(目标: 8.8.8.8)`。
    
2. 因为函数被 Hook 了，这个调用实际上执行的是 Proxifier 的代码。
    
3. Proxifier 的代码一看：“哦，你要连 8.8.8.8 啊。稍等。”
    
4. **核心伪装：** Proxifier 在后台悄悄地向你的代理内核（`127.0.0.1:7897`）发起连接，并**代替这个游戏**完成了我们上一轮讲过的 SOCKS5 握手（“请帮我连 8.8.8.8”）。
    
5. 管道建好后，Proxifier 会给游戏返回一个信号：“报告老大，`8.8.8.8` 连接成功！”
    

**从头到尾，游戏根本不知道代理的存在。** 它以为自己连上了 `8.8.8.8`，实际上它发出的所有数据，都被 Proxifier 偷偷包裹进了 SOCKS5 协议，转交给了 `127.0.0.1:7897`。这就是为什么 Proxifier 能强制所有软件走代理的底层真相。

### 第二部分：世纪大撞车 —— Proxifier 遇上 TUN 模式

现在，高潮来了。你的电脑里同时存在两个“霸权主义者”：

- **Proxifier：** 在应用层（Layer 7）通过 API Hook 拦截程序的网络请求，强制把它们转成发往 `127.0.0.1:7897` 的 SOCKS5 数据。
    
- **TUN 模式：** 在网络层（Layer 3）篡改操作系统的全局路由表，强行把发往外网的 IP 包吸入虚拟网卡。
    

**当它们同时开启时，数据包是怎么走的？是走 SOCKS5 还是走 TUN？**

答案是：**它们会发生“堆叠”（Stacking），并且顺序是严格的——先过 Proxifier，再过 TUN 路由表。**

我们来推演一下一个包裹（数据包）的奇幻漂流：

#### 阶段一：在应用内部（Proxifier 拦截）

1. 你的应用想访问 Google (`142.250.x.x`)。
    
2. Proxifier 瞬间拦截，把目的地**篡改**为 `127.0.0.1` 的 `7897` 端口，并将原始请求包装成 SOCKS5 格式。
    
3. 此时，从应用进程里流出来的数据包，**它的目标 IP 已经不再是 Google 了，而是 `127.0.0.1`。**
    

#### 阶段二：进入操作系统底层（TUN 接管）

1. 这个目标为 `127.0.0.1` 的包裹，被扔给了操作系统的网络栈，来到了**路由表**。
    
2. 此时，TUN 模式的规则开始生效。
    
3. 接下来发生的事情，完全取决于你的 TUN 模式底层配置文件（`.yaml`）写得对不对：
    

**结局 A：TUN 配置正确（绕过了本地回环）**

- 路由表一看：“这个包是去 `127.0.0.1` 的。TUN 虚拟网卡的霸王条款里写了 `skip-proxy: 127.0.0.1`，所以不归 TUN 管。”
    
- 包裹顺利通过 `lo`（本地回环接口），抵达代理内核（7897 端口）。
    
- **结论：** 流量**实质上走了 SOCKS5**。TUN 模式在这个过程中虽然开着，但被完美绕过，毫无建树。
    

**结局 B：TUN 配置有 Bug（没有绕过本地回环）**

- 路由表一看：“霸王条款规定，所有的包统统进虚拟网卡！”
    
- 这个已经被 Proxifier 伪装成 SOCKS5、准备发给 `127.0.0.1` 的包裹，被无情地吸入了 `tun0`。
    
- 代理内核从 `tun0` 收到这个包裹，一看：“怎么会从外部网卡收到一个发往我自己内部端口的 SOCKS5 请求？”
    
- **结论：** 触发安全机制，连接被拒绝。也就是你之前遇到的那个 `1008 reason=connect failed` 报错的翻版。
    

### 总结

- **Proxifier 是一种位于更高维度（进程内存级别）的劫持。** 它在数据包变成 IP 包进入网卡之前，就已经把它们变成了目标为本地代理的 SOCKS5 流量。
    
- **如果你用了 Proxifier，TUN 模式其实就失去了意义**（对于被 Proxifier 代理的软件而言）。因为到了 TUN 发挥作用的路由表层面，所有的外部流量都已经被 Proxifier “洗”成了内部流量（`127.0.0.1`）。
    

这也是为什么在网络极客的圈子里有一个潜规则：**“不要同时混用 Proxifier 和 TUN 模式”**。它们在解决同一个问题（强制全局代理），同时开启只会增加路由死循环和协议冲突的风险。
