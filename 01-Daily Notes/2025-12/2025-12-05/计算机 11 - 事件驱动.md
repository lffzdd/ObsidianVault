# 什么是事件驱动

### 1. 关键角色

| **步骤**       | **真实的事件驱动 (Reactor 模式)**                                                            |
| ------------ | ----------------------------------------------------------------------------------- |
| **1. 发起任务**  | 主进程向内核**“注册”**感兴趣的事件（`epoll_ctl`）。<br><br>  <br><br>_(并不是丢进队列，而是贴个便利贴告诉内核：这事儿归你盯梢)_ |
| **2. 等待**    | 主进程调用 `epoll_wait` **阻塞/挂起**（或者设置短暂超时）。<br><br>  <br><br>_(没错，主进程在这里休息)_            |
| **3. 谁在干活?** | **内核（硬件中断）负责接收数据。<br><br>  <br><br>_(对于网络 IO，不需要别的进程，网卡和内核就搞定了)_                     |
| 4. 通知        | 内核把就绪的事件放入就绪列表**，`epoll_wait` 返回。                                                   |
| **5. 处理**    | 主进程拿到事件，**亲自**调用回调函数处理业务。                                                           |

#### 角色分配：

- **你（主进程/Event Loop）：** 餐厅里**唯一**的一个服务员。
- **顾客（Socket）：** 连接上来的客户端。
- **厨师（Kernel/OS）：** 负责准备食物（准备数据）的人。

#### 流程演示： #重点 

1. 注册（Registration）：
    
    顾客 A 进来了，点了一份牛排。
    
    你（服务员）并没有去厨房煎牛排（因为那样你就阻塞了）。
    
    你只是对着厨房（内核）喊了一嗓子：“顾客 A 要牛排，做好了叫我！”
    
    （这叫==非阻塞调用== + 注册 epoll 事件）
    
2. 循环（Looping）：
    
    喊完这一嗓子，你立刻转头去接待顾客 B、顾客 C。
    
    如果没有新顾客，你就在出餐口稍微眯一会儿（==epoll_wait 阻塞等待==）。
    
    （这就叫 Event Loop）
    
3. 触发（Trigger）：
    
    厨房里的牛排煎好了（数据通过网卡到了内核缓冲区）。
    
    厨师按了一下铃（中断 -> 就绪链表）。
    
    （这就是“事件就绪”）
    
4. 回调（Callback）：
    
    你听到铃声，醒了过来。
    
    你一看出餐口，标签上写着“顾客 A”。
    
    你端起牛排送到顾客 A 的桌子上（执行 read 读取数据，并运行对应的业务逻辑代码）。
    
    （这就是执行回调函数）

### 3. 代码视角的事件驱动

所谓的“事件驱动”，在代码里其实就是**一个死循环 + 一堆回调函数**。

```Python
# 伪代码：极其简化的事件驱动模型

# 1. 定义一堆“收到信后该干嘛”的函数（回调）
def on_connect(socket):
    print("有人连上来了！")
    # 注册：我想读这个 socket 的数据
    epoll.register(socket, READ_EVENT, on_data_arrive)

def on_data_arrive(socket):
    data = socket.read() # 非阻塞读
    print("读到数据：", data)
    # 处理业务...

# 2. 只有这一个主循环 (Event Loop)
while True:
    # A. 这里的 wait 是阻塞的，为了省 CPU
    # 只有当有事发生（有人连接、有数据到）才会醒来
    active_events = epoll.wait() 

    # B. 醒来后，挨个处理发生的事情
    for event in active_events:
        # C. 这里的 callback 就是上面的 on_connect 或 on_data_arrive
        # 主进程亲自去执行这些函数！
        event.callback(event.socket)
```

### 4. 你的疑惑点解答

> **你觉得：“主进程先将事件丢进等待队列...”**

**纠正：** 不是主进程丢进去的。主进程只是**注册**。是**操作系统内核**在数据到达时，把这个事件“生成”并放进了就绪队列。

> **你觉得：“然后某个进程完成事件...”**

纠正： 对于网络 IO，没有“某个进程”。是硬件（网卡）和操作系统内核在默默干活。主进程只需要等结果。

(注：只有在处理本地磁盘 IO 这种特殊情况，Nginx 才会用到线程池，那才符合你说的“别的进程完成事件”。)

> **你觉得：“主进程在 while 中轮询事件是否完成...”**

**纠正：** 这里的轮询不是“每隔一秒问一次”，而是“一直睡，有事才醒，醒了就处理一堆”。这叫**Reactor（反应堆）模式**——被动地对事件做出反应。

### 总结

**事件驱动的核心就是：**

1. **我（主进程）不干重活**（不负责等数据，也不负责读磁盘）。
2. **我只负责“分发”**（Dispatcher）。
3. **所有重活都外包**给内核（Kernel）或线程池。
4. **结果回来了通知我**，我再执行下一步。

这就像一个**塔台调度员**。飞机（IO）起飞降落是飞机自己的事（内核/硬件），调度员只负责在无线电里喊：“跑道清空，可以降落（可以读了）”。

只不过在写原生的 C/C++ `epoll` 代码时，我们通常没有给它起个名字叫 `on_message`，而是直接把这坨代码写在了 `while` 循环的 `if` 语句里面。

为了让你彻底看清这两者的对应关系，我把“原生写法”和“封装后的回调写法”放在一起给你看。

### 1. 视角的转换：从“面条代码”到“回调函数”

#### A. 原生 Epoll 写法（你之前看到的）

这是最底层的样子，逻辑是写死的。

```C++
while (true) {
    // 1. 阻塞等待：老板（内核）去盯着
    int n = epoll_wait(epfd, events, ...);

    // 2. 遍历结果：老板把有动态的人名单给你
    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;

        if (events[i].events & EPOLLIN) {
            // ============================================
            // ↓↓↓↓↓ 这部分逻辑，本质就是回调函数 ↓↓↓↓↓
            
            char buf[1024];
            int len = read(fd, buf, ...); // 非阻塞读
            
            // 拿出这个 FD 对应的“拼图板”（Buffer）
            string& user_buffer = buffer_map[fd]; 
            user_buffer.append(buf, len);
            
            // 检查拼图是否完成
            if (check_complete(user_buffer)) {
                process_logic(user_buffer); // 执行业务
                user_buffer.clear();
            }
            
            // ↑↑↑↑↑ 这部分逻辑，本质就是回调函数 ↑↑↑↑↑
            // ============================================
        }
    }
}
```

#### B. 封装后的事件驱动写法（React/Node.js/Nginx 风格）

为了让代码不那么乱，架构师会把上面那段逻辑抽离出来，变成一个函数。

```C++
// 这就是传说中的“回调函数”
// 只有当数据到达时，才会被调用
void on_message_callback(int fd) {
    char buf[1024];
    int len = read(fd, buf, ...);
    
    // ... 这里写刚才的拼图代码 ...
    // ... 如果拼好了，就处理业务 ...
}

// 主循环变成了这样，非常清爽
while (true) {
    int n = epoll_wait(epfd, events, ...);
    
    for (int i = 0; i < n; i++) {
        // 内核通知我这件事发生了，我直接“调用”对应的处理函数
        // 这就是“事件驱动”
        on_message_callback(events[i].data.fd);
    }
}
```

### 2. 再看“拼图模式”

现在结合你刚才的理解：

1. **Event (事件):** 也就是 `epoll_wait` 返回的那一刻，告诉你“网线里有水流过来了”。
2. **Handler / Callback (回调):** 就是你写的那个“拼图代码”。
3. **Non-blocking (非阻塞):** 因为网线里的水可能只流过来了一半（只有 100 字节，但你要 200 字节），你的“拼图代码”读完这 100 字节，发现不够，**不能死等**，立刻函数结束（return）。
4. **Context (上下文):** 等下次 `epoll_wait` 又通知你时，你必须知道上次拼到哪了。所以你需要一个全局的 `buffer_map`（或者存在 Connection 对象里）来保存半成品的拼图。

### 3. 高级技巧：C++ 是怎么把“对象”塞进 Epoll 的？

你可能好奇：_“Epoll 怎么知道哪个 FD 对应哪个回调函数呢？”_

epoll_event 结构体里有一个神奇的字段叫 data。

大多数教程（包括我之前写的）为了简单，都只往 data.fd 里存一个整数 fd。

但在高手的代码（如 Nginx, Muduo, Netty）里，他们不存 `fd`，而是存**指针**！

```C++
struct Connection {
    int fd;
    string buffer; // 每个连接自带拼图板
    // 这是个函数指针，指向该连接对应的回调逻辑
    std::function<void()> callback; 
};

// 注册的时候
struct epoll_event ev;
Connection* conn = new Connection();
conn->callback = std::bind(&my_puzzle_logic, ...); // 绑定拼图代码

// 【关键点】我不存 fd，我直接存对象的地址！
ev.data.ptr = conn; 
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);
```

**于是，主循环就变成了真正面向对象的“回调”：**

```C++
while (true) {
    int n = epoll_wait(epfd, events, ...);
    for (int i = 0; i < n; i++) {
        // 1. 从事件里直接取出对象指针
        Connection* conn = (Connection*)events[i].data.ptr;
        
        // 2. 直接调用在这个对象上绑定的回调函数
        // 根本不需要 switch/case，也不需要查 map
        conn->callback(); 
    }
}
```

- **事件驱动 (Event-Driven)** 是**“灵魂”**（设计思想）。
- **Epoll** 是**“肉体”**（Linux 下实现该思想最高效的工具）。

- **F1 赛车的设计图纸**（事件驱动/Reactor 模式）是通用的。

### 3. 这个“高效代码”的核心公式

你刚才总结的这段话，其实就是高性能服务器的**“万能公式”**：

$$\text{高性能} = \text{Epoll (同步监控)} + \text{Non-blocking I/O (非阻塞读写)} + \text{Application Buffer (应用层拼图)}$$

- **少一个都不行：**
    - 没有 Epoll？监控 1 万个连接会累死（Select O(N) 问题）。
    - 没有 Non-blocking？读数据时会卡死整个线程（队头阻塞问题）。
    - 没有 Buffer？读到的半截数据没地方放（数据丢失问题）。
