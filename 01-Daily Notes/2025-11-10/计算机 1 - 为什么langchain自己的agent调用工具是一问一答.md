# 提示词模板

好问题！这是因为 **LangGraph 的 `create_react_agent` 使用了不同的提示词模板和工具调用策略**。

## 核心差异

### 2.py（你的手写 Agent）

```python
llm = deepseek.bind_tools(TOOLS)
ai = llm.invoke(messages)
```

- 直接调用原始模型
- 使用 OpenAI 标准的 **parallel tool calling**（并行工具调用）
- AI 一次性决定调用多个工具，**不生成中间文本**

---

### 3.py（LangGraph Agent）

```python
agent = create_react_agent(llm_model, TOOLS, system_prompt=system_prompt)
```
- LangGraph 内部使用了 **ReAct 提示词模板**
- 强制 AI 按照 **Thought → Action → Observation** 的循环
- 每次工具调用前，AI 会先生成"思考过程"

---

## LangGraph 内部做了什么？

`create_react_agent` 会在后台构造类似这样的提示词：

```python
system_prompt = """
你是阿强，最喜欢洗脚。你可以调用工具来获取信息，并给出有条理、简洁的中文答案。

你应该按照以下格式回答：
Thought: 我需要先思考一下该怎么做
Action: 调用某个工具
Observation: 工具返回的结果
... (重复 Thought/Action/Observation)
Final Answer: 最终答案
"""
```
**关键技巧：** LangGraph 会通过特殊的提示词格式，让 AI 在每次工具调用前先输出"思考"文本。

好的，我们把“工具调用”的整条链路拆成三层来讲：**为什么要这样走（演化与动机）→ 怎么一跳一跳地走（消息与状态机）→ 术语与实现要点**。你看完应该能把这条链在纸上画出来并说清楚“为什么必须多一轮”。

## 为什么要这样设计？

早期的 LLM 只接受纯文本提示、输出纯文本。要让模型“会做事”，就必须把**外部可执行能力**（检索、计算、读库、调业务系统）纳入对话循环。但为了安全与可控，执行权不能交给模型本体，而应由**宿主程序**（你的客户端/中间层）掌握；模型只给出“**我想调用哪个工具及其参数**”的意图。因此形成了今天的通用范式：

- **请求阶段**：把“我拥有哪些工具（名称、用途、入参模式）”明示给模型；
- **决策阶段**：模型基于用户消息与工具清单，产生一个或多个结构化的“调用意图”；
- **执行阶段**：由宿主去真的执行工具，得到**观察结果（observation）**；
- **收敛阶段**：把观察结果回灌，模型再基于它生成最终自然语言回答或进一步调用下一工具。

这使三件事得以同时满足：**安全（白名单+参数约束）、可测（结构化 I/O）、可编排（多轮循环与停止条件）**。

---

## 怎么做：消息流与状态机（按两种主流模式）

### 模式 A：**客户端编排**（以 LangChain/代理为代表）

这里的“服务器”仅指 LLM 服务商；工具执行都在你这边。

**一回合的最小闭环**（把它想成一个两次往返的状态机）：

1. **客户端 → LLM**
	
	- 内容：`messages`（对话历史）+ `tools schema`（你拥有哪些工具）
	- 形式：JSON 请求体里除对话，还包含工具清单与入参 JSON Schema（名称、描述、参数字段与类型、必填项等）。
		
2. **LLM → 客户端（决策）**
	
	- 返回一个“assistant”消息，其中**不直接给答案**，而是带 `tool_calls` 数组：

		```json
        {
          "role": "assistant",
          "content": null,
          "tool_calls": [
            {
              "id": "call_abc123",
              "name": "calculator",
              "arguments": {"expr": "(2+3)*4-7/2"}
            }
          ]
        }
        ```
		
3. **客户端本地执行工具**
	
	- 你查到相同 `name` 的本地函数/远程 API，先做参数校验（Pydantic/JSON Schema），再执行，得到结果（建议结构化）。
		
4. **客户端 → LLM（回灌观察结果）**
	
	- 把工具结果作为一条或多条“tool 角色”消息追加到对话里，并**携带同一个 `tool_call_id` 对齐**：

		```json
        {
          "role": "tool",
          "tool_call_id": "call_abc123",
          "name": "calculator",
          "content": {"value": 15.5, "explanation": "..."}
        }
        ```
		
5. **LLM → 客户端（收敛）**
	
	- 模型阅读观察结果，输出最终“assistant”自然语言回答；或再发起下一轮 `tool_calls`。
	- 你的编排层（LangChain/自写状态机）根据**迭代上限、停止信号**决定是否结束。

**要点**

- LangChain 在 `bind_tools([...])` 时，会把你的 `Tool/StructuredTool` 转为供应商支持的工具规范（名称、描述、参数 Schema）附加到请求中；在收到含 `tool_calls` 的响应时，为你解析出**要执行的工具清单**；执行后再把“tool 消息”帮你拼回第二次请求。
- 这就是为什么**必须多一轮**：第一次让模型给“调用意图”，第二次让模型基于**真实世界的观察**产出答案或继续行动。
- 多工具、并行调用时，`tool_calls` 会有多个条目；你可以并发执行，然后以多条“tool 消息”分别携带各自的 `tool_call_id` 回灌。

**流式细节（Streaming）**

- 一些供应商会**边生成边吐出 `tool_calls` 片段**；LangChain/SDK 在流里累积 delta，凑成完整的 `arguments` 后再触发工具执行。
- 你需要在流结束或检测到 `tool_calls` 完整时切换到“执行与回灌”分支。

**错误与重试**

- **参数校验失败**：构造一条“tool 消息”把错误描述（结构化）回灌，让模型自我纠正重试。
- **工具执行异常**：同样以“tool 消息”形式告知失败原因，是否重试由编排策略和上限决定。
- **幂等性**：对外部副作用工具（转账、下单）务必设计幂等键或在图里加“人工确认”节点。

---

### 模式 B：**服务端函数调用 API**（OpenAI/Anthropic 等的“原生工具调用”）

流程与模式 A 的对话结构类似，只是**工具清单直接传给模型服务端**，返回也直接包含 `tool_calls`。你仍然需要本地执行工具并回灌“tool 消息”。差异主要体现在**协议字段名与 SDK 封装**，但本质仍是**两次往返**的“思考—行动—观察—收敛”。

> 有的厂商宣称“服务端可执行工具”。即模型服务端替你跑了某些内置工具（如检索、简单算数）。这能少一次回合，但前提是：
>
> 1. 工具必须是供应商托管的；
> 
> 2. 你愿意把权限与审计交给对方。
> 绝大多数业务自有工具仍建议走**客户端执行**的安全边界。
>

## 实现要点清单（贴近 LangChain 客户端）

1. **工具声明（schema-first）**
	
	- 给每个工具定义**名称、描述、入参模式**（Pydantic/JSON Schema）；返回值也尽量结构化，便于后续链消费。
	- 描述里写清**单位、范围、前置条件**，帮助模型做正确映射（减少无效调用）。
		
2. **消息粘合**
	
	- 第一次响应若包含 `tool_calls`，**不要当成最终答案**；必须执行后再发第二次请求。
	- 回灌“tool 消息”要用**同一个 `tool_call_id`** 关联；内容可以是 JSON/文本，但倾向 JSON。
		
3. **编排与停止条件**
	
	- 简单场景：一次 `bind_tools()` + 一次执行足够。
	- 复杂场景：用 LangGraph/自写循环，设置**最大迭代次数**、**终止信号**（例如模型返回 `tool_calls=[]` 且有自然语言内容）与**失败分支**。
		
4. **流式处理**
	
	- 支持流时，监听增量片段：当发现 `tool_calls` 已完整，可提前中断自然语言生成，转去执行工具，提高时效。
		
5. **安全与审计**
	
	- 工具端做**白名单与参数校验**，对副作用操作引入**人工确认**或“只读—写入”两阶段。
	- 记录“谁调用了哪个工具、用什么参数、结果如何”，便于追责与复现。
		
6. **并行与缓存**
	
	- 多个 `tool_calls` 可并行执行；合并回灌后再请模型收敛。
	- 对纯函数工具接入缓存（键 = 工具名 + 规范化实参）能显著省钱省时。

## 常见误区

- **把第一次 assistant 消息当最终答案**：只要返回里出现 `tool_calls`，就还没结束。
- **工具返回纯自然语言**：模型二次推理会更稳，建议返回结构化 JSON，再由模型负责“解释给人听”。
- **没有停止条件**：代理兜圈子是常见坑。务必设上限，或在图里显式“终止边”。
- **让模型“自己执行”**：模型不能也不该执行任意代码；执行权在你这里，模型只给“意图”。

---

## 术语对齐（最后再给名词）

- **Tool/StructuredTool**：受约束的能力插槽；声明式名称+描述+入参模式。
- **Tool Calls / Function Calls**：模型在响应中产出的结构化调用意图（含 `name`、`arguments`、`id`）。
- **Observation（工具观察）**：你执行工具后生成的结构化结果，以“tool 角色消息”回灌。
- **ReAct/Agent 回路**：思考（计划）→行动（工具调用）→观察（结果）→再思考（收敛或下一步）。
- **LangGraph ToolNode**：把“执行工具”抽成节点，纳入图形化、有状态的编排。
