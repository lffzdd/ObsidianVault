先把「统一数据基座」这个词拆对——这决定了它会被建成什么样、花多少钱。给老板和 IT 看的时候，最容易出两个误区：一是 IT/外包听到「数据基座」就想上数据中台/数据湖（5 个亿、IT 弱的体量根本撑不住，也违背你「非为建而建」的纪律）；二是业务方以为它就是「帆软看板」（看板只是出口，基座是看板背后那套让数字可信、可复用的东西）。

所以我先给一个定调，再逐层落到部门能照着干。

## 一、基座不是一个系统，是三层；而且是"长出来的"不是"建出来的"

它由三层构成，缺一层都不成立：

- **语义层（口径字典）**——同一个指标全公司只有一个定义。这是地基里的地基，最便宜、最高杠杆。
- **数据层（分析数据）**——帆软真正去读的那份干净、对齐、留了历史的数据放哪。
- **治理层（谁拥有口径、怎么改）**——把上面两层从"项目里的临时约定"变成"公司资产"。

关键纪律：**这三层在每一期里只长到业务当期需要的大小**。一期帆软看板只读伯俊，就不需要单独的分析库；二期要跨库 join（会员）+ 要留历史（选品血缘），分析库才被业务"拉"出来；三期再收口成公司资产。基座的每一块，都是被前面业务用出来的沉淀，不是先盖好等业务来用。

**明确划出边界（写给 IT 和老板，防止预算跑偏）**：不做数据中台、不做数据湖、不做实时流、不自建 ML 平台。这套体量，分析库一个轻量实例 + 帆软 + 外包实施就够。

---

## 二、技术层：数据物理上放哪，怎么随三期长

你们的底子其实很好——**伯俊↔驿氪 已打通、驿氪↔企微 已打通，会员身份和交易能对应**。这意味着最难的"身份打通/数据采集"在源头基本解决了。基座不需要重新解决身份识别，只需要把这个已经对齐的 ID 一路带下去、留住、对齐口径。

数据流的走向是固定的，会变的只是"中间那层有多重"：

```
伯俊 ERP（交易/商品/库存/调拨/订货）─┐
驿氪 CRM（会员/分层/标签）──────────┼─→〔集成/同步〕→〔分析数据层〕→ 帆软 → 业务动作
企微（私域/导购关系）───────────────┘
```

中间那层随期演进：

- **一期**：帆软**直连伯俊（强烈建议走只读副本/从库，不要直连 POS 生产库）**，在帆软里建售罄/滞销数据集。**不建独立分析库。** 数据全在伯俊，这是最省、最快出活的。
- **二期**：两个需求把"独立分析库"拉出来——(1) 会员看板要 join 伯俊+驿氪+企微，在帆软里硬 join 会越来越吃力；(2) 选品血缘、生命周期状态这些**源系统会覆盖/不留历史的数据，必须有人按时间快照存下来**，靠查实时源库做不到。这时上**一个轻量分析库**（一台 MySQL/PostgreSQL 实例即可），ETL 把清洗、对齐、历史化后的表落进去，帆软改读这个库。ETL 由帆软实施伙伴建——IT 弱，这块必须外包。
- **三期**：**收口**。把分析库里被业务验证有用的那几张对齐表 + 口径字典，固化成"公司官方数据资产"，ETL 文档化、稳定化，以后所有报表都从这里出。销售预测（远期）就坐在这套已经历史化的数据上。

一句话给 IT：架构是 **直连（一期）→ 轻量分析库 + 历史化（二期）→ 收口成官方基座（三期）**，永远不碰中台。

## 三、语义层：口径字典——这一块是基座的命根子，写最厚

你最痛的"报表口径不统一、按部门分管"，根子在这层。**没有统一定义，帆软看板建不出来；建出来了部门也会为"你那个数怎么算的"吵起来，吵起来就没人按信号行动，止血就空转。** 所以一期就得起。

口径字典就是一张维护中的表（Excel/wiki 都行，别上 MDM 工具），每个指标一行，至少含：**指标名 / 精确定义（分子分母/层级/时间窗）/ 归属部门 / 唯一裁定人 / 受影响的看板 / 版本与变更日期**。

下面是**我建议的第一批必须先钉死的口径**（这些是提案，给商品/会员/财务拍——但请注意每条背后我标了"为什么是它先"）：

| 口径项 | 建议定义（待你们拍） | 层级 | 归属 | 为什么先做它 | |---|---|---|---| | 售罄率 | 上市后 N 周累计销售件数 ÷ 累计入仓件数（残次/退仓从分母剔） | SKC | 商品 | 一期看板"早期售罄异常"的核心，定义不定看板做不出 | | 早期售罄异常 | 上市后 4 周售罄率 高于阈值=卖太快(防断码/补货)、低于阈值=滞销预警；阈值按品牌/波段定 | SKC | 商品 | 一期止血信号本身 | | 季中滞销预警 | 上市 N 周售罄率<X% 且 在库件数>Y → 进预警池（还能救，触发调拨/折扣） | SKC/SKU | 商品 | 这是"行动信号"，跟下面的存量定义必须分开 | | 沉淀滞销 | 过季（季节结束+缓冲期）后仍未售出库存，按吊牌价计——就是那 2000 万 | SKC | 商品/财务 | "存量定义"，进清货池；和上面别混为一谈 | | 库龄 | 以**入仓日**起算（最客观，伯俊有）；分析动销时另叠加"上市时长" | SKU | 商品 | 区分"入仓库龄"vs"上市多久"，否则调拨进来的货库龄会被误读 | | 可售库存 | 门店在库 + 可调拨仓在库 − 残次 − 已分配未出；在途/调拨在途单列 | SKU | 商品 | 商品决策用"可售"，财务算资产用"含残次总库存"——**两个都对、用途不同，这正是部门吵架点，要写清** | | 销售额 | 吊牌销售额（看动销、不受折扣噪音）与 实收销售额（算清货 ROI/毛利）**两套并存、标签分清**；退货 T+N 冲减 | — | 商品/财务 | 商品看吊牌、财务看实收，长期口径打架的根源 |

二期再加会员与清货口径：

|口径项|建议定义|归属|
|---|---|---|
|三层会员|注册会员(10w) ⊃ 有效会员(近12个月有交易) ⊃ 私域可触达(已加企微且未删/未拉黑，<3w)——**基座要能同时算出这三层**|会员|
|私域净回收率|私域成交实收 ÷ 吊牌价|会员/商品|
|奥莱地板线|走奥莱的净回收率（成交÷吊牌 − 渠道成本）；**规则：私域净回收 > 奥莱地板线 才走私域定向清货**|商品/财务|

**变更流程**（轻量但必须有）：任何部门可提议改/加定义 → 跨域负责人裁定 → 裁定后即全公司定义，帆软看板必须用它 → 在字典里记版本、记哪些看板受影响。一个指标只能有一个裁定人，别让两个部门各执一套。

## 四、数据层：分两块——日常对齐表 + 选品血缘（后者是修 2000 万源头的关键）

**日常对齐表（一期起、二期入库）**：销售、库存、调拨、会员、触达，按上面口径清洗对齐。这块不难，伯俊数据齐。

**选品血缘（二期最重要的"打地基"，本身不出成果，但三期复盘全靠它）**：

要让"拍脑袋选品"变成"看战绩"，必须把这条链路**按时间快照留下来**——源系统不会帮你留：

```
订货会决策（订了哪些SKC、各订多少、谁拍的、依据什么）
   → 入仓/上市
   → 生命周期表现（逐周售罄、折扣轨迹、调拨、补货）
   → 终局（全生命周期售罄率、正价售罄占比、毛利、是否沉淀滞销）
```

再给每个 SKC 挂上**结构化商品属性**（品类/版型/价格带/波段/颜色/面料），三期才能学出"哪类属性好卖、哪类必沉淀"。

**这里有两颗必须二期处理掉的数据地雷，请 IT 和商品现在就去验**：

- **上市日是否在伯俊里干净、每个 SKC 都有**？所有"上市后 N 周"的指标都靠它，脏了全盘皆输。〔一期就该审计这一条〕
- **商品属性是结构化字段还是自由文本/空着**？如果版型、面料、价格带是手填散字段，血缘学不动。二期开订货模块时要**同时定一份小的"商品属性字典"，强制结构化录入**，否则血缘攒了等于白攒。

另外两个会员侧待确认：伯俊交易里**能挂到会员 ID 的占比有多少**（散客占比直接决定会员分析的完整度）；以及调拨会改变门店级"入仓"分母，**滞销信号建议在公司/品牌级看（调拨中性），门店级只用于运营动作**，别让搬货把售罄率搅乱。

## 五、治理层：联邦式拥有 + 中央裁定，不重组

呼应你定的"不重组、虚拟组、一把手授权"——治理也照这个来，**不要把数据收到一个团队**（你们 IT 也撑不住）：

- **域归属不变**：商品拥有商品/库存/销售口径，会员拥有会员/触达口径，财务拥有财务口径。
- **跨域负责人是口径字典的唯一主人**：各部门提议，他裁定冲突、持有主字典。这是"联邦拥有 + 中央裁定"，不是中央集权。
- **从项目级到公司级**：一期字典是虚拟组的工作文档 → 二期项目制跑顺、字典随会员/血缘扩 → 三期**字典升级成公司数据治理制度，跨域岗变常设**，并设一道"口径审查闸"——以后任何新看板/报表上线前，必须对齐字典才放行。这就是目标三"先用、验证、再收口"的兑现。

---

## 六、三期里基座的交付物（部门知道每期在交什么）

- **一期**：① 口径字典 v1（上表第一批，SKC/SKU + 售罄/滞销）；② 帆软直连伯俊（只读副本）+ v1 数据集；③ 上市日/属性数据质量审计报告（暴露地雷）。**不建分析库。**
- **二期**：① 轻量分析库 + ETL（外包建）；② 会员三层 + 清货口径入字典；③ 选品血缘骨架（订货快照 + 生命周期 + 终局 link 表）+ 商品属性字典强制录入。
- **三期**：① 分析库对齐表 + 口径字典固化为公司官方资产；② 口径审查闸 + 治理制度；③ 历史化数据就位，销售预测可起步。

## 七、部门照着干

|角色|在基座上具体干什么|
|---|---|
|**跨域负责人**|持有并裁定口径字典（贯穿三期）；一期组织第一批定义对齐；三期推审查闸与治理制度化、对基座 ROI 负责|
|**商品部**|一期拍售罄/滞销/库存/库龄定义、审计上市日数据；二期定商品属性字典、配合搭血缘、提订货决策需求；三期用血缘做订货会复盘|
|**会员部**|二期拍三层会员与净回收/地板线口径，提供驿氪分层与触达数据对齐需求|
|**财务部**|一/二期参与销售额（吊牌vs实收）、可售vs总库存的口径裁定，确保和账面对得上|
|**IT**|一期建伯俊只读副本、接帆软；二期协调分析库环境与源系统取数权限；**只做取数/对接/运维，不做建模**|
|**帆软实施伙伴（外部）**|一期建直连数据集；二期建分析库 ETL、历史化、血缘 link 表（IT 弱，这块必外包）|
|**一把手**|授权跨域负责人持有口径裁定权（关键，否则部门各执一套）；三期固化常设岗|
